卡 17　模型调优：先归因到层，再选训练方法 ​

要解决的问题 ​

Agent 出错时直接想到「换模型/训模型」，但工具协议含混、上下文缺失、权限失效、外部服务异常都不是模型问题。选错优化层，训练只会把系统缺陷固化进参数。

具体做法（步骤 / 机制 / 指标） ​

  1. 三层归因（模型 / Harness / 执行环境），按固定顺序排查：先排除能够独立复现的执行环境故障，再检查 Harness 的信息与运行控制，最后才判断模型能力缺口（原书表 17.1-1 给出每层的验证方法：绕过模型直调工具、固定模型改 Harness、固定 Harness 换模型）。
  2. 把「效果不好」拆成四类可训练的能力缺口：任务理解与约束识别、工具使用与反馈理解、多步决策与状态利用、失败恢复与合理终止。
  3. 指标三件套 + 安全护栏：质量（端到端任务成功率、关键动作正确性）、可靠性（同任务多次运行的波动）、成本（单位成功任务成本，失败任务的消耗也计入分子）、安全（越权与约束穿透单独报告）。
  4. 方法选择树：有可示范的正确行为 → SFT；存在多条可行路径且环境能给可验证反馈 → Agentic RL；教师已具备能力且目标是迁移/降本 → 蒸馏。三者可组合（蒸馏通常由教师数据上的 SFT 实现）。
  5. SFT 样本纪律：只监督「经验证的行为」；错误动作保留在上下文里帮模型理解为何修正，但屏蔽其训练损失；样本覆盖正常执行、多轮推进、异常恢复三类。
  6. Agentic RL 准入（原书表 17.3-1）：任务可重复执行、状态可重置、探索可隔离、过程可追踪；结果可验证比过程可标注更重要。奖励 = 任务结果 + 关键过程 − 执行成本 − 约束违反；训练奖励、独立评测、系统硬约束三者分离。
  7. 蒸馏两路线：黑盒序列级（只要教师文本/轨迹，跨 tokenizer 可用，企业主流）与白盒分布级（要 logits/log-prob，监督更稠密）。高风险任务保留教师校验；收益用「单位成功任务成本」核算，不只看 token 单价。
  8. 上线五道门禁：接口兼容、目标收益、能力回归（非劣效界值）、运行预算、安全硬门禁；灰度按影子验证 → 低风险灰度 → 分阶段扩量 → 稳定替换，回滚单位是「模型 + Harness + 环境」整个发布单元。

前置条件 ​

  • 已能量化区分「模型缺陷」与「Harness/环境缺陷」（按表 17.1-1 的验证方法做过对照）。
  • 任务分布稳定到值得投入数据与训练成本；训练条件与生产条件一致或被可靠适配。

适用边界 ​

  • 低频、快速变化的任务：轻量 Harness 调整通常比训练更经济。
  • 路径优劣无法可靠验证时不要上 RL——不可靠反馈会把偏差固化进策略。
  • 教师本身不稳定的任务不要蒸馏，只会更高效地复制错误。

反例 / 失败模式 ​

  • 把「字段含义没给到模型」当模型能力差，训完模型「猜得更好看」，根因仍在。
  • 蒸馏后 token 单价下降，但学生规划变差、重试增多，单位成功任务成本反而上升。
  • 训练奖励升高、独立成功率没动——奖励被投机（reward hacking）或验证器有漏洞。

可验证的效果指标 ​

  • 端到端任务成功率（含困难任务，固定任务构成比较）。
  • 单位成功任务成本 = 统计期内全部任务执行成本 ÷ 成功任务数（分子含失败与重试）。
  • 能力回归：核心通用能力非劣效；安全：越权尝试与约束拦截分别报告。

原文引用（逐字） ​

  • 归因顺序："先排除能够独立复现的执行环境故障，再检查 Harness 是否提供了充分的信息和可靠的运行控制，最后判断是否属于模型能力缺口。"
  • 归因到 Harness 的判据："若必要信息缺失、工具协议含混、状态不可见或反馈被截断，应优先修复 Harness"
  • 单位成功任务成本："可采用“单位成功任务成本”，即统计期内全部任务的执行成本除以成功完成的任务数量，失败任务消耗的资源也计入分子。"
  • SFT 样本处理："可以将错误动作保留在历史上下文中，使模型理解当前为何需要修正，但屏蔽该错误动作对应的训练损失，只监督经过验证的后续行为。"
  • 算法与设计的关系："算法不能弥补任务和奖励设计缺陷。"
  • 蒸馏核算："只比较 token 单价，会忽略学生因规划能力下降而产生的额外步骤和失败重试。"
  • 蒸馏边界："若教师在某类任务上本身不稳定，蒸馏只会更高效地复制其错误。"

一人公司 / 小团队降级做法 ​

  • 归因照做：这是全篇性价比最高的一步，一张表就能避免「用训练弥补系统工程问题」。
  • 训练降级为 prompt-only：把 SFT 的目标行为写成 few-shot 示例与检查清单；确实要微调时，用 LoRA（学习率取全参约 10 倍）在单卡上迭代。
  • RL 降级为「拒绝采样 + 人工抽检」：同一题让模型跑 N 次，保留通过校验的样本做 SFT 数据（DeepSeek-R1 / Qwen3 冷启动的同款思路，◇ 第三方公开做法）。
  • 蒸馏降级为级联：小模型/便宜模型先跑，规则校验或自评不一致时升级到强模型；兜底比例与单位成功任务成本用一张表按月核算。

卡 18　数据飞轮：先选一个业务问题，把第一轮闭环跑通 ​

要解决的问题 ​

上线后运行记录每天都在产生，但「单次排障」无法转化为「下次直接用」；团队搭了一堆看板，却说不出哪次改动真的有效。

具体做法（机制 / 步骤） ​

  1. 入口选最小业务问题：第一次建设调优流程时，先选一个团队确实想解决的问题（如「产品客服遗漏操作步骤」），不要一次性覆盖所有场景。
  2. 六步闭环：找到真实问题 → Pipeline 持续收集 → 写成题库 → 评估器持续运行 → 新旧版本同题对比 → 采用有效方案并继续接收反馈。
  3. 两条并行反馈路径：一条改进数据与判断标准（如给两类题分别写 Rubric），一条改进 Agent 行为（补 Skill、改工具描述、修重试逻辑）；两者都通过「同条件实验 + 回归」决定是否采用。
  4. 认知基线：会做、做完、稳定交付是三个层次——手册引用公开基准说明「一次做对」之后还要检查重复执行（◇ τ-bench：GPT-4o 原生工具调用 pass¹ 61.2%，pass⁸ 低于 25%）。

前置条件 ​

  • 有一个业务负责人能确认「什么算答对」。
  • Trace 已能记录执行步骤与工具返回（见卡 19）。

适用边界 ​

  • 日流量 < 50 次：先做人工抽样评审，不要铺 Pipeline。
  • 业务规则周更：先做题库版本管理（卡 21），否则实验失去可比性。

反例 / 失败模式 ​

  • 「搭了完整数据中台但没人用」：评估结果没有人工复核环节，样本与标准口头化。
  • 「只看平均分上升」：关键操作题仍失败，被总体均值掩盖。
  • 把样本数量、经验入库当收益——它们只是过程产物，有效变更进入运行后的新任务结果才是反馈。

可验证的效果指标 ​

  • 一轮闭环的节拍：从 trace 进 dataset 到评估器给出分数的端到端时延。
  • Badcase 入题库转化率；一次实验能说清「哪类题改善、哪类退化」。

原文引用（逐字） ​

  • 飞轮的本质："样本数量增加、经验入库、候选生成，都还只是过程产物。有效变更进入运行以后，新任务的结果才提供下一轮反馈。"
  • 起步原则："第一次建设调优流程时，先选一个团队确实想解决的问题。"
  • 正确性的判据："对话顺利结束、接口没有报错，都不足以说明这件事办对了。"
  • 评估与调优的分工："评估负责把“好不好”落实为可检查的标准和结果；调优负责根据这些结果改变系统。"
  • 能力层次："一次做对之后，还要检查重复执行的可靠性。"

第 18 章　Agent 调优总览（18.1 持续回答的问题、18.2 数据飞轮、18.4 从一个业务问题开始）

阿里云主张 / 第三方数据 ​

  • ◇ SWE-Bench Pro、OSWorld、OSWorld 2.0、τ-bench 等公开基准数字为手册转引的各家报告，用于说明「会做 ≠ 稳定交付」，不是企业业务成功率。
  • ✦ 手册给出的模块关系图与「六步闭环」是阿里云产品（Agent 观测与优化控制台）的操作路径抽象；流程本身可独立复现，按钮不可。

一人公司 / 小团队降级做法 ​

  • 用一张 Notion/Excel 题库 + 每月 50 条人工抽样评审起步；评估器从 1 个 LLM-as-judge + 1 段代码规则开始。
  • 「Baseline vs 候选」降级为「本周 vs 上周」同题对比，省去实验平台。
  • 反馈路径只保留一条：每次改动必须能在同一批题上重放，否则不算完成一轮。

卡 19　轨迹数据：先找到一条「自己知道发生了什么」的任务 ​

要解决的问题 ​

用户反馈「没解决」时，团队要在 trace 里定位：没理解需求、没找到材料，还是没用对材料。而大多数团队连「记录是否真的采到了」都没验证过。

具体做法（步骤 / 机制） ​

  1. 第一步亲手做：跑一条自己知道答案的任务，记下 TraceID/SessionID，逐字段核对记录（输入、输出、步骤数、Tokens、耗时、工具调用与返回）。不要仅凭开关已开启就认为数据已到达。
  2. 列表为空的排查顺序：先检查采集范围与筛选条件，区分「数据未采集」与「Agent 未正确执行」，避免反复发业务请求代替定位。
  3. 检索策略：已知 TraceID 精确查找；连续交互用 SessionID；没有标识时按「Agent 应用 + 模型 + 工具名 + 时间窗」从少到多加条件，结果为空先撤最近加的条件。
  4. 阅读顺序：目标与结果 → 概览（步骤/Token/耗时）→ 关键步骤（按工具名/关键词定位）→ 仅在怀疑字段缺失时看 JSON。结论要落到相邻事实：「用户要求操作步骤 → 检索返回了步骤 → 最终回答遗漏步骤」。
  5. 三条分析路径：工具失败看失败后的行动（追问/改参/重试）；耗时与 Token 偏高先找「多出来的工作」（重复检索、过大返回），不直接删步骤；业务质检核对「回答完成」与「业务结果真完成」。
  6. 三个对象边界：Trace（一次执行与调用）/ Session（一段连续交互，可能多任务）/ Trajectory（整理后的行为过程）——SessionID 不能自动证明同属一个任务。

前置条件 ​

  • Trace 采集已开启，字段覆盖 step、tool call、token、耗时。
  • 至少有一个能拿到 trace id / session id 的入口。

适用边界 ​

  • 日流量 < 10 条：直接读 trace JSON，省去检索界面。
  • 多 Agent 委派：必须看主子轨迹的委派关系与实际返回，不能只看子 Agent 是否结束。

反例 / 失败模式 ​

  • 「回答里说已完成」当作任务完成——业务结果未真正落地。
  • 「Tokens 高就压缩提示」——可能压掉必要检索上下文。
  • 把时间接近的记录认定为同一任务——任务边界要可靠身份关联。

可验证的效果指标 ​

  • 一条投诉从反馈到定位到具体步骤的平均时间。
  • 「回答完成」与「业务完成」的偏差率（可量化、可抽检）。

原文引用（逐字） ​

  • 业务质检判据："Agent 回答“完成”只是一条输出；工具接收请求、任务执行结束和业务目标达成都不是同一件事。"
  • 成本分析纪律："不要仅凭总 Tokens 高就删步骤。"
  • 排查纪律："先区分数据未采集与 Agent 未正确执行，避免反复发业务请求来代替定位。"
  • 对象边界："SessionID 帮助查找相关交互，但不会自动证明它们都属于同一个任务。"
  • Trace 的边界："适合定位某次执行和调用问题；能看到的范围取决于实际采集"

来源 ​

第 19 章　Agent 轨迹数据（19.1 第一条任务、19.2 检索、19.3 读轨迹、19.4 三类分析、19.6 三个对象）

阿里云主张 / 第三方数据 ​

  • ✦ AgentSpace、「数据中心 → Agent 轨迹」界面与 ATIF 轨迹格式是阿里云产品形态；「先跑一条已知任务核对字段」的方法与产品无关。
  • 通用可复现部分：已知任务核对、检索收敛策略、阅读顺序、三条分析路径、三对象边界。

一人公司 / 小团队降级做法 ​

  • 没有 trace 系统就自己加日志：每步记录 step_name, tool, args_hash, result_summary, duration_ms, tokens，一个 JSONL 文件即可。
  • 开源自托管：Langfuse / Phoenix / OpenLLMetry，两小时接入，先保证「一条已知任务能逐字段核对」。
  • 把「找一条自己知道答案的任务」写成团队 onboarding 必做项：先会读 trace，再谈调优。

卡 20　Pipeline：把 trace 持续变成「业务能直接读的样本」 ​

要解决的问题 ​

质检人员每天需要一张表：用户问了什么、Agent 怎么答、跑了什么操作、来自哪条 trace。而 trace 是事件级、字段是技术名词的，每次人工导出整理无法成为日常工作。

具体做法（步骤 / 机制 / 指标） ​

  1. 先定粒度再选入口：选择之前，先明确一行代表什么（一次任务 / 一次会话 / 一条并行路径）——这个决定后面所有分组、采样与评分。已有轨迹做评估选「轨迹数据」；从调用日志提业务字段选「Trace 数据」；只要问答优先「问答提取」。
  2. 第一条任务只做三件事：字段投影（input / output / 轨迹 + 来源 ID）+ 明确时间范围 + 输出到指定 dataset。去重、采样、LLM 标注都先不加。
  3. 预览先行：用真实样本预览，专门找「工具失败但回答成功」这类关键样本；如果过滤模块删掉了工具失败记录，调整条件保留。
  4. 从单次到周期：第一轮「单次执行 + 昨天时间窗」跑通后，另起「周期执行」任务按小时/天写日常 dataset，历史补数与周期起始衔接好。
  5. 按需叠加：人工复核超负荷时加随机/分组采样；没有业务标签时加 LLM 调用（分类/摘要，先供筛选，不作正式评分）；合成数据先入候选、人工确认后使用并保留来源标记。
  6. 三项长期约定：样本粒度、关键字段含义、数据用途——写下来，否则换人即换口径。

前置条件 ​

  • Trace 接入已完成（卡 19）。
  • 业务负责人能确认「收到这样的表能否开始工作」。

适用边界 ​

  • 业务场景单一（< 3 类）：无需聚类与 LLM 分类。
  • 高基数类目（> 20 类）：先 LLM 分类 + 分组采样，再人工复核。

反例 / 失败模式 ​

  • 首次就把所有处理模块全开：出错难定位是数据范围还是加工规则。
  • 输出 7 个字段但质检只用 1 个：配置被废弃。
  • LLM 标注结果直接当评分用：正式质量评分必须经可校准的评估器。

可验证的效果指标 ​

  • 「找到昨天的某类失败任务」查询时延（目标 < 1 分钟）。
  • 质检人员日处理样本量；Pipeline 任务成功率与平均处理时延。
  • 输出被持续消费的比例（有人用的字段数 / 总字段数）。

原文引用（逐字） ​

  • 三项约定："长期使用时，保留三项简单约定：样本粒度、关键字段含义、数据用途。"
  • 价值判据："管线简单而输出被持续使用，通常比配置了很多处理却无人消费更有价值。"
  • 粒度先行："选择之前，先明确一行代表什么。"
  • 预览纪律："如果过滤模块删掉了工具失败记录，也要调整条件。"

卡 21　黄金数据集：把「什么算对」沉淀为可复用题库 ​

要解决的问题 ​

每次升级临时找题、凭印象判断；团队成员对「什么算答对」各有一套标准，实验结论无法复现。

具体做法（步骤 / 机制） ​

  1. 黄金 = 题 + 标准：题目与标准可信；Agent 曾经答错的任务，补齐正确要求后同样可以成为黄金样本——保存这类题往往比只收漂亮成功回答更有帮助。
  2. 字段最小集：input（用户原始问题）、actual_output（原回答，供分析）、expected_output（业务认可的答案）、rubric（必须覆盖什么、允许什么措辞）、scenario（场景）、source_ref（来源）。
  3. 两类题的要求分开写：如「有哪些功能」（能力覆盖 + 说清用途）与「如何做评估」（必须给出可执行步骤）——共用评估器会导致评分错位；Rubric 要落到字段，不能只停留在讨论里。
  4. 三阶段流程：建候选集 → AI 标注 + 人工复核 → 确认的题选入黄金集 v1；证据暂缺或仍在争论的留在候选集。
  5. 版本管理：重要实验或规则更新前创建版本（写明版本号与依据），比较期间不再向其追加或修改数据。
  6. 三种用法：校准评估器（用好/坏/边界样本核对机器评分）、比较版本（同题跑基线 vs 候选）、长期回归（升级前重复运行）。
  7. 切分原则：参与改写 Prompt、生成 Skill 或提炼经验的题，与最后独立检查效果的题分开——后者要留未参与优化的独立验证集。

前置条件 ​

  • 已有 Pipeline 持续产出候选样本（卡 20）。
  • 业务负责人能给出 expected_output 与 rubric。

适用边界 ​

  • 业务规则日更：把变动最频繁的题隔离为「短期黄金集」，规则稳定后再固化。
  • 高风险操作（退款、权限变更）：把「业务应达到的状态」写进 expected，不只写文本答案。

反例 / 失败模式 ​

  • 只收低分题 → 看不到正常能力退化；只收高频题 → 漏掉代价高的少数情况。
  • 「这题应当这么答」停在口头 → 实验无法读取。
  • 黄金集与训练/改标题混在一起 → 间接过拟合，必须独立 held-out。

可验证的效果指标 ​

  • 黄金集覆盖的场景数与业务子能力数。
  • 评估器在黄金集上的人机一致率（人工抽样对比，> 80% 才信任持续评估）。
  • 每次升级前后的退化题数（回归集）。

原文引用（逐字） ​

  • 黄金的定义："“黄金”指题目与标准可信。"
  • 错题也是黄金："Agent 曾经答错的任务，只要补齐了正确要求，同样可以成为黄金样本。"
  • 训练/验证切分："参与改写 Prompt、生成 Skill 或提炼经验的题，与最后独立检查效果的题分开。"
  • 使用才算数："一份从未进入评估、实验或发布检查的数据集，即使整理得很精细，也还没有参与改进 Agent。"
  • 标准要落字段："仅在讨论中留一句“这题应当这样答”，实验并不能自动使用它。"

第 21 章　Agent 黄金数据集（21.1 用途、21.3 建设、21.4 选题、21.5 三种用法、21.6 版本与更新）

卡 22　Badcase 与评估实验：让「修过的 bug 不再回来」 ​

要解决的问题 ​

评估器分数一直在变，但团队说不清「哪条题修了、哪条题退了」；实验同时改模型和 Prompt，结论无法解释；修过的问题下次升级又回来。

具体做法（步骤 / 机制 / 指标） ​

  1. 评估器三件套：Code（结构/必填等确定条件）、LLM（切题与遗漏）、Agent（多步任务 + 轨迹一致性）。一个任务可挂多个评估器，但结果不能简单平均就代表业务质量。
  2. 试评三件样本：至少覆盖已知好、已知坏、信息不全各一条；检查「扣分依据是否真的出现在这条回答中」「是否引用了正确的工具结果」。
  3. 字段映射三步：用户问题 → 输入变量；最终回答 → 输出变量；过程判断 → 轨迹变量。需要「最终回答」的位置不能误接到某次工具调用的输出。
  4. 读 Badcase 四件套：原始问题 + Agent 回答 + 分项判断 + 解释一起读；不要看到低分便立即改 Prompt——先分辨是回答完整性、评估器/映射错误，还是执行异常。
  5. 实验单变量：先记录当前方案为 Baseline；若同时换模型、改 Prompt、增添 Skill，分数变化就难以解释；第一轮只改变最有依据的一项。
  6. 内网 Agent 接入：SDK 在能访问业务系统的环境执行题目再回传；有会话状态的 Agent 要「创建 Session → 发送 → 取最终响应」；API 先返回任务受理时必须继续等最终回答，不能把受理成功当作题目完成。
  7. 采用判定三问：严重错误是否消失，原来正常的场景是否退化，耗时与消耗是否可接受。
  8. 回归闭环：确认有效的题进回归集，评估器误判进校准集，未解决留下一轮。

前置条件 ​

  • 黄金集已建（卡 21）。
  • 实验能固定 Harness 与预算，仅改变一个变量。

适用边界 ​

  • 有状态 Agent：实验用独立 Session，避免上下文串味。
  • LLM 评审者：必须用人工标尺集校准，并检查长度/措辞/模型身份偏好。

反例 / 失败模式 ​

  • 总分上升就上线：关键条款未通过被均值掩盖。
  • 同时改 Prompt + 工具 Schema + 换模型：收益归因错位。
  • 用「受理成功」当任务完成：题目根本没跑完。
  • 结果出来后临时改统计口径。

可验证的效果指标 ​

  • 评估器人机一致率（人工抽样 50 条对比）。
  • Badcase → 修复 → 重测 → 确认不再回归的闭环时间。
  • 一次实验能定位的「改善题数 vs 退化题数」。

原文引用（逐字） ​

  • 单变量原则："若同时换模型、改 Prompt、增添 Skill，分数变化就难以解释；第一轮可以先只改变最有依据的一项。"
  • 采用三问："严重错误是否消失，原来正常的场景是否退化，耗时与消耗是否可接受。"
  • 映射纪律："需要“最终回答”的位置不能误接到某次工具调用的输出。"
  • 多评估器："不能把多个评估器的结果简单平均，就默认代表业务质量。"
  • 异步任务："如果 API 先返回任务受理信息，还需要继续等待最终回答，不能把受理成功当作题目完成。"
  • 排障纪律："不要看到低分便立即改 Prompt。"

卡 23　受控自进化：把「走通的方法」沉淀为 Skill / 资产 / 机制 ​

要解决的问题 ​

成功的方法只存在于老员工脑子里，下次相似问题仍从零探索；同类失败反复以不同变体重现；想上自动化又怕「自动跑偏」。

具体做法（步骤 / 机制） ​

  1. 先判断优化层：能写成方法的就不训练模型。例：排障 Agent 查询范围过大，先在 Skill 中补充「按故障时间和对象缩小范围」；查询工具不支持过滤，才由工具维护者补能力。
  2. 经验库建库三步：选应用与挖掘起始时间（覆盖成功、失败、失败后恢复）→ 抽查代表经验三件事（解决什么问题、建议什么动作、什么条件下适用）→ 回来源 Trace 确认动作真的出现过。
  3. 召回接入四步：安装召回 Skill → 配经验库地址与开关 → 开必要工具权限 → 用一条已核对的经验做真实查询验收，观察 Agent 在哪一步使用了它。口头说「参考了经验」不算，要对应真实调用与执行动作。
  4. 召回参数五维度：阈值、返回数量、触发时机（规划前 vs 失败后）、放置位置与长度、是否要求「经验是历史参考，采用前检查当前条件」。保留一组不使用经验的运行作 Baseline，用新 Session 重放同一请求。
  5. 资产四件套（按需交付，不必一次齐）：SQL 模板（现场值参数化）、Script/工具（封装分页解析去重）、Skill（何时用、确认什么口径、字段变化怎么办）、Workflow（固定步骤接成流水线）。最大开销来自重复生成查询就先交 SQL 模板；常漏验收就先修 Skill。
  6. Badcase 推动 Skill 改进：把原 Skill + 实际失败轨迹 + 相邻成功任务 + 预期行为交给优化助手生成局部补丁；用「目标 Badcase + 原本成功的任务 + 不应触发该 Skill 的任务」三组共同验收。
  7. Harness 改进：如「提交已发生但恢复后再次提交」——区分尚未开始 / 已经开始但结果未知 / 已经完成；结果未知时先核对业务状态。这类改动是执行代码/配置，交付前要在可控环境模拟中断点验证。
  8. 自动化三档：手动 → 半自动（系统整理候选、人比较与决定）→ 受控自动（规则范围内自动采用、异常交负责人）。适合先自动化的是高频、范围清楚、结果容易检查的动作。

前置条件 ​

  • 已有轨迹与评估器（卡 19、22）。
  • 团队至少有 1 人熟悉业务 + 1 人熟悉 Agent 工程。

适用边界 ​

  • 任务样本 < 100 条：经验挖掘意义有限，先写 Skill 文本。
  • 高风险任务：经验召回先限速（条数 + 风险分级），不全量启用。

反例 / 失败模式 ​

  • 「查询不到就扩大时间窗口」被不加条件复用：数据未接入导致永久空结果。
  • 把「自动调优」当「自动上线」：缺少四件确认。
  • Skill 越写越长成为通用注意事项：真正的方法被淹没。
  • 仅暂停挖掘却不停用旧经验：问题经验继续影响任务。

可验证的效果指标 ​

  • 同类任务「二次探索率」（重新查资料/试错参数的比例）下降。
  • 召回接受率（实际采用 / 召回条数）。
  • 自动化采用率 × 退化回滚率（看自动与人工的边界是否合适）。

原文引用（逐字） ​

  • 优化层判断："排障 Agent 查询范围过大，可以先在 Skill 中补充“按故障时间和对象缩小范围”；如果查询工具不支持过滤，就由工具维护者补能力。"
  • 采用四件确认："负责人确认四件事：目标问题是否改善，原有任务是否退化，额外代价是否可接受，目标 Agent 是否实际使用了被验证的内容。"
  • 召回验收："Agent 口头说“参考了历史经验”，还需要对应真实调用和执行动作。"
  • 自动化边界："适合先自动化的，是高频、范围清楚、结果容易检查的动作。"

卡 24　边缘运行时与全球优化：什么时候该管、什么时候别管 ​

要解决的问题 ​

Agent 在单一 Region 内已稳定，但用户分布全球后体验不一致：跨洋请求的网络传输可能占首 Token 延迟（TTFT）40% 以上 ✦（示例场景假设）；要不要上边缘优化？上到哪一阶段？

具体做法（机制 / 指标） ​

  1. 四个优化方向：延迟不对称（只有网络传输由物理距离决定，边缘就近接入命中它）、成本不透明（Token + 带宽 + 边缘请求统一计量，语义缓存卸载重复推理）、安全前置（DDoS 边缘清洗、Bot 拦截、Prompt Injection 前置初筛）、内容适配（HTML→Markdown 在边缘完成，减少二次处理延迟与 Token）。
  2. 分工原则：边缘能处理的（缓存命中、安全拦截、就近路由）不回源 Region；边缘处理不了的（复杂推理、状态变更、长任务执行）才进入 Region。判断「能处理」要看事实权威、身份与权限、写副作用、数据驻留和故障恢复语义。
  3. 边缘评估四维度：性能（全球各区域 TTFT P50/P95/P99）、成本（端到端调用成本、语义缓存节省量、回源流量占比）、安全（边缘拦截率、DDoS 吸收量、注入检出率）、体验（区域体验一致性、流式完整性、断连恢复成功率）。
  4. 发布准入双基线：Region 内指标 + 边缘指标同时达标才允许发布。
  5. 三阶段演进：阶段一边缘基础设施增强（Anycast、智能路由、DDoS 清洗、WAF/Bot、静态缓存、SSL 卸载；通常数天 ✦ 示例评估）；阶段二能力部署到边缘（语义缓存、内容转换、轻量推理）；阶段三原生边缘 Agent（EdgeFunction + RegionFunction 两级运行时 + AI 加速网关）。
  6. 语义缓存纪律：只覆盖公开、幂等、低风险请求；缓存键纳入租户、权限域、地区、模型、Prompt 和知识版本；定义 TTL、失效、来源标记与回源策略，避免跨租户泄露、越权、版本陈旧与个性化误命中。
  7. 全球统一基线 + 区域适配：Prompt、核心 Skill、基础安全规则全球一致；模型路由、缓存、安全规则按区域差异化——避免各区域独立演进造成能力割裂。
  8. 成熟度自评 L1–L4 ✦（本书归纳）：L1 无边缘优化 → L2 边缘加速独立看板 → L3 边缘指标纳入发布准入 → L4 边缘数据驱动自进化。不是越高越好，与全球化程度匹配。

前置条件 ​

  • Region 内已有稳定的调优与评估体系（卡 17–23）。
  • 已有真实跨区域流量或明确的出海计划。

适用边界 ​

  • 仅单区域运营：暂不需要边缘优化。
  • 严格数据驻留：语义缓存与全球分发按区域合规配置，必要时放弃边缘缓存。
  • 个性化强、权限敏感、时效性高的回答：不进语义缓存。
  • 流量规模小或缓存命中率低：边缘层额外成本可能超过收益——「不优化」也是正确选择。

反例 / 失败模式 ​

  • 「全球延迟差异大就上阶段三」：先用阶段一量化收益。
  • 边缘缓存跨租户共享键：数据泄漏。
  • 把「全球基线 + 区域适配」做成「每区域独立演进」：能力割裂、版本漂移。
  • 把示例指标（EdgeFunction 冷启动 <1ms、路由决策 <5ms、故障转移 <3s ✦ 示例目标）当成产品现状承诺。

可验证的效果指标 ​

  • 全球 P50/P95/P99 TTFT（分区域）；语义缓存命中率与 Token 节省率。
  • 边缘处理请求占比（阶段三）；边缘-Region 故障转移时间。
  • 边缘指标是否进入发布准入（L3 的判定信号）。

原文引用（逐字） ​

  • 分工原则："边缘能处理的（缓存命中、安全拦截、就近路由），就不回源 Region；边缘处理不了的（复杂推理、状态变更、长任务执行），才进入 Region。"
  • 就地完成的条件："只有无需权威状态判定、无需写副作用、且符合数据驻留要求的请求才适合在边缘就地完成"
  • 发布准入："一个版本如果在全球 P95 延迟上未达标，即使 Region 内评估全部通过，也不应被发布。"
  • 阶段选择："边缘优化同样不追求最高阶段，而是根据业务的全球化程度选择成本与收益最优的阶段。"
  • 数字的性质："本章出现的所有性能数字均为示例场景假设或架构示例目标，正式实施前必须由企业基线和压测校准。"
  • 现实建议："大多数企业长期停留在阶段一或阶段二即可获得显著收益"
  • 缓存边界："语义缓存应限定在公开、幂等、低风险请求范围内"

一人公司 / 小团队降级做法 ​

  • 不上边缘集群：用 Cloudflare/Fastly 的边缘 AI 网关或 CDN，按量付费。
  • 跨区域只做三件事：静态结果缓存、HTML→Markdown 中间件、一套 WAF 规则。
  • 「区域适配」= 不同 Prompt 模板 + 不同工具白名单，不做边缘运行时。
  • 先用卡 19–22 的体系把 Region 内做好；全球化成为真实需求时，从阶段一开始，别跳级。
