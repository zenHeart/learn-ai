AI Agent 工程实践卡：Harness、任务、信息与行动 ​

来源：阿里云《AI Agent Handbook》第二篇「构建」第 3—6 章（每张卡内附章节链接）。本页只做转述与提炼，每张卡附一句逐字引用，不复述大段原文。

读之前先分清两类内容：【可复现】 = 不依赖阿里云产品即可照做的工程机制；【主张】 = 阿里云团队对其产品或架构的陈述（产品行为、版本时间点等），以所查证版本文档为准，采用前需自行验证。第 3—6 章未给出可外部验证的效率数字，本页所有「效果指标」均为编者建议的可验证指标，不是原文承诺。

一、范式与入口（第 3 章） ​

卡 1｜先固定任务契约，再选构建入口 ​

  • 要解决的问题：团队从选框架、打开工具开始动手，做到一半发现权限边界、成功标准、验收证据都没有定义，Agent 行为无法测试、无法回滚、故障无法归属。
  • 具体做法：先写一份可机读的 Agent Contract——Agent 为谁工作、接受什么输入、交付什么结果、允许影响哪些系统、哪些动作必须拒绝或审批、什么证据能证明完成。之后才决定 Harness 由谁实现。原文把构建入口分四类（高代码框架自建 / 产品化 Harness / Managed Agents / 云产品），并强调它们的差异不是模型能力，而是「通用行为由谁实现、Runtime 与 Sandbox 由谁提供、企业还要补哪些控制和验收责任」；四类入口不是成熟度阶梯，也不必互斥。
  • 前置条件：能说清任务的成功标准；有一张系统影响面清单（哪些系统只读、哪些可写、哪些禁止触碰）。
  • 适用边界：契约不清时，换任何入口都不会解决问题——只是把不明确的行为转移到别处。审批、交易、客服、运营任务不能照搬 Coding Agent 的流程，应复用其中可泛化的 Harness 机制。
  • 反例/失败模式：漏洞修复 Agent 未获发布授权，却把「修复完成」解释为「已经发布生产」。
  • 可验证的效果指标：契约每条成功标准都对应一个可执行检查；新人只读契约即可复述该 Agent 的禁止事项；「完成」的证据清单可被逐条核对。
  • 原文引用：「构建 Agent 不能从选择框架或打开工具开始，而应先固定任务契约（Agent Contract）。」——第 3 章 范式：Harness 的主流构建方式和责任边界
  • 属性：可复现。
  • 小团队降级：一页 Markdown 分五节（目标 / 输入 / 输出 / 禁止 / 验收证据），每轮放进 system prompt；把「禁止发布」落成工具白名单和人工确认，而不是 Prompt 里的一句话。

卡 2｜用八类构建对象做生产准入检查 ​

  • 要解决的问题：Demo 能跑，进生产就缺东西——没有权限策略、没有恢复机制、没有评估基线；出故障时说不清该找模型、Harness、Runtime 还是平台。
  • 具体做法：按原文的八类构建对象逐项确认「开发阶段要回答的问题」和交付物：Agent Contract（角色指令、输入输出、成功标准）、Execution（Loop、状态机、预算、Verifier）、Context & State（Context Policy、Session/Task Schema、Workspace、Memory）、Capability（Tool Schema、MCP、Skill、Subagent、能力目录）、Environment（Environment Contract、Sandbox、Artifact 边界）、Control（Permission Policy、HITL、短时凭证）、Interaction（Event Schema、Streaming、Channel、恢复游标）、Quality（Trace、Outcome、测试用例、评估基线）。模型与这些行为配置共同版本化，线上结果才可复现、可回滚。
  • 前置条件：卡 1 的契约已存在。
  • 适用边界：最小 Agent 可以只实现一部分；但进入企业生产环境后，每一项都必须有明确责任人。**【主张】**原文以 QwenPaw 为例转述其官方文档：后台 Subagent 不可恢复、Sandbox 未启用约束时不自动提供隔离——「不能把功能可用直接等同于生产责任已经满足」。这是阿里云对第三方/自家产品文档的陈述，采用前以你所选版本的官方文档为准。
  • 反例/失败模式：把 Registry 里能注册大量能力当作生产就绪；把一次成功演示当作验收通过。
  • 可验证的效果指标：八项各有一个 Owner 和一个可检查的交付物；一次线上故障能按 Model / Harness / Runtime / Sandbox / Platform 分层定位到具体对象。
  • 原文引用：「一个最小 Agent 可以只实现其中一部分，但进入企业生产环境后，这些问题都必须有明确责任人。」——第 3 章
  • 属性：可复现（QwenPaw 产品陈述为【主张】）。
  • 小团队降级：检查表缩为四项——契约、权限（ALLOW/DENY/ASK 清单）、完成证据（脚本）、版本记录（git 提交即回滚单元）。

二、任务编排（第 4 章） ​

卡 3｜权威任务状态机与多维预算 ​

  • 要解决的问题：把消息历史当任务状态——长任务中模型「忘记」目标、重复探索、循环调用；失败后无法恢复；「在等待」和「卡死了」在观测上无法区分。
  • 具体做法：维护一份可机读的权威状态：目标、当前阶段、Plan/Todo、已确认事实、阻塞项、子任务、Artifact、剩余预算、等待原因、完成依据。状态显式化，至少包含：CREATED / RUNNING / WAITING_INPUT / WAITING_APPROVAL / WAITING_EVENT / PAUSED / VERIFYING / COMPLETED / FAILED / CANCELLED。预算进入 Loop：步骤数、总时长、Token 与费用、工具调用次数、子任务并发数、高风险动作次数；接近阈值时要求模型收敛范围、停止新委派、优先完成可交付部分或请用户选择；耗尽时产出明确终态与未完成清单，而不是悄然截断。模型看到的是由权威状态生成的「当前任务视图」，而不是从几百条历史消息里猜进度。
  • 前置条件：任务超过一次模型调用；有一个能存状态的地方（文件即可）。
  • 适用边界：状态显式化之后，上层 Runtime 才能在等待期释放计算资源；观测系统才能区分执行慢、审批慢、工具慢。
  • 反例/失败模式：只设最大步数，预算耗尽后静默截断，用户不知道缺什么、下一步做什么。
  • 可验证的效果指标：任意时刻能从状态文件回答「Agent 在等什么、下一步做什么、还剩多少预算」；等待中的任务不长期占用执行资源。
  • 原文引用：「消息历史记录了模型和用户曾经交换的内容，却不应成为任务状态的唯一来源。」——第 4 章 任务：编排、长程推进与协作流转
  • 属性：可复现。
  • 小团队降级：一个 STATE.yaml（目标 / 阶段 / todos / 预算 / 证据路径），每轮由脚本或 Agent 更新；预算先用「步骤数 + 分钟数」两个维度。

卡 4｜阶段门禁与计划外化 ​

  • 要解决的问题：长任务直到最后才验证，错误方向上持续投入；计划只存在于模型「脑子里」，用户无法审阅、无法干预、无法在中断后接续。
  • 具体做法：按复杂度选三种控制方式——轻量 Todo（目标明确、步骤少、反馈快）/ Plan Mode（影响面大、需要审阅、环境不明）/ Planner–Executor（长任务、多依赖、可并行）。把任务划阶段，每阶段门禁必须回答「输出是什么、证据在哪里、谁来确认」；原文的五阶段示例：影响分析 → 修复规划 → 变更实施 → 独立验证 → 发布准备。Plan Mode 把执行分为「只读探索 → 写入计划 → 人工确认 → 进入执行」：探索阶段只开只读工具和计划工具，计划落盘（如 plans/PLAN.md），Todo 存状态，两者都能跨调用恢复。计划必须允许修订：每次重规划说明触发事实并保留已完成项，不能靠改写目标掩盖失败。
  • 前置条件：任务可划分为有明确产物的阶段；工具有只读/可写两档权限。
  • 适用边界：Todo 只记录会改变任务可交付状态的事项，不记录每次微小工具调用；保持唯一当前进行项或明确的并行分组。
  • 反例/失败模式：只用 Prompt 要求「先规划再修改」——没有权限模式、工具白名单、持久状态与 HITL 共同生效时，这个约束不存在。
  • 可验证的效果指标：每个阶段有可检查的门禁证据；计划获批前，写工具调用次数为 0；中断后能从计划文件恢复而不重头探索。
  • 原文引用：「只有权限模式、工具白名单、持久状态与 HITL 共同生效，系统才真正具备“计划获批前不可写”的约束。」——第 4 章
  • 属性：可复现。
  • 小团队降级：在 Coding Agent 里先用只读/计划模式探索，计划写进仓库的 PLAN.md 供 review；阶段门禁用 CI 和测试脚本代替人肉检查。

卡 5｜受控委派：Subagent 契约与失败策略 ​

  • 要解决的问题：多 Agent 相互触发、子 Agent 权限过大、结果无法验收；或者不该委派却委派，通信与合并成本超过收益。
  • 具体做法：先判断是否值得委派——原文指出 Subagent 解决三个具体问题：上下文隔离（子任务只加载相关文件、工具和历史）、能力隔离（不同模型、指令、Skill、工具与权限）、并行执行（缩短墙钟时间）；三者收益不超过成本时不要委派。每个子任务携带可机读契约七项：目标与边界、已知上下文、能力与权限、预算、输出与证据、失败语义、验收条件。子 Agent 默认不继承父任务的全部上下文和权限——父任务有权委派，不意味着子 Agent 自动获得同等授权。显式定义失败策略：关键分析失败用 FAIL_FAST；非关键探索用 BEST_EFFORT；瞬时故障用 RETRY_OR_REASSIGN；需要业务决定时 ESCALATE。合并结果时校验输入版本和证据时间，避免采用基于旧代码或旧业务状态的结论。区分 Delegation（父任务保留责任，委派有边界的子任务）与 Handoff（控制权转移，接收者成为责任人）——二者都不能只通过一条自然语言消息实现。
  • 前置条件：父任务有稳定计划和预算；子任务边界可以一句话描述。
  • 适用边界：多个执行者同时修改同一工作区时，用隔离分支、对象级锁或补丁合并；评审必须读取固定的差异和测试结果，不能与执行者共享未提交的中间判断。
  • 反例/失败模式：把「任务完成」的责任一并交给子 Agent；研究 Subagent 的结论未经 Schema 校验和父任务验收就直接进入权威状态。
  • 可验证的效果指标：每个子任务有契约记录和父任务验收记录；并行任务墙钟时间显著小于串行；无未经合并的并发写冲突。
  • 原文引用：「多个执行者若同时修改同一工作区，应使用隔离分支、对象级锁或补丁合并，不能依赖“大家小心不要冲突”。」——第 4 章
  • 属性：可复现。
  • 小团队降级：用两个独立会话或两个 git worktree 做「实现 vs 评审」；把评审者的输入限制为固定 diff + 测试输出文件，不让它看到实现者的中间推理。

卡 6｜完成由证据决定 ​

  • 要解决的问题：模型说「已完成」但其实没完成——文件没生成、测试没跑、审批没生效。把自述当完成，错误直接流出系统。
  • 具体做法：模型只能提出完成申请，Harness 才能提交完成状态。按风险匹配五层验证：结构验证（Schema、必填字段、格式、文件存在）→ 环境验证（查询真实系统、检查文件差异与执行结果）→ 确定性验证（测试、规则、静态检查、业务校验）→ 独立模型验证（用独立 Context 检查质量与遗漏）→ 人工验收（高影响、主观或合规任务）。Verifier 返回结构化缺口、失败证据和可修复性；验证失败不是简单结束，而是新的 Observation——决定继续修复、重新规划、转交还是失败。完成结果是一组目标相关的事实，原文案例要求同时成立：受影响版本已被替换且无传递依赖重新引入、差异仅落在授权目录、测试与安全扫描有可寻址报告且强制项全过、独立评审无未关闭阻断问题、变更单含影响范围与回滚方案；且目标只到「形成可审批变更」时，不得把「尚未发布」误判为未完成。
  • 前置条件：成功标准可编码或可查询；有权威状态可挂接证据。
  • 适用边界：Verifier 是单次任务的完成门禁；跨版本判断哪个 Harness 更好属于 Evaluation Harness，不要把昂贵的发布评估器嵌进每次线上任务。过度验证同样是失败模式。
  • 反例/失败模式：目标是「形成可审批变更」，系统却因「还没发布」判失败；或反过来，模型自述完成就直接 COMPLETED。
  • 可验证的效果指标：每个 COMPLETED 任务附带证据清单（路径 / ID / 报告）；定期抽样审计「声称完成」与「证据支持」的一致率。
  • 原文引用：「模型只能提出完成申请，Harness 才能提交完成状态。」——第 4 章
  • 属性：可复现。
  • 小团队降级：把「完成」定义成一个脚本：测试通过 + 扫描通过 + diff 只在授权目录；Agent 自称完成不算，脚本跑过才算。

卡 7｜副作用、幂等与无进展检测 ​

  • 要解决的问题：超时后盲目重试，造成重复发布、重复通知、重复写库；Agent 陷入循环空转，烧钱且无产出，到预算耗尽才发现。
  • 具体做法：有副作用的行动在重试前必须先回答「上一次究竟有没有发生」——生成幂等键、记录请求与结果、优先查询状态；无法证明未执行时不直接重复。按失败类型选恢复策略：瞬时模型/网络错误用有界退避；参数错误修正后重试；环境缺失重建；权限拒绝等待或终止；重复探索重新规划；业务条件不满足则明确缺口。无进展检测比单纯最大步数更早发现问题，常见信号：连续调用相同工具且参数高度相似、反复得到同一错误、Plan 长时间不变、工作区没有新增事实、模型在少数行动间循环；检测后先要求模型依据结构化证据重新规划，再逐步缩小任务、切换能力、创建独立评审或转人工。切换模型、工具或环境的降级路径也要记录——能力、权限和结果质量可能已经变化。
  • 前置条件：写操作有幂等键，或有可查询的状态接口。
  • 适用边界：「Agent 失败」不是一个可执行的诊断，盲目重试只会增加成本和风险。
  • 反例/失败模式：发布类操作超时（可能只是响应丢失）后直接重发，导致重复发布。
  • 可验证的效果指标：重复副作用事件数（目标为 0）；从循环检测到人工接管的平均时长。
  • 原文引用：「有副作用的行动在重试前必须先回答“上一次究竟有没有发生”。」——第 4 章
  • 属性：可复现。
  • 小团队降级：用 CI 的幂等性（同一 commit 重跑同一 job 不重复副作用）；个人工作流里给所有写操作包一层「先查状态再动作」的脚本。

三、信息与可复用资产（第 5 章） ​

卡 8｜Context 分层编译与 Context Manifest ​

  • 要解决的问题：system prompt 是一个越长越好的字符串——关键约束被重复信息和低可信内容淹没；内容冲突时无法归因；模型「看不见」正确材料时无法调试。
  • 具体做法：把每轮模型实际收到的 System Context 当作一次「编译」：多来源按层级合并、冲突被处理、超预算内容被压缩或移除。System Context 六层（优先级从高到低）：平台策略（不可覆盖）> Agent 契约 > 租户/项目规则 > Runtime Reminder（当前阶段、预算、等待项、操作模式）> 本轮选中的 Skill > Tool Descriptors。Task Context 包括：用户目标与最新纠偏、Plan/Todo、最近交互、压缩历史、检索 Memory、检索 Knowledge、Workspace 引用。优先级函数同时考虑：约束强度、任务相关性、时间有效性、来源可信度、执行依赖、信息增量、Token 成本。管线先做身份与权限过滤，再做相关性排序——不要为了排序方便先把跨租户内容交给检索器或模型。每次模型调用生成一份 Context Manifest：来源类型与稳定 ID、作用域、版本、信任等级、权限依据、入选原因、token 数、变换方式（原文/摘要/截断/引用化）、内容 hash，以及 omitted 列表和排除原因。
  • 前置条件：规则、知识、工具有稳定标识和版本。
  • 适用边界：外部内容（网页、文档、工具返回、Memory）保留来源和信任等级，不能自动升级为系统指令；「模型看见了正确材料」要先于「模型推理有问题」被排查。
  • 反例/失败模式：所有内容拼成同一层文本——无法判断冲突来自哪里，更无法独立版本和回归。
  • 可验证的效果指标：出现「模型遗漏信息」类问题时，能先用 Manifest 回答本轮采用了哪些版本、为何选择、为何排除；两个 Agent 版本可比较 Context 差异。
  • 原文引用：「只记录 Prompt 文本无法稳定完成这些任务，因为同一文本片段的来源、权限和版本可能完全不同。」——第 5 章 信息：上下文、状态与可复用能力资产
  • 属性：可复现。
  • 小团队降级：把 AGENTS.md / 项目规则 / 当前任务状态 / 相关文件清单分成明确区块按序拼装，规则文件用 git 管版本；Manifest 先用「本轮拼装的区块标题 + 来源文件」清单代替。

卡 9｜压缩四步生命周期与大结果卸载 ​

  • 要解决的问题：历史无限增长——成本、延迟上升，注意力退化；简单截断最早内容又丢失初始目标和关键决定。
  • 具体做法：原始历史保存在外部状态，活动窗口只保留六区：稳定目标与约束、当前任务状态、最近逐轮交互、结构化历史摘要、本轮检索事实、Artifact 引用。「最近」不只按时间定义：用户对目标的最新修改、未解决的错误、待审批动作、验收失败证据即使更早也属活动状态。压缩不是普通摘要，必须保留：原始目标与成功标准、已确认事实及来源（区分事实/假设/模型建议）、已做决定及原因和被否决方案、已执行行动与副作用、当前 Plan/Todo/阻塞、Artifact 路径与外部对象 ID、用户偏好与审批结果、失败尝试及避免重复的原因。流程四步：Commit（事实先提交到权威状态）→ Compact（转结构化摘要，附来源与覆盖事件范围）→ Rebuild（用新摘要 + 当前状态 + 最近消息重装配，检查关键约束仍在）→ Validate（对目标、未解决项、权限模式、关键证据做完整性检查，并用续行用例验证行为无漂移）。数万行的大结果（日志、扫描报告、搜索结果）写入 Workspace / Artifact Store，窗口只留摘要、首尾关键片段、内容类型、大小、权限范围和可继续读取的引用；需要细节时按范围读取。压缩质量至少衡量：事实保留率、继续成功率、矛盾率、引用可用率、成本收益。
  • 前置条件：权威状态和 Artifact 存储先于压缩存在。
  • 适用边界：多次压缩仍不足以维持有效窗口、或任务进入新的大阶段时才做 Context Reset，且以 Continuation 已形成一致继续点为前提；新窗口从 Continuation Package + 权威状态重建，不重放全部对话。
  • 反例/失败模式：一次不准确的摘要改变了任务真实状态——因为事实没有先入权威状态就退出了窗口。
  • 可验证的效果指标：压缩或 Reset 后能在不重复大量探索的情况下继续；关键约束在压缩后仍可在窗口中被检索到；续行用例行为无明显漂移。
  • 原文引用：「任何会影响后续行动的事实，都应先进入权威状态，再允许从活动上下文中移除。」——第 5 章
  • 属性：可复现。
  • 小团队降级：长日志/扫描结果写文件，对话里只留路径和摘要；换新会话时粘贴一份「交接包」（目标 / 计划 / 已确认事实 / 待办 / 证据路径），不要重放全部对话。

卡 10｜Skill 渐进式披露与资产化 ​

  • 要解决的问题：能力一多就全塞进上下文——窗口耗尽、模型选错能力；一次成功任务的方法没有沉淀，下次从零开始。
  • 具体做法：Skill 告诉 Agent「在某类任务中如何正确使用若干动作」，由指令、脚本、模板、示例、检查清单和参考资料组成；它不直接拥有额外权限，只有在当前用户、任务和环境允许时，相关能力才能执行。渐进式披露三层：发现层只给名称、简短描述、适用条件和主要风险；选择层由 Harness 按任务、权限、环境解析候选并加载完整 Manifest（同时检查模型兼容性、工具依赖、环境条件、租户许可、版本状态）；执行层只在真正需要某一步时读取详细指令、脚本和参考资源。只读探索阶段的 Skill 可以被发现，但不能进入可执行状态。从成功任务沉淀：从 Trace 提取稳定步骤、移除特定任务 ID 和一次性判断、为脚本和模板补测试，再形成 Skill。当作软件资产管理：Registry 记录所有者、作用域、版本、依赖、权限需求、测试结果、弃用状态；生产执行不用 latest 指针；评估比较启用前后的任务成功率、步骤数、工具错误、人工修改量、成本和安全事件。
  • 前置条件：有 Trace 可提取；Skill 有版本和测试。
  • 适用边界：稳定、重复、可编码且失败代价高的步骤沉淀为脚本；需要理解模糊目标、比较方案、解释异常的部分留作模型指令；脚本仍要通过 Action Plane 和权限契约运行，不能藏在说明文本里被不受控执行。
  • 反例/失败模式：把一次任务的临时状态当成长期经验、把模型总结当成企业事实、把尚未验证的方法推广到所有项目。
  • 可验证的效果指标：Trace 能定位到具体 Skill 版本；Skill 启用前后成功率/步骤数/成本可比较；很少被采用或持续降低效果的 Skill 被调整、缩范围或下线。
  • 原文引用：「一次任务成功，不意味着它已经成为可复用能力。」——第 5 章
  • 属性：可复现。
  • 小团队降级：把反复用的流程写成带 checklist 的 md（如「漏洞修复 SKILL.md」）放进仓库按需读取；用 git tag 做版本；每次用完后补一条「这次改进了什么」。

四、行动与反馈（第 6 章） ​

卡 11｜统一 Action Plane：看见 ≠ 注册 ≠ 授权 ​

  • 要解决的问题：把「工具出现在 Schema 里」等同于「可以调用」——最小权限、用户委派、阶段只读全部失效；模型用通用 HTTP 或 Shell 自行拼接生产操作，审批和验证都无法精确落到具体动作。
  • 具体做法：行动链八步：Model Intent → Schema 校验 → 身份绑定（用户/Agent/任务）→ 策略决策（ALLOW/DENY/ASK）→ 审批/HITL → 执行（Tool、Sandbox 或 Remote Agent）→ Observation（结构化结果、错误、Artifact）→ 状态与 Trace。统一 Action Request 契约字段：action_id/task_id、capability_id/version、参数与输出 Schema、actor 身份、purpose 与当前任务阶段、环境与资源范围、副作用/可逆性/风险分级、幂等键与超时、审批与审计要求。Action 有生命周期：REQUESTED → VALIDATED → AUTHORIZED/WAITING_APPROVAL → RUNNING → SUCCEEDED/FAILED/CANCELLED。工具设计暴露业务语义：原文案例把「创建变更单」（change.create，中风险、可逆）与「发布生产环境」（production.deploy，高风险、ASK）拆成两个 Action——即使底层调用同一变更平台，也能分别授权、审计、重试和验证。
  • 前置条件：能力有 Registry（元数据、所有者、版本、作用域、依赖）。
  • 适用边界：模型产生的自由文本只能作为 purpose 的候选输入；能力名称、参数类型、影响范围和身份必须由确定性代码解析与校验。企业可以在 Registry 注册大量能力，却只向当前模型披露少数相关能力。
  • 反例/失败模式：策略仅按工具名称匹配——把用户对「生成草稿」的同意错判为「允许发布」，触发越权。
  • 可验证的效果指标：每次外部行动都能回答「以谁的身份、在哪个环境、依据什么策略」；高风险动作 100% 有审批记录和幂等键。
  • 原文引用：「模型产生的自由文本说明只能作为 purpose 的候选输入，能力名称、参数类型、影响范围和身份必须由确定性代码解析与校验。」——第 6 章 行动：受控执行、验证反馈与交付准备
  • 属性：可复现。
  • 小团队降级：工具白名单 + 写操作前人工确认（Coding Agent 的默认权限模式即可）；把「创建变更单」和「发布」拆成两个命令，后者永远手动执行。

卡 12｜权限三分与 Preview—Approve—Commit—Verify ​

  • 要解决的问题：要么什么都不问（越权、误操作），要么什么都问（用户形成机械确认，Agent 失去连续性）。
  • 具体做法：策略结果统一为三类：ALLOW（当前条件下可执行，记录决策依据）、DENY（无论模型如何解释都不得执行，向 Loop 返回结构化原因和允许的替代项）、ASK（动作可执行，但需要指定的人或系统确认）。ASK 不是默认兜底——优先用更窄的工具、参数约束、预览、资源范围和 Sandbox 降低风险，只在目的或后果无法由策略充分判断时请求人工。按风险定默认策略：读取当前项目内非敏感文件 ALLOW；查询当前用户有权查看的业务数据 ALLOW 或按数据等级 ASK；修改工作区文件但尚未提交外部系统 ALLOW（提供 Diff 与可撤销能力）；发送外部消息、发布、支付、删除、改变生产数据 ASK 或 DENY（要求预览和明确影响）；访问跨租户数据、绕过安全控制、请求长期 Secret DENY。HITL 分三层：Plan 审批、Action 审批、结果验收。不可逆或高影响动作统一走 Preview—Approve—Commit—Verify：Preview 展示接近实际提交的内容和影响；Approve 绑定身份、范围和对象版本；Commit 使用幂等键执行；Verify 查询真实系统状态。批准后 Harness 仍要重新校验对象版本和策略，防止等待期间环境已变化。
  • 前置条件：有身份体系和可执行的策略（规则文件即可）。
  • 适用边界：审批请求应包含：想做什么、为什么、以谁的身份、作用于什么对象、预计影响、参数与差异、是否可逆、失败如何处理、批准范围（仅本次 / 当前 Task / 一类受限动作）。
  • 反例/失败模式：为了「减少打扰」把整个 Session 切换成无条件放行；验证失败却把已发送的请求当作成功。
  • 可验证的效果指标：审批率与越权事件数同时监控（不是审批越少越好）；高影响动作 100% 走过 PACV；无法回滚的动作在 Preview 中明确标注。
  • 原文引用：「不是默认兜底。过多审批会让用户形成机械确认，也让 Agent 失去连续性。」——第 6 章
  • 属性：可复现。
  • 小团队降级：把风险默认策略表写成仓库里的 policy.md；用 Coding Agent 的 allowedTools 预授权只读工具，其余每次确认；发布、发送、支付类操作永远手动。

卡 13｜环境契约与窄工具优先 ​

  • 要解决的问题：Harness 假定「本机一定有某目录、某版本依赖或可访问公网」——环境不满足时模型进入不确定状态自行猜测；直接用通用 Shell / Computer Use 做高风险动作，副作用和攻击面失控。
  • 具体做法：提交 Environment Contract：镜像/OS/架构、文件系统挂载与读写范围、网络出入口策略、Secret 引用与委派身份、必需工具与版本、CPU/内存/存储/GPU 配额、超时/空闲/并发策略、持久化/快照要求、审计与清理策略。环境无法满足契约时，Action 应在执行前失败或请求降级。隔离粒度按 Agent/Session/Task/Action 选择，在线多租户至少按 Task 或 Session。原则：能用窄 Tool 完成的高风险动作，通常不应优先开放通用 Shell 或 Computer Use；处理长尾应用和非结构化工作区时，再用 Sandbox 把通用能力限制在可接受边界内。Secret 不出现在 system prompt、Tool Schema、Task State 或模型可见环境变量中；执行侧按 Action、身份和目的获取短时凭证，只注入目标工具或进程。环境销毁前确认 Artifact 与证据已转存、临时凭证已撤销。
  • 前置条件：能创建容器或等价隔离环境。
  • 适用边界：托管 Harness 与自托管 Sandbox 可以组合；关键是 Session、Harness 与 Sandbox 之间使用稳定的事件、状态和身份契约，不把长期 Secret 或完整企业数据复制到托管控制侧。稳定、确定性的步骤沉淀为 Tool/脚本/策略，需要模型理解目标和权衡方案的部分留在 Agent Loop，可能影响外部世界的动作统一经过权限和 Sandbox。
  • 反例/失败模式：Sandbox 允许修改代码副本，却提供生产集群凭证——工作区里的恶意文件诱导模型执行部署命令时，仍可能绕过企业 Action Plane。
  • 可验证的效果指标：代码修改 100% 发生在隔离工作区；执行环境无长期 Secret；环境不满足契约时 Action 在执行前失败而非带病运行。
  • 原文引用：「能用窄 Tool 完成的高风险动作，通常不应优先开放通用 Shell 或 Computer Use」——第 6 章
  • 属性：可复现。
  • 小团队降级：git worktree/分支 + 容器（或虚拟机）跑测试和生产构建；生产凭证不放开发机；Sandbox 网络默认禁止出站。

卡 14｜任务语义事件流与断线续传 ​

  • 要解决的问题：长任务只在结束时返回一段文本——用户不知道 Agent 在做什么、是否在等审批、是否遇到阻塞；断线后无法继续，客户端重复连接导致重复消费。
  • 具体做法：产生一组与内部事件对应、经过脱敏的外部语义事件，至少八类：Text、Progress、Tool、State、Approval、Artifact、Error、Usage；模型内部的隐藏推理不通过 Streaming 暴露。每个事件有单调序号或可恢复游标；客户端重连时从最后确认位置续传，服务端按 ID 去重；高频文本 Token 可合并或采样，但状态、审批、Artifact 和终态事件不能因背压被丢弃。Channel 只做适配层：身份映射、消息线程→Session→Task、附件/按钮/命令→统一输入事件、Harness 事件→渠道消息、跨入口保持任务连续、渠道级脱敏与审计；Channel 不应成为唯一状态存储。同一 Task 在不同 Channel 按接收者身份生成不同视图（开发控制台看 Trace，客户应用只看业务进度）。**【主张】**原文关于 Qoder Cloud Agents 的产品行为提示：2026-08-24 起不带 Last-Event-ID 的新 SSE 连接只接收建连后事件；session.status_idle 只表示当前回合结束，需结合 stop_reason 判断待响应动作，不能仅凭 idle 判定完成——以所查证版本文档为准。
  • 前置条件：事件有稳定 ID；Session 与 Task 分离。
  • 适用边界：用户发出 Cancel/Interrupt 后，Channel 要尽快确认请求已进入状态机，并区分「已收到取消」和「底层 Action 已安全停止」。
  • 反例/失败模式：把内部 Trace 原样广播给所有观察者；慢消费者被背压丢掉了终态事件。
  • 可验证的效果指标：断线重连后无重复副作用、无丢失终态事件；用户任意时刻能回答「Agent 在哪个阶段、在等什么」。
  • 原文引用：「状态、审批、Artifact 和终态事件则不能因背压被丢弃。」——第 6 章
  • 属性：可复现（QCA 产品行为为【主张】）。
  • 小团队降级：长任务放后台进程，状态写文件（task_id + 事件序号），轮询或通知只发状态变化和待审批项；不需要 AG-UI/A2UI 这类协议。

卡 15｜从 Trace 到 Harness Patch 的评估闭环 ​

  • 要解决的问题：出了问题直接改 Prompt——同一根因反复出现；两个版本孰优孰劣说不清，分数差异可能来自运行条件而非改动本身。
  • 具体做法：Task Trace 关联因果链：Agent/模型/Harness 版本、Session/Task/父子拓扑、Context Manifest 与压缩决策、Plan/Todo/状态迁移、模型调用与成本、Action Request/策略/审批、工具与环境结果、Workspace 变更与 Artifact、重试/降级/失败分类、Verifier 结果与完成证据、业务 Outcome 与用户反馈。Evaluation Harness 必须固定或披露模型、推理设置、Harness、工具版本、预算、重试、环境和评分规则。三层评测：单步（工具选对、参数正确、检索含关键证据）、轨迹（绕路、重复、越权、错误委派、过度消耗）、最终结果（Artifact、环境终态、业务 Outcome）。闭环：Trace+Outcome → 按症状与根因做失败聚类 → 诊断（Model/Context/State/Tool/Policy/Environment/Loop）→ 最小针对性 Harness Patch → 回归（原失败用例 + 相邻正常用例 + 安全对抗用例）→ 发布门禁 → 新版本。Patch 与根因一一对应：缺事实调 Context/Knowledge；错误经验反复出现修 Memory；不会执行稳定方法新增/修订 Skill；工具误用改进 Tool Schema 或权限；无进展调 Loop/Plan/模型；环境不一致修 Environment Contract；完成误判强化 Verifier；只有确定模型能力本身不足时才优先换模型或路由。
  • 前置条件：Build 时就有稳定事件、版本和关联 ID。
  • 适用边界：人工反馈不是天然真值，需区分用户偏好、业务结果和操作便利性；模型升级后要重新检查旧 Harness 里的补偿逻辑，删除已失效或阻碍新模型的规则。
  • 反例/失败模式：局部补丁通过回归、上线后损害了其他任务类型；或用单条失败直接改 Prompt，从不聚类归因。
  • 可验证的效果指标：每个线上版本可关联回归集与评估分数；Top 失败聚类有对应 Patch 记录；相邻正常用例在 Patch 后保持通过。
  • 原文引用：「如果 Build 时没有稳定事件、版本和关联 ID，后续平台无法补出可信的 Agent Trace。」——第 6 章
  • 属性：可复现。
  • 小团队降级：git + 固定测试集：每次改 Prompt/规则/Skill，跑同一组任务样本，对比成功/失败/成本；失败先按七类根因归类再动手。

五、一人团队 / 小团队降级路线 ​

上面每张卡都有单卡降级，这里给一条可在一个周末落地的最小路径：

  1. 契约一页纸（卡 1）：目标 / 输入 / 输出 / 禁止 / 验收证据五节，放进 system prompt。
  2. 状态外置（卡 3）：STATE.yaml 记录阶段、todos、两维预算（步骤 + 分钟）；长任务后台跑，人可随时查看。
  3. 先只读后写（卡 4）：计划模式探索，计划写进仓库，人 review 后才开写权限；门禁尽量用 CI/脚本。
  4. 写操作人工确认，发布永远手动（卡 11、12）：白名单 + policy.md；「创建变更单」与「发布」拆成两步。
  5. 完成 = 脚本证据（卡 6、7）：测试 + 扫描 + diff 范围检查全过才算完成；写操作前查状态。
  6. 大结果落盘 + 会话交接包（卡 9）：日志/报告写文件，对话只留摘要；新会话贴交接包而不是重放历史。
  7. 流程 md 化并版本化（卡 10）：反复用的流程写成 SKILL.md，git tag 管理，用完复盘改进。
  8. 改必有回归（卡 15）：固定一组任务样本，改 Prompt/规则/Skill 前后各跑一次，对比成功与成本。

不需要做的：四类构建入口的选型论证、Agent Platform、A2A/AG-UI/A2UI、多租户治理——一人团队直接复用产品化 Harness（CLI/SDK）即可，把精力放在契约、权限和证据上。什么时候升级：出现多租户、合规审计、长时恢复需求时，再回到对应章节深读（卡 2、卡 13、卡 14）。
