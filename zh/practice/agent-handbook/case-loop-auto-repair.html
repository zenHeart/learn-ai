Loop 工程实践：从报警到自动修复（PolarDB-X 案例） ​

案例来源：阿里云《AI Agent Handbook》第 25 章《研发效能》——从报警到自动修复，PolarDB-X 的 Loop 工程实践。 本页只做转述与提炼，不整段搬运原文；每张卡的引文均逐字来自该章，可点链接复核。

这套做法回答什么问题 ​

值不值得把 Agent 从「帮写代码」推到「自己接报警」？原文给的答案不是「模型够不够强」，而是三件工程事：

  1. 现场信息能不能让 Agent 按需查询，而不是研发截几张图喂给它；
  2. 修复过程有没有「稳定复现」这个门禁，让评审时有可复查的证据；
  3. Agent 能不能云端常驻，而不是每人本机各起一份。

原文对价值的判断落在一句话上：提效范围要从编码环节扩展到完整缺陷处理过程。

原文：第 25 章 · 2.4 节

「现场收集、根因排查、复现和测试验证由 Agent 自主完成后，研发可以围绕提交的证据和代码开展审查，无须再逐项承担前述工作。提效范围由编码环节扩展到完整的缺陷处理过程。」

原文把任务分成两类，也决定了适用边界：需求明确的新功能开发仍由研发主导、Agent 执行；只有具备明确验证方法的任务才交给 Loop 自主推进。

「对于这类任务，我们采用研发主导、Agent 执行的协作方式：研发负责方案和关键决策，并在开发、测试过程中持续把关；Agent 则承担具体的编码和测试工作。」

「其他团队可从具有明确验证方法的任务入手，接通所需信息和工具，完成从任务输入到结果交付的全流程，再根据实践逐步完善。」

卡 1：把 Agent 的任务起点前移到「收报警」 ​

要解决的问题 ​

原有流程里，研发既要编码测试，又要承担问题分析、根因定位和修复需求产出。一次修复最终可能只涉及几行代码，但排查吃掉了大部分时间——只让 Agent 帮写代码，省下的非常有限。

具体做法 ​

  • 换起点：从接收人工整理好的修复需求，改成直接接收报警或工单。
  • Agent 自认现场：自主确认问题发生在哪个实例、涉及哪些节点、运行什么版本、异常前后发生了什么。
  • 强制迭代：要求它沿线索持续查询——发现节点异常后查同期日志，发现状态变化后查源码，而不是一次成稿。
  • 固定产物：这一阶段必须输出问题现象、时间线、相关证据、待验证的原因假设这四件套，作为后续复现的检查目标。
  • 保留人在环：结论仍提交研发审查，不是自动合并。

前置条件 ​

  • 报警/工单系统有可程序化入口（webhook 或 API），且能带出实例、节点、版本、时间窗。
  • 至少有一条真实故障链路的完整日志、监控、拓扑可查（卡 2 展开）。
  • 有一份「这个系统通常怎么排」的 SOP 可沉淀（卡 3 展开）。

适用边界 ​

  • 适用：现象具体、能靠复现验证假设的任务——线上告警、工单、回归出来的缺陷。
  • 不适用：需求本身还在变的探索性开发（原文明确这类由研发主导、Agent 执行）。
  • 不适用：只有截图、没有数据入口的外部投诉；跨团队协调类工单。

反例与失败模式 ​

  • 把排查结果截成监控截图交给 Agent：它无法自己扩时间窗，只能等研发补材料。
  • 一次成稿：Agent 输出报告后不再自证，研发只能从零复核，等于没省事。
  • 起点前移但没有数据入口：告警直接扔给 Agent，等于把噪声放大。

可验证的效果指标 ​

  • 首轮由 Agent 完成处理的告警占比（原文内部口径：半年内所有报警先由 Agent 完成首轮处理和分析）。
  • 「等研发补材料」的回合数（目标趋近 0）。
  • Agent 产出的四件套完整率（现象/时间线/证据/假设缺一即不算完成）。

原文短引用 ​

原文链接：第 25 章 · 2.2 节 — 从人工整理需求到 Agent 自主分析

「这些表现促使我们将 Agent 的任务起点，从接收人工整理的修复需求，前移到直接接收报警或工单。」

「由 Agent 自主确认问题发生在哪个实例、涉及哪些节点、运行什么版本，以及异常前后发生了什么，将现场还原和问题分析一并纳入自主处理流程。」

「这一阶段应形成问题现象、时间线、相关证据和待验证的原因假设，为后续复现提供明确的检查目标。」

卡 2：把现场信息产品化——集中日志 + 结构化 CLI ​

要解决的问题 ​

Agent 分析到一半发现还得看另一个节点、或者再往前一小时，如果只能找研发要，它就退化成聊天机器人；研发成了人肉 API 网关。

具体做法 ​

分三层，从便宜到贵：

  1. 集中：日志等数据集中管理。分散在各生产节点时，查询要逐节点访问、检索、汇总；集中后 Agent 用一个入口跨节点、跨时段取数。
  2. 给现成 CLI/接口：常用平台提供结构化查询，返回 JSON 这类可解析结果（含节点、指标、采样点），让 Agent 按返回数据识别异常节点和时段，按需扩大范围。
  3. 让 Agent 自己把存量平台包成 CLI：没有官方 CLI 的平台，参考已有 CLI 实现，让 Agent 操作浏览器走一遍功能、分析接口请求与认证方式，再把所需功能封装出来。

前置条件 ​

  • 平台愿意给只读权限与稳定的 API/CLI；返回值结构化（JSON）而非渲染后的页面。
  • 有权限边界意识：Agent 用的是只读凭据，封装工具时不把高权限写进脚本。
  • 有统一的工具落点（一个仓库/一个包目录），避免每个排查各自造轮子。

适用边界 ​

  • 适用：任何需要按需跨节点、跨时段、跨指标关联分析的排查。
  • 不适用：认证方式本身敏感、不愿让 Agent 持有的平台；数据量小到人工看一眼就够的场景。
  • 提醒：线上多版本并存时，新版本修好的问题在老版本仍会出现，查询必须带版本维度。

反例与失败模式 ​

  • 只喂截图不喂接口：Agent 描述得了「看到了什么」，定位不到精确时间点。
  • 没先集中日志就急着封 CLI：CLI 底层仍逐节点抓取，结果不可复现。
  • 允许 Agent 自行封装高权限接口：省下的时间会以安全事故的形式还回去。

可验证的效果指标 ​

  • 常见查询走 CLI/API 的比例（目标：排查里 0 次人工截图）。
  • Agent 单次分析内的自主查询轮数（轮数上升 = 信息可达性变好）。
  • 「等待研发补充材料」回合数的下降曲线。

原文短引用 ​

原文链接：第 25 章 · 2.2 节 — 通过结构化接口支持按需查询、将存量平台封装为 CLI

「为便于这些工具查询和关联现场信息，日志等数据也需要集中管理。如果日志分散在各个生产节点上，查询仍需逐节点访问、检索文件并汇总结果；集中到统一平台后，Agent 就能通过统一入口获取不同节点、不同时间段的数据。」

「我们进一步让 Agent 完成这项工作：参考已有 CLI 实现，自主操作浏览器、使用目标平台功能，分析接口请求和认证方式，再编写代码，将所需功能封装出来。」

卡 3：把诊断方法沉淀成 Skills ​

要解决的问题 ​

排查套路只在老员工脑子里，Agent 每单都从零发明；工具用法散落在 wiki 和群里，Agent 检索不到，等于没有。

具体做法 ​

  • 把诊断方法、CLI 工具说明、排查经验整理成 Skills（不是给人读的 FAQ，而是给 Agent 按需调用的程序性知识）。
  • 一个诊断 Skill 的最小骨架：现象确认 → 查拓扑与基础指标 → 定位异常时段与组件 → 按原因假设选择验证手段（日志、火焰图等）→ 据结果调整方向。
  • 配套资源与 Skill 同处：采集脚本、指标字典、日志查询模板、常见问题诊断参考，随取随用。

前置条件 ​

  • 已有若干「按这个套路能定位」的真实案例可提炼。
  • 写 Skill 的视角切换：从给人解释原理，改成给 Agent 一步步可执行的判断与动作。
  • 与平台 Skills 机制对齐（本站已有 Agent Skills 页面可参考写法）。

适用边界 ​

  • 适用：有稳定套路、可脚本化的诊断流程（数据库、交易链路、CI 流水线、服务性能）。
  • 不适用：产品决策、业务策略这类没有对错判据的判断。

反例与失败模式 ​

  • Skill 写成散文：Agent 读不到下一步该做什么，退化成背景知识。
  • 脚本和文档分仓放：Agent 按文档找不到脚本，或按脚本不知道前提。
  • 只写不更新：旧套路留在 Skill 里，Agent 按废弃路径排查。

可验证的效果指标 ​

  • 单次排查中 Skill 被调用与命中的次数（命中 = 真的省掉一轮试错）。
  • 新成员/新 Agent 从上线到独立定位第一个根因的时长。
  • 「同一类问题重复摸索」的复现率（应随时间下降）。

「该 Skill 还配套提供采集脚本、指标字典、日志查询模板和常见问题诊断参考，供 Agent 按需查阅和调用。」

卡 4：给 Agent 运行时验证能力（保活调试会话 + 指定线程断点） ​

要解决的问题 ​

只读代码出根因报告，会把「可能发生的路径」当成「实际执行的路径」。原文的 MDL 案例里，Agent 给出的并发时序解释被人工验证推翻，之后多轮调整仍未收敛——静态推演解决不了执行顺序问题。

具体做法 ​

  1. 会话型调试 CLI：交互式调试器对 Agent 太笨重（要维护进程、反复收发命令、跨调用保状态）。做法是后台进程持续保活调试会话，前台每次一条命令、随用随退，下一次调用接着操作同一现场。
  2. 指定线程断点：只有目标线程触发断点，命中时只暂停该线程，其他线程继续跑；配合线程恢复操作，Agent 可以控制线程执行顺序验证特定时序。
  3. 闭环写进流程：暂停 → 观察状态 → 对照源码分析 → 回到同一会话继续执行，让调试过程与分析过程衔接，而不是各跑一遍。

前置条件 ​

  • 你的语言有可编程的调试接口（JVM 的 JDI、Go 的 Delve/DAP、Node 的 inspector 协议、Python 的 debugpy 等），能被包成 CLI。
  • 有权限在目标环境挂调试器（生产慎用，见卡 8 的隔离建议）。
  • 有可复现的环境可以挂会话（见卡 6）。

适用边界 ​

  • 适用：并发/时序类缺陷、状态机走错分支、偶发竞态、性能热点归因。
  • 不适用：纯业务逻辑错误（读代码就能定位，不必上运行时）。
  • 前提提醒：挂调试器会改变时序，结论要在同等条件下对照修复前后。

反例与失败模式 ​

  • 把 Agent 的根因报告直接当结论：原文案例里这正是被人工推翻的那一步。
  • 只复现一次就下结论：偶然未触发 ≠ 已修复（见卡 7 的对照要求）。
  • 只在最新版上验证：线上仍跑老版本时，问题可能照旧。

可验证的效果指标 ​

  • 提出假设到被实测否掉的收敛轮数（越少越好，理想个位数）。
  • 静态分析与运行结果不一致的假设占比（这是 Agent 自我校正能力的体检指标）。
  • 从低概率偶发转成可稳定复现的问题条数。

原文短引用 ​

原文链接：第 25 章 · 2.3 节 — 通过 JDB CLI 调试运行中的 Java 程序

「为此，我们基于 Java 调试接口 JDI 重新实现了 JDB CLI，通过后台进程持续维护调试会话。前台每条命令执行后即可退出，下一次调用仍能继续操作同一个调试现场，查看线程、断点和变量。」

「另一个关键能力是指定线程断点：只有目标线程会触发断点，命中时也只暂停该线程，其他线程继续运行。配合线程恢复操作，Agent 可以控制相关线程的执行顺序，验证特定时序下的程序行为。」

「偏差来自静态推演与实际执行的差异。」

卡 5：把内存现场集中化（Heap Dump + 查询接口） ​

要解决的问题 ​

排查对象泄漏、锁未释放这类问题时，光看代码不够，得看故障那一刻的内存状态：对象字段的值、引用关系。而 dump 文件动辄几十 GB，本地打开慢，逐项请人查又回到人肉环节。

具体做法 ​

  • 把 Heap Dump 放在大内存机器上集中加载和处理，不让它在不同人之间传来传去。
  • 给 Agent 提供查询接口：按需查对象字段和引用关系，拿到结果继续查相关对象，自主验证假设。
  • 分析完把记录和最终报告上传到展示平台，供研发事后查阅与复核（原文内部数据：累计两千多份处理任务）。

前置条件 ​

  • 有一台内存吃得下 dump 的机器（云上大内存实例或托管的内存分析服务）。
  • 一个能跑对象查询语言的服务端 + 简单查询接口（HTTP 即可）。
  • 采集侧能安全触发 dump（常见做法是收到告警后由人采集，而非让 Agent 直接抓生产）。

适用边界 ​

  • 适用：JVM 堆、Node 的 heap snapshot、Go 的 pprof profile、Rust 等能出进程级内存快照的运行时。
  • 不适用：内存占用本就很小的服务；无法安全采集 dump 的强合规环境。

反例与失败模式 ​

  • dump 落盘后在研发之间传：谁打开都要等，结论还不可复查。
  • 让 Agent 直接读大文件：token 和上下文都撑不住。
  • 没有归档与查询接口：分析记录随会话消失，下次同类问题重来一遍。

可验证的效果指标 ​

  • 从 dump 采集、Agent 取证到结论的总时长（目标：分钟级而非小时级）。
  • 单份 dump 的查询次数与假设否掉率（越高说明 Agent 在真的用证据纠错）。
  • 报告归档率（能否事后复查）。

原文短引用 ​

原文链接：第 25 章 · 2.3 节 — 通过 Heap Dump 查询内存现场

「Heap Dump 文件通常很大。我们将其放在大内存云服务器上集中加载和处理，并为 Agent 提供查询接口。」

「Agent 可以按需查询对象字段和引用关系，根据返回结果继续检查相关对象，自主验证分析假设，无须由研发逐项查询后再提供材料。」

卡 6：按故障条件分级提供复现环境 ​

要解决的问题 ​

有了调试能力，还得有个能真跑起来的环境。万能环境既贵又难对齐版本与拓扑，简单问题用它是浪费。

具体做法 ​

原文按「故障条件」给两级，让 Agent 自行选择：

环境适用情况使用方式
临时实例SQL 报错、功能异常等简单问题的初步复现创建最新版本的临时实例，完成验证后释放
完整复现环境依赖历史版本、特定拓扑，或需要控制并发时序的问题按问题实例的版本和拓扑搭建，结合调试工具验证
  • 同一套环境兼任修复验证：改完代码把修复版部署到对应环境，按已确认的复现步骤重放一次，检验原始问题是否解决。
  • 复现失败也是数据：首次没触发故障时，让它据实际执行路径重排线程关系、断点与执行顺序再试，而不是宣布「无法复现」。

前置条件 ​

  • 有可编程创建的临时环境（容器、临时实例、CI 里的环境）。
  • 有按版本/拓扑复刻的能力（版本号、节点数、分片规则等可参数化）。
  • 资源回收机制：临时实例用完即释放，避免自建环境变成成本黑洞。

适用边界 ​

  • 适用：能在测试环境重放的功能/时序缺陷。
  • 不适用：依赖真实生产数据、硬件抖动、外部第三方时序的偶发问题——这类靠观测证据而非复现。
  • 注意：线上多版本并存时，复现环境要按出问题那个版本建，否则等于没复现。

反例与失败模式 ​

  • 只在最新版本复现：改好了不代表老版本没问题（原文明确提到这个陷阱）。
  • 复现不了就结案：低概率缺陷恰恰要求把偶然交错变成主动构造的步骤。
  • 临时实例不回收：数量涨起来后没人敢删。

可验证的效果指标 ​

  • 首次复现成功率、平均复现尝试轮数。
  • 临时环境的平均存活时长与回收率。
  • 复现环境与线上版本、拓扑一致的比例（可抽查）。

卡 7：把「稳定复现」设为修复交付门禁 ​

要解决的问题 ​

评审时凭什么相信「真修好了」——靠口头描述、靠在测试环境跑一下没复现，都不可复查。没有证据的合并，就是把风险推给线上。

具体做法 ​

  1. 硬门禁：没有稳定复现用例，修复不进代码评审。
  2. 把复现固化成用例：复现过程直接写成测试用例；并发类问题可在关键位置注入延迟，换取可重复执行。
  3. 双向校验：该用例在修复前必须能触发原问题，修复后必须能正常通过，再叠加完整回归测试。
  4. 不通过就回环：没通过就继续分析和修改，直到满足要求。
  5. 评审顺序固定：研发先检查复现用例、对照原始问题确认它覆盖目标故障，再审查代码修改。
  6. 提交物成套：代码修改 + 复现用例 + 修复前后验证结果 + 回归测试结果，缺一不算完成。

前置条件 ​

  • 测试框架能承载这类用例：它本身就是故障触发器（可能需要测试专用 Hint 或注入点）。
  • 复现步骤可脚本化、可重复，不是「人手点一遍」。
  • 评审流程认这套证据（把复现用例 + 前后对照结果作为合并的硬性材料）。

适用边界 ​

  • 适用：能确定触发条件的缺陷修复，尤其并发/时序类。
  • 不适用：无法在测试环境重放的偶发问题——此时门禁要退化为观测证据加灰度监控，而不是硬套复现用例。
  • 边界提醒：挂调试/注入会改变时序，回归结论要单独跑一遍正常路径。

反例与失败模式 ​

  • 把没复现当通过：故障本来低概率，没触发不等于修好了。
  • 只交代码不交复现用例：评审退化成人工重走一遍排查，等于回到原点。
  • 只对照不复现：修复前后要在相同条件下跑，才能排除这次恰好没触发。

可验证的效果指标 ​

  • 进入评审的修复中带稳定复现用例的比例（原文内部数据：超过 70%）。
  • 修复后回滚/二次修复率（门禁有效的直接体现）。
  • 复现用例对原始故障的覆盖率（研发评审第一步就要核对这项）。

卡 8：把 Loop 放进云端沙箱常驻 ​

要解决的问题 ​

Agent 跑在每个研发本机上，状态不能复用、权限散在个人账号、无法 7×24 接告警；本机被 Agent 搞坏，损失的是自己的开发环境。

具体做法 ​

  • 云端承载：把 Agent 和任务流程放到云端沙箱，持续处理告警、推进修复。
  • 环境隔离：Agent 的运行环境与研发本地电脑隔离，沙箱被破坏也不影响本地开发环境。
  • 权限最小化：只授予完成任务所需的权限，限制它能访问和操作的范围。
  • 团队共用：成员共用同一套云端环境，协同配置和完善工具与流程（环境是团队资产，不是某人的私产）。
  • 产出可复查：分析记录与报告上传展示平台，供事后查阅。

前置条件 ​

  • 一个能被程序化创建/销毁的执行环境（容器、临时云主机、Codespaces 类服务）。
  • 告警能以 API/webhook 形式投递到该环境。
  • 权限模型设计：按任务类型授最小权限，凭据可轮换、可吊销。

适用边界 ​

  • 适用：需要长期待命的场景——值班、告警响应、定时巡检。
  • 不适用：所有动作必须由本人在本地发起才合规的场景（金融/政务的强留痕环境）。
  • 注意：常驻意味着风险常驻，隔离与最小权限不是可选项。

反例与失败模式 ​

  • 为了上云而上云：每人各装一套环境，成本和漂移双爆。
  • 沙箱权限给成管理员：出问题回滚比本机还难。
  • 没有可观测面板：不知道它在处理什么、卡在哪一步。

可验证的效果指标 ​

  • 累计处理告警数 / 累计完成修复数（原文内部数据：半年内从上万次报警识别并记录两百多个缺陷）。
  • 单条告警端到端时长（接收 → 复现 → 修复提交）。
  • 沙箱环境的复用率与故障隔离次数（隔离机制是否真的生效过）。

哪些是阿里云主张 / 内部数据，哪些可以自己复现 ​

结论性质你能自己做什么
稳定复现是缺陷修复里最重要的一步（团队主张）团队主张（文中明确是「我们认为」）直接当自家修复门禁，零成本
Agent 现场信息梳理优于人工团队内部观察，无对照实验自测：同一批告警人工 vs Agent 首轮，比对定位到根因的耗时与漏线索率
从接告警起步而非从接需求起步团队主张 + 内部实践任何有 webhook 的告警系统都能起步

一页速查：Loop 的三条工程经验 ​

原文最后收敛成三条，可当作自检清单——三条缺一条，Loop 就退化成聊天机器人：

  1. 让研发系统可以被 Agent 调用：把日志等现场材料集中管理，通过 CLI 或接口提供常用查询能力，并把诊断方法、工具说明和排查经验整理成 Skills，让 Agent 能够按需获取信息，沿着线索继续分析。
  2. 让研发过程可以验证：提供复现环境、调试和内存分析工具，让 Agent 自行检验假设，再将稳定复现的过程固化为测试用例，通过修复前后的对照验证和回归测试检查修改效果。
  3. 让任务能够持续运行：将 Agent 和任务流程放到云端，支持 7×24 小时持续处理报警、推进修复，并通过环境隔离和最小权限控制访问与操作范围。
