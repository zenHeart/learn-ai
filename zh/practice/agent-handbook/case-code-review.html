领域专用 Code Review Agent：把通用模型变成懂行的项目审查员 ​

来料：aliyun/ai-agent-handbook 第 25 章 · Kitta：领域专用 Code Review Agent

本页结论：AI 写的代码越多，瓶颈越不在「写」——原文说得很直白：「编码已不再受人力限制，但审查的人力并没有同步增长。产能的瓶颈，正在从"写"转移到"审"」。通用 Review 工具在这个位置上会同时栽两跤：工程行为约束不足（漏文件、位置漂移、提示词一变质量就抖）和检查深度不足（只扫代码本身的缺陷，不懂这个项目什么算问题）。Kitta 给的解法不是换个更强的模型，而是把通用 Agent 领域化：沉淀项目级专家资产、定制审查流程、建评测与进化闭环。本文把这套方法拆成 6 张可以照做的卡。

声明：本文每条主张都标了来源等级—— 【内部数据】 阿里云团队自己的生产环境统计，读者无法独立复现，只能作为量级参考； 【可独立复现】 机制、流程、API 形态，读者在自己仓库内可独立实施； 【外部可核实】 第三方公开报告，读者可自行核对。 原文末尾自己声明：「本文档为技术能力介绍材料，文中数据来源于内部评测与生产环境统计。」

1. 实践卡 · 用「项目级专家资产」替代通用最佳实践 ​

1.1 要解决的问题 ​

通用 AI Review 在两个维度同时失灵。原文的拆解很值得抄进设计文档：

  • 工程行为约束不足：「覆盖不全、位置漂移、效果不稳定——变更较大时倾向于只评审部分文件导致遗漏，报告的问题与实际代码位置对不上，评审质量随提示词的细微差异大幅波动。」
  • 检查深度不足：「缺乏对审查项目的语义理解，规则浮于表面——对每个项目、每次评审一视同仁，只能扫描代码本身的缺陷，感知不到项目特有的审查需求。」

落到具体症状：模型能识别「这段代码有 SQL 拼接」，但识别不了「这个仓库不允许引入新的同步 IO」。

1.2 具体做法 ​

【可独立复现】 从本仓库的真实历史里提炼资产，四步走：采集关联 → 规整去噪 → 语义解析 → 隔离复现。原文特别强调第四步：「其中"隔离复现"是为了让每一条缺陷模式与预期结论都可验证、经得起追问，而不是把噪音当经验。」

产物只有两类，但两类都不能少：

资产内容回答的问题
评判标准评审原则、缺陷模式、项目惯例「按什么标准判」
验证样本问题样本、正常样本、预期结论「判得对不对如何度量」

关键在于这两类是成对的：只有标准没有样本，你无法证明改了提示词之后是变好还是变坏（这正是卡 5 要接的问题）。

最小可复现形态（个人版，不需要做 pipeline）：翻 git log 和 PR 评论，挑 20–50 条「过去真的吵过架的改动」+ 10–20 条「明确 LGTM、一行没改的改动」，写成两份文件：review-rubric.md（判定标准）+ review-samples/（样本与预期结论）。这就是专家资产的最小形态，一晚上能建好。

1.3 前置条件 ​

  • 仓库有至少 3 个月可追溯的 PR / issue / commit 历史（否则只能从开源同类项目的惯例起步）。
  • 至少有一个人能把「什么算问题」写清楚——这项工作无法外包给模型，它就是领域知识的载体。
  • 样本需要人工确认一次（模型可以起草，人只做是/否）。

1.4 适用边界 ​

  • 适用：任何「有历史、有惯例、有隐性标准」的仓库——企业内部服务、长期维护的 SDK、基础软件。
  • 不适用：绿地项目（没有历史可提炼）、一次性脚本、几百行的个人项目（资产维护成本高于收益）。
  • 半适用：全新仓库但有强上游/标杆项目——可以从上游的评审惯例起步，但必须标注「这是外来的标准，不是我们的」。

1.5 反例 / 失败模式 ​

  • 把通用清单当专家资产。原文明确反对「泛泛的"最佳实践"」。CWE 全文、OWASP Top 10、某公司内部规范粘贴进来，长得像资产，实则对每个项目一视同仁，回到「检查深度不足」。
  • 跳过隔离复现。从旧评论里直接抓结论，会把当年误判的结论一起固化，并给它盖上「我们一直这么做」的权威。
  • 只写标准不写样本。评审质量从此只能靠感觉，而感觉正是原文要反对的：「用户说"好"不一定是真的好，Agent 自我感觉良好更是靠不住——没有客观的评估与进化闭环，信任就无从建立。」
  • 资产只增不减。半年后 rubric 里一半条目已被代码改动作废，Agent 会开始按废标准报警，团队直接关掉通知。

1.6 可验证的效果指标 ​

  • 分类型意见采纳率（原文口径）：回合补丁一致性检查 70.4%，自研 PR 代码质量意见 41.8%。【内部数据】
  • 同类问题复发率：某个已被写进 rubric 的缺陷类型，在后续 20 个 PR 里再出现的次数。
  • 人工复核时间：Maintainer 花在「确认这条意见对不对」上的时间，而不是花在逐行读 diff 上。

1.7 原文逐字引用 ​

「通用模型见过很多代码，但未必懂内核的锁语义，也未必懂编译器的中间表示约定——而这些恰恰是评审结论对错的关键。」

「领域知识不是凭空来的，而是从真实历史中提炼的。」

2. 实践卡 · 五阶段分级流水线：先分类，再规范，再依赖，最后质量 ​

2.1 要解决的问题 ​

一次性把所有检查糊在一个大 review 里，会同时踩三个坑：成本浪费（对自研补丁跑回合补丁专属检查）、报告淹没（所有问题同级，没人看）、定位困难（评论挂不到具体行）。

2.2 具体做法 ​

【可独立复现】 Kitta 在 ANCK 上跑的是一条五阶段流水线，触发方式是提交 PR 或在评论里输入 /check-code-review。原文的顺序设计值得直接照搬：

阶段做什么为什么放这个位置
Stage 1. PR 分类判断纯自研补丁还是回合补丁分类决定后续检查范围
Stage 2. PR / Commit Message 规范检查基于社区规范文档检查描述、标题、commit message最便宜、拦得最多
Stage 3. 补丁完整性检查追上游依赖链，找遗漏的 Fixes只对回合补丁执行
Stage 4. 补丁回合一致性检查三层对比上游原补丁只对声明了上游来源的补丁执行
Stage 5. 代码质量审查通用质量维度，按严重程度分级最后兜底

三个关键机制：

  1. 分类先于检查。Stage 1 的判据极简：「如果 Commit 中存在类似 commit xxxx upstream 的上游补丁声明，则归为回合补丁。」原文点明收益：「纯自研补丁不会执行补丁完整性检查和回合一致性检查，避免不必要的开销。」这就是一个十行的正则，收益是砍掉 2/5 的审查开销。
  2. 没有问题则不报告。Stage 2 原文：「没有问题则不报告；有问题则给出 Message 规范建议，供开发者参考。」——沉默是默认态，这是「克制打扰」在工程上的落点。
  3. 结论用分层标签输出，而不是一段自然语言。Stage 4 的差异分级是 consistent → text-inconsistent → semantic-inconsistent → inconsistent；Stage 5 的严重度分级是 Critical / Medium / Low，没风险直接给 LGTM。

2.3 前置条件 ​

  • 有 PR 模板和 CI 触发能力（GitHub Actions / GitLab CI 等价物均可）。
  • bot 有仓库读权限；Stage 3–4 还需要上游仓库或邮件列表的读权限。
  • 严重度标签有明确定义——否则分级只是换了个词。

2.4 适用边界 ​

  • 适用：多提交、多人、有人工 maintainer 的仓库。
  • 可裁剪：单模块小仓可合并 Stage 3+4；没有上游同步场景的直接删掉 Stage 1 的分类和 Stage 3、4，只留 Stage 2 + 5。
  • 不适用：一次性脚本、无人 review 的个人实验分支。

2.5 反例 / 失败模式 ​

  • 不做分类就全量跑。所有检查无差别执行，成本翻倍，且回合专属的检查在自研补丁上必然误报。
  • 所有问题同一优先级。Critical 和「命名不够好」混在一张清单里，前者会被淹没。检验方法：如果 Critical 与 Medium 的采纳率相近，说明分级是装饰性的，该重做。
  • 评论不落行。原文批评过「报告的问题与实际代码位置对不上」——不落行的评论等于让开发者手工二次定位，等于没审。
  • Stage 2 变成噪音源。规范检查最容易被写成挑刺清单，「没有问题则不报告」这条纪律必须写进代码，不能靠自觉。

2.6 可验证的效果指标 ​

  • 单 PR 审查耗时（含模型调用与排队），分自研 / 回合两类分别统计。
  • 分层采纳率差值：Critical 与 Medium / Low 的采纳率之差。差值小 = 分级失效。
  • Maintainer 追问回合数：原文称「大幅减少了 Maintainer 反复追问、来回确认的回合数」，但未给出具体数字——读者应把它当成待验证假设，自己在 10 个 PR 上量一次。【内部数据（无量化）】

2.7 原文逐字引用 ​

「开发者提交 PR 或在评论中输入 /check-code-review 后，审查任务即被触发；整个流程先分类、再检查规范与依赖、最后落到代码质量，层层递进。」

「Kitta 将审查出的问题按严重程度分为 Critical、Medium / Low，Critical 问题通常会以内联评论定位到具体代码行，需要开发者处理或明确是否为误报；未发现风险则给出 LGTM。」

3. 实践卡 · 上游依赖链完整性检查（「该带什么」比「改了什么」更重要） ​

3.1 要解决的问题 ​

回合 / backport 场景有一个通用 Review 抓不到的缺陷类型：这次改动本身是对的，但它依赖的其他补丁没跟过来。于是下游重新引入了上游早就修掉的漏洞——而且代码看起来完全正常。

3.2 具体做法 ​

【可独立复现】 Kitta 的检查是一个三段式判定，Stage 3 原文写得很清楚：

「按"检索上游 Fixes → 判断是否在 PR 中 → 判断是否在下游仓库已存在"的流程排查遗漏。」

输出必须是三类互斥的结论，而不是一个布尔值：

输出含义处理
无遗漏 Fixes无需补充放行
已合入的 Fixes 补丁相关修复已存在于下游仓库放行（且要能指出是哪个 commit）
遗漏的 Fixes 补丁需要开发者补充拦截，「防止已知漏洞被重新引入下游」

一致性检查同理，分三层递进：基础对比（改了哪些文件、哪些代码块）→ 上下文对比（引用的符号、函数、变量定义是否一致、是否做了合理适配）→ 语义对比（由 LLM 判断上下游是否实现了相同功能）。

补丁完整性检查在 3.1 节被称为「采用四阶段遗漏 Fixes 检索流程」，而 Stage 3 正文只展开了三步。两处口径不一致，原文未说明第四步是什么；读者照做时按三步起步即可，不要卡在这里。

3.3 前置条件 ​

  • 有可访问的上游源：公开 Git 仓库、邮件列表，或至少能拉到上游 git 历史。
  • commit message 里有稳定追溯线索：commit xxxx upstream、Fixes: 标签、或可解析的原始 commit id。没有线索就得先补线索，否则这一步没法自动化。

3.4 适用边界 ​

  • 适用：内核回合、cherry-pick / backport 修复、把上游配置或 vendor 目录同步进内仓、从上游抄安全补丁。
  • 可外推：任何「从别处搬代码进来」的场景——包括抄开源库源码、升级 vendored 依赖、迁移老代码到新框架。依赖闭包的逻辑一样。
  • 不适用：纯自研、无上游的模块；上游不可访问的闭源组件（此时退化为「本仓库同类修复清单」人工 grep）。

3.5 反例 / 失败模式 ​

  • 只问「这次改了什么」，不问「该带什么」。这是回合场景最典型的漏判，也是 Stage 3 存在的全部理由。
  • 把「已合入」和「未合入」混成一个布尔输出。开发者无法区分「不需要处理」和「没查到」，噪音直接翻倍。
  • 把「逐行都对」当成一致。原文对一致性检查的方案描述里有一句是对所有 Review 的警告：「方案上先微观溯源、比对补丁级差异，再宏观评估整体功能是否一致，避免"逐行都对、整体变了"的漏判。」适配改动越多的回合，越容易出现「每个 hunk 都对、合起来语义变了」。
  • 依赖 LLM 去数 Fixes 标签。这类工作应该由脚本按 git 历史确定性完成，交给模型只会引入不稳定性。

3.6 可验证的效果指标 ​

  • 遗漏检出率：在已合入的历史 PR 上回溯跑一遍，看能捞出多少「当时漏带的补丁」——这是建立信任的关键实验，成本很低。
  • 补齐率：被报遗漏的 PR，最终有多少真的补上了。
  • 回合补丁一致性意见采纳率 / 准确率：原文为 70.4% / 99.8%。【内部数据】。这个数字远高于自研 PR 场景，恰好说明：确定性可判的检查，AI 的意见才敢当真。

3.7 原文逐字引用 ​

「检查结果分为三类：无遗漏 Fixes 表示无需补充；已合入的 Fixes 补丁 说明相关修复已存在于下游仓库；遗漏的 Fixes 补丁 则要求开发者补充，防止已知漏洞被重新引入下游。」

「基础对比看修改的文件和代码块是否一致；上下文对比看引用的符号、函数、变量定义是否一致、是否做了合理适配；语义对比则通过 LLM 判断上下游补丁是否实现了相同功能和语义。」

4. 实践卡 · 按子系统切知识库 + 「有罪推定—调用链分析—自我辩论」 ​

4.1 要解决的问题 ​

同一份 checklist 覆盖整个仓库，等于没有 checklist。内核的不同子系统关注点差异极大（并发子系统看锁语义，文件系统看崩溃一致性，网络栈看协议状态机）；用同一套标准审，只会得到泛泛的「最佳实践」。

4.2 具体做法 ​

【可独立复现】 两件事叠加。

（a）知识库做子领域拆分。原文：「内核不同子系统的评审关注点差异很大，按子系统组织专用知识库，让评审贴合各子领域的真实惯例」。

落地形态：目录即子系统。先把仓库按目录划成 3–6 个子系统，每个子系统一份 checklist.md，由这个子系统的 owner 维护。Review 时先分类到子系统，再加载对应清单——这一步用规则做（看 diff 落在哪些目录），不需要模型。

（b）深度审查走三段流程。原文定义的流程是「有罪推定—全栈调用链分析—自我辩论」：

「引入"有罪推定—全栈调用链分析—自我辩论"的审查流程：先假设代码有问题，沿全栈调用链追语义，再自我辩论验证结论，加强对内核常见关键代码风险的识别深度。」

拆成 Agent 可执行的动作：

段动作对抗的错误
有罪推定不问「有没有 bug」，直接问「这段改动最可能引入什么后果」默认收束到「看起来对」
全栈调用链分析沿调用者/被调用者追语义，找可达路径上的约束孤立看 diff 片段，漏掉跨模块不变量
自我辩论生成「支持有缺陷」「支持无缺陷」两段论证，再由结论环节按证据裁决单次采样幻觉（一次生成说没 bug 就信）

硬约束（个人版最重要的一条）：任何缺陷结论必须附带具体行号 + 一个能触发的反例场景，否则不许输出。这一条把幻觉率压下来的成本，比自我辩论低一个数量级。

4.3 前置条件 ​

  • 能拿到调用关系：语言服务器、cscope / clangd、或者退化的 grep 兜底。
  • 仓库目录结构本身有语义（如果所有代码平铺在一个目录里，先做子系统划分）。
  • 有一个「强制输出格式」机制（schema / 模板），否则约束会被模型忽略。

4.4 适用边界 ​

  • 适用：跨模块调用密集、有隐性不变量的系统（基础设施、SDK、平台服务）。
  • 不适用：几百行的小项目——调用链分析的成本大于收益；纯 UI / 文案 / 配置生成——语义链太浅；能被编译器 / linter / 类型系统确定判定的问题（能否编译、类型对不对），不要交给 LLM。
  • 谨慎适用：对时延敏感的 CI——三段流程意味着 3 倍以上模型调用。

4.5 反例 / 失败模式 ​

  • 把「有罪推定」做成「默认报缺陷」。有罪推定是搜索策略，不是结论策略。原文自己的数据就是警示：自研 PR 场景准确率只有 73.6%，即每四条意见里有一条不准。【内部数据】
  • 用有罪推定审确定性可判的问题。「这段代码能否编译」不是 LLM 的强项，让它去答只会引入抖动。
  • 不加载子系统知识库就开审。等于退回通用 Review，只是套了个「深度审查」的名字。
  • 自我辩论退化成让模型自我复读。两次调用用同一个 prompt、同一个采样种子，等于一次调用。

4.6 可验证的效果指标 ​

  • 按缺陷类型 / 子系统的准确率矩阵。原文正是靠「与 sashiko、review-prompts、qoder 等 SOTA 方案横向对比」，「能够清楚看到自身在特定缺陷类型、特定子系统上的差距」，再把差距转成迭代优先级。【可独立复现】——矩阵比总分有用得多。
  • 误报确认率：Stage 5 要求「开发者处理或明确是否为误报」，这个「明确为误报」按钮的点击率就是误报率的直接度量。
  • 有效意见密度 = 采纳意见数 / 总意见数。低于某个值就该收窄触发条件，而不是换更强的模型。

4.7 原文逐字引用 ​

「先假设代码有问题，沿全栈调用链追语义，再自我辩论验证结论，加强对内核常见关键代码风险的识别深度。」

「引入 sashiko、review-prompts、qoder 等多个 SOTA 代码审查工作参与横向评估，用对比结果指导 Skills 进化。」

5. 实践卡 · 先有验证样本，才谈得上「进化」 ​

5.1 要解决的问题 ​

没有客观评估时，改进是盲改。原文把这个叫「信任边界模糊」，说得很准：

「用户说"好"不一定是真的好，Agent 自我感觉良好更是靠不住——没有客观的评估与进化闭环，信任就无从建立。」

具体症状：今天改了一版 prompt，感觉输出更好了；下周 review 效果下降，你分不清是 prompt 退化、代码难度变了，还是随机波动。

5.2 具体做法 ​

【可独立复现】 双侧机制：

离线侧——「用验证样本做隔离评测，根据结果反思进化，持续校准 Agent 的判断标准。」关键在「隔离」：评测样本不能和优化样本重叠，否则分数是泄漏出来的。

评估集的三类来源（这是整套方法里最值得抄的一条设计）：

来源作用对应原文理由
真实社区评审过程（LKML）对齐真实 reviewer 的判断标准「问题分布均匀、真实性强」
单 commit—单 issue 精确对应（sashiko benchmark）让改进方向足够聚焦「提供了严格的单 commit—单 issue 映射」
自家仓库数据把评估拉回真实服务语境「把评估拉回到 Kitta 实际服务的仓库语境中」

三类互相制衡：只用自己的数据会过拟合，只用外部数据会脱离语境，只看真实评审过程则缺精确标签。

最小可复现版本：30–50 条带标准答案的样本，每条 = diff 摘要 + 上下文 + 预期结论 + 判这个结论的理由。规则变更时重跑，跑 precision / recall，不看「感觉」。

5.3 前置条件 ​

  • 有人愿意标注样本。可行路径：让模型先按 rubric 起草结论与理由，人只做确认（每条 1 分钟）。不要从零人工写。
  • 评测集必须版本化。rubric 改了，样本也要跟着标版本，否则分数不可比。
  • 样本要覆盖「正常样本」——只有问题样本会让 recall 好看、precision 一片狼藉。

5.4 适用边界 ​

  • 适用：任何要长期迭代的 review agent / prompt。
  • 不适用：样本 < 20 条（指标波动大于收益）；只做一次性接入的项目。
  • 注意：样本分布必须跟着代码演进更新，否则评测集会系统性放过新出现的问题类型。

5.5 反例 / 失败模式 ​

  • 拿优化数据当评测集。用同一批样本既调 prompt 又测效果，分数必然虚高。这是自评体系最常见的自欺。
  • 只统计「提了多少个问题」当质量。数量可以刷。真正该看的是采纳率和准确率。
  • 样本全是自研补丁。回合补丁那类确定性检查的高准确率会掩盖开放性质量意见的弱项。
  • 评测分数与线上采纳率长期背离。这是评测集失真的最强信号，一旦出现就重采样本。

5.6 可验证的效果指标 ​

  • 评测集上的准确率 / 召回率，以及每次改动 prompt 后的净变化值（±1% 属于噪声，要看多次）。
  • 评测分与线上采纳率的相关性。两者应当同向；不同向说明评测集已经不代表真实分布。
  • 隔离纪律：优化样本与评测样本的交集必须为空，这条最好在 CI 里做成检查。

5.7 原文逐字引用 ​

「基于三类来源收集数据——LKML（真实社区 Reviewer 的评审过程，问题分布均匀、真实性强）、sashiko benchmark（单 commit—单 issue 精确对应）、龙蜥 Gitee 社区数据」

「用验证样本做隔离评测，根据结果反思进化，持续校准 Agent 的判断标准。」

6. 实践卡 · 行为作证：用「代码改了什么」校准，而不是听人夸 ​

6.1 要解决的问题 ​

用户反馈稀疏、有偏，而且最有信息量的那批反馈根本不存在——大部分人只是默默无视。如果把「没人反对」当成「大家认可」，Agent 会朝着沉默的幻觉方向进化。

6.2 具体做法 ​

【可独立复现】 把评估主信号从「人说了什么」换成「代码改了什么」。原文的表述：

「不把开发者的默默无视当成认可，不看用户说什么，看"代码改了什么"：通过置信度熔断与追踪真实代码变更，基于客观变更驱动审查和模型迭代。」

三个可落地的机制：

  1. 意见 ID + 变更回查。每条 review 意见带一个稳定锚点（内联评论 id）。PR 后续有 commit/push 时，回查这些行是否被修改 → 得到自动化的「采纳率」口径。这正是原文线上评估框架的作用：「结合 Review 采纳率持续监控、知识更新、迭代校准与阈值调整」。
  2. 置信度熔断。低置信度的意见不升级为门禁，只作为提示；置信度高且类别硬（安全漏洞、破坏性变更）才拦 CI。原文的底线划分是：「对安全漏洞和破坏坚决拦截 CI 流程，这是底线；其余问题分级呈现、仅作提示」。
  3. 阈值是调出来的，不是拍的。随着线上数据积累，持续调「哪些类别在什么置信度下才拦截」。

6.3 前置条件 ​

  • review 意见有稳定 id（GitHub 内联评论锚点天然有）。
  • 能拿到 PR 后续 commit 与 diff。
  • 分类型统计的脚本（几十行即可）。

6.4 适用边界 ​

  • 适用：有人类 maintainer 的团队仓库。
  • 半适用：纯个人项目——「采纳率」= 你改没改，跟另一个人讨论成本一样高，直接跳过这套机制。
  • 注意：改了代码 ≠ 认同意见（可能是自己先发现了、要赶时间、或者顺手重构）。所以这是代理指标，不能单独作为唯一优化目标。

6.5 反例 / 失败模式 ​

  • 用点赞 / LGTM 计数当效果。礼貌文化会直接污染这个信号，一票一个假阳性。
  • 把采纳率当唯一优化目标。Agent 会很快学会只提「一眼就对的建议」来刷分，意见总数暴跌，长期价值归零。要盯的是分类型采纳率而不是总采纳率。
  • 同一行反复修改导致重复计数。必须按（PR、行号、内容 hash）去重。
  • 静默当成认可——原文点名要拒绝的正是这个。

6.6 可验证的效果指标 ​

  • 分类型采纳率。原文给了最有信息量的一组对照：【内部数据】

    场景意见采纳率准确率
    回合补丁场景（一致性检查）70.4%99.8%
    自研 PR 场景（代码质量审查）41.8%73.6%

    读法：差了近 30 个百分点。原因不是模型变笨了，而是**「可确定性判定」的意见采纳率天然远高于「开放式判断」的意见**。这个结论可以直接拿来指导资源分配——先把确定性检查做扎实，开放性问题先当提示而非门禁。

  • 置信度—采纳率曲线：按置信度分桶统计采纳率，找到「拦得住」的置信度阈值。

  • 静默率：被提出后完全无后续动作的意见占比。这是最容易被忽略的失败信号。

6.7 原文逐字引用 ​

「行为作证，拒绝自嗨——用户可能沉默，但代码变更骗不了人。」

「结合 Review 采纳率持续监控、知识更新、迭代校准与阈值调整，让 Agent 在真实使用中越用越准。」

7. 共识提炼 · AI 与人的三条信任边界 ​

这三条不是 Kitta 独有，是社区跑出来的共识。原文原话可以直接贴进团队规范：

原则落地规则谁来兜底
精准分级，克制打扰「对安全漏洞和破坏坚决拦截 CI 流程，这是底线；其余问题分级呈现、仅作提示，不过多占用开发者的注意力」底线类由 CI 兜底，提示类由人自行判断
行为作证，拒绝自嗨「不把开发者的默默无视当成认可，不看用户说什么，看"代码改了什么"」数据兜底
人类兜底，适时退场「AI 是探照灯，照亮风险、给出证据；Maintainer 是方向盘，最终决策权在人，是最后一道防线。」人

结语值得原样抄进团队 wiki：

「最好的 AI 门禁，不是替代 Maintainer，而是让他们只把精力花在真正需要人类智慧的地方。」

注意第三条和 procurement-plan.md 里「开发者为代码质量第一责任人」是同一件事的两种说法——门禁可以自动化，责任人不能自动化。

8. 个人 / 一人公司 / Agent 工作流降级做法 ​

Kitta 的完整形态（专家资产管线 + 五阶段 + Benchmark + 线上评估框架）需要团队和内核仓库。个人版的目标是拿到这套方法 20% 左右的收益（编辑估计，原文无对应数据），成本从「人月」降到「一两天」。

8.1 专家资产 → 两份文件 ​

放弃四步管线，直接手写：

  • review-rubric.md：从这个项目真实吵过架的历史里列 10–20 条判定标准（每条带一个例子）。
  • review-samples/：20 条样本（15 条问题 + 5 条 LGTM），每条一句预期结论 + 一句理由。

合计一晚上。这是原文专家资产的最小可运行形态——两类资产都保留了，只是靠手写而非管线产出。

8.2 五阶段 → 两阶段 ​

砍掉 Stage 3、4（没有回合场景），Stage 1 分类也可以并进去。个人版只保留：

  1. 规范检查：commit message 格式 / PR 描述是否写清「为什么改」（只提示，不拦截）。
  2. 代码质量审查：按 §4 的子系统清单 + 行号/反例场景硬约束输出。

挂在一个 GitHub Action 或 pre-commit hook 上。注意：个人仓库里没有第三方 reviewer，门禁意义有限，主要价值是「强制自己停顿一次」。

8.3 依赖链检查 → 手工 checklist ​

没有上游回合，但有等价场景：cherry-pick 修 bug、升级 vendored 依赖、抄开源代码、同步配置。每次做这类操作时，勾一遍：

□ 这个改动依赖的其它改动，都带过来了吗？
□ 同一个上游修复（同一个 issue / 同一个 commit），是否还有其它 hunk？
□ 抄进来的代码，它的测试/配置/依赖声明是否也抄了？

三条比自动化脚本有用——自动化要等到你一年抄 20 次才划算。

8.4 子系统知识库 + 有罪推定 → 目录级 checklist + 输出约束 ​

  • 知识库：每个顶层目录一份 checklist.md，3–5 条就够。
  • 自我辩论降级为输出格式硬约束：每条结论必须给 文件:行号 + 触发反例；给不出就不许输出这一条。
  • 确定性可判的（编译、类型、lint）交给工具，只让模型负责语义判断。这是最重要的一条省钱原则。

8.5 验证样本 → 20 条金标准，放在 CI 里 ​

每次改 prompt 跑一遍，20 条 × 1 分钟内出结果。样本 < 20 条时分数波动大，但足以回答「这次改动是变好还是变坏」这个唯一重要的问题。

8.6 行为作证 → 一行 git 命令 ​

不需要评估框架。review 评论发出后 7 天，看那几行有没有被改过：

bash
git log --since=7.days -p -- <file> | grep -A5 '<行号上下文>'

采纳率手动记在一个 md 表里即可。个人仓库没有统计价值，但有一个真实价值：它会逼你发现「哪些意见你自己都不当回事」——那些就该从 rubric 里删掉。

8.7 时间表与预算 ​

阶段投入产出
第 1 天2–3 小时review-rubric.md + 20 条样本
第 2 天2–3 小时CI Action（两阶段）+ 输出格式约束
第 2–3 周每次 PR 自动跑10 个 PR 的第一组自有数据：采纳率、误报率、耗时
第 4 周1 小时按数据收窄触发条件，删掉没人当回事的意见

明确不要做的：不要自建向量库、不要复刻五阶段、不要训模型、不要为了「看起来专业」写复杂的多 agent 编排。原文自己都把结论落在「沉淀专家资产 + 定制审查流程 + 评测闭环」这三件朴素的事上。

9. 反模式清单（可直接贴进 CONTRIBUTING.md / PR 模板） ​

任何一条踩中，这次 review 的产出就不该被信任：

  1. 没有项目级评判标准，只跑了通用 lint / 通用 checklist 就叫「AI 评审」——那是工具调用，不是领域定制。
  2. 一份巨大清单里塞满通用最佳实践，没有一条来自本仓库的真实历史。
  3. 所有问题同一优先级，Critical 被淹没在 30 条提示里。
  4. 报告里的问题定位不到具体代码行。
  5. 只检查「这次改了什么」，不检查「该带什么」（回合 / backport / 抄代码场景）。
  6. 把「逐行都对」当成语义一致。
  7. 没有验证样本，改 prompt 全靠「感觉更聪明了」。
  8. 拿优化样本当评测集，分数虚高还拿来汇报。
  9. 用点赞 / LGTM 计数当效果指标。
  10. 把静默当认可，据此放宽阈值。
  11. 让 LLM 去判断能否编译、类型是否匹配这类确定性问题。
  12. 允许模型输出没有行号、没有触发场景的缺陷结论。
  13. rubric 只增不减，半年后一半条目已被代码改动作废。
  14. 把 AI 门禁当成对人的替代——原文的底线是「最终决策权在人」。

10. 一句话操作流（给 Agent 用） ​

On PR opened (or comment `/check-code-review`):
  ↓
[1] CLASSIFY            规则：commit msg 含 `commit xxx upstream` / Fixes: 标签？
      ├─ 回合/backport → 走 [3][4]
      └─ 自研         → 跳过 [3][4]
  ↓
[2] HYGIENE            PR 描述 / commit title / message 规范
      无问题 → 不输出任何评论（沉默是默认态）
  ↓
[3] DEPENDENCY CLOSURE  检索上游 Fixes → 是否在本 PR → 是否已在下游存在
      输出三选一：无遗漏 / 已合入(指 commit) / 遗漏(要求补充)
  ↓
[4] CONSISTENCY        基础对比(文件/代码块) → 上下文对比(符号/适配) → 语义对比(LLM)
      标签：consistent | text-inconsistent | semantic-inconsistent | inconsistent
  ↓
[5] CODE QUALITY        加载子目录 checklist
      缺陷推理：有罪推定 → 沿调用链追语义 → 自我辩论
      硬约束：每条结论必须带 file:line + 可触发的反例场景，否则丢弃
      分级：Critical（内联到行） / Medium·Low（汇总） / 无风险 → LGTM
  ↓
Post inline comments（每条带 stable id）
  ↓
On every subsequent commit/push:
  回查 stable id 对应行是否被修改 → 更新分类型采纳率 → 调阈值
  ↓
Nightly: 验证样本隔离评测（precision/recall）→ 与线上采纳率交叉验证
  ↓
BLOCK merge only if: 安全漏洞 or 破坏性变更（且置信度高于熔断阈值）

与原文的差异（有意为之）：原文在 CI 顶部就有独立的「智能化测试」环节；个人/小团队应把本文这条链路接在自己的测试之上，而不是替代它。
