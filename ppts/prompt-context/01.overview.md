# 从 Vibe Coding 出发后的三座大山

<v-clicks>

上一讲，你学会了和 AI 协作编程。然而真实工作中，你一定遇到过这些时刻——

**场景 1：问得不对**
> 你告诉 AI"帮我优化下代码"，它不知道优化什么——性能？可读性？体积？
> 结果随机改动，无法验证。

**场景 2：给得不准**
> 生成的代码看起来非常合理，跑起来才发现——
> 它调用了一个根本不存在的 API，且信心满满。

**场景 3：质量不佳**

> 同一个问题，今天问和明天问，结果完全不同，团队每个人问出来的代码风格也完全不同。随着交互轮次变多代码出现劣化。

</v-clicks>

<v-click>

<br/>

:::tip
如何跨过，**问得不对** → Prompt 工程（明确指令）；**给得不准** → Context 工程（精准上下文）；**质量不佳** → Harness 工程（闭环约束）。
:::

</v-click>

# Why Prompt / Context / Harness Engineering？

<v-clicks>

> 模型固有缺陷的概念认知

| 模型机制 | 直接导致的问题 | 工程方法论 |
|---------|----------------|------------|
| **1. 按概率续写 Token** | 指令模糊时，输出会发散、跑偏，按照一般的通用原则续写 | **Prompt Engineering**：明确目标、边界、背景、输出格式 |
| **2. 知识固化在权重里** | 不知道最新代码、业务状态、实时事实 | **Context Engineering**：把当前事实注入本轮上下文 |
| **3. 上下文窗口有限** | 塞太多会稀释注意力，关键信息被淹没 | **Context Engineering**：最小有效集、结构化分块、首尾放置 |
| **4. 无状态** | 历史信息污染当前任务，错误在后续轮次累积 | **Harness Engineering**：用 Memory 固化规则，用 Tool +  Loop 观察、验证、纠偏 |

</v-clicks>
