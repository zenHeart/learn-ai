# 演练目标：把一次对话变成工程闭环

<v-clicks>

**场景**：用户反馈“登录 30 分钟后刷新页面会被踢回登录页”。

**目标**：让 AI coding 工具完成定位、修复、补测试、验证，并沉淀一条可复用规则。

**三层分工**：

| 层次 | 本次要做什么 | 交付物 |
|------|-------------|--------|
| **Prompt** | 把 Issue 变成任务契约 | Done 标准 / 边界 / 输出格式 |
| **Context** | 给足定位证据 | 日志 / 复现步骤 / 相关文件 |
| **Harness** | 让 Agent 闭环执行 | 测试 / CI / 规则沉淀 |

</v-clicks>

# Step 1：Issue → Prompt 任务契约

**核心要点**：不要把“修一下”丢给 AI，要先定义完成标准。

::left::

<div class="col-bad">

### ❌ 模糊 Issue

```text
登录有问题，帮我修一下。
```

- 不知道触发条件
- 不知道允许改哪里
- 不知道怎样算修好
- 容易引发大范围重构

</div>

::right::

<div class="col-good">

### ✅ 任务契约

```text
目标：修复登录 30 分钟后刷新页面被踢回登录页
边界：优先只改 auth/session 和 http interceptor
验收：
- 保留原有登录流程
- 新增 session refresh 回归测试
- npm test -- auth/session 通过
输出：修改摘要、风险点、验证命令
```

- 目标清楚
- 边界可控
- 验收可运行

</div>

# Step 2：Context 包不是资料堆

**核心要点**：Agent 最需要的是“可定位证据”，不是完整聊天记录。

::left::

<div class="col-good">

### ✅ 最小有效 Context

```xml
<symptom>
登录后等待 30 分钟，刷新订单页跳回 /login
</symptom>

<evidence>
- Network: GET /api/orders → 401 SESSION_EXPIRED
- Console: refreshToken returned null
- Log: auth/session.ts:88
</evidence>

<repro>
登录 → 打开订单页 → 等待 30min → 刷新
</repro>
```

</div>

::right::

<div class="col-good">

### ✅ 让 Agent 按需读取

```text
先读取这些文件：
- src/auth/session.ts
- src/api/http.ts
- tests/auth/session.spec.ts

如果需要更多信息，先说明原因，
再读取最小相关文件。
```

```text
已排除：
- 账号权限问题
- 订单接口本身异常
- 浏览器缓存清理
```

</div>

<!--
演讲者备注：这里要强调测试、产品、研发都能提供 Context。复现步骤、截图、日志、已排除项都比“帮我看看”更有价值。
-->

# Step 3：给 Agent 一份可执行工单

<v-click>

```markdown
你是本仓库的 AI coding agent。

[Instruction]
修复 session refresh 失败导致的登录态丢失问题。

[Context]
- 现象、证据、复现步骤见上文
- 本仓库 TypeScript strict，禁止 any
- 只做最小修改，避免重构无关模块

[Input]
请先阅读：
1. src/auth/session.ts
2. src/api/http.ts
3. tests/auth/session.spec.ts

[Output]
1. 根因：文件位置 + 证据
2. 修改：改了什么、为什么
3. 测试：新增/修改了哪些用例
4. 验证：实际运行命令和结果
5. 风险：仍需人工确认的点
```

</v-click>

<v-click>

> 这份工单把 Prompt、Context、Harness 接在一起：任务明确、材料可追踪、验证可执行。

</v-click>

# Step 4：Harness 让质量闭环

**核心要点**：不要在 AI 回答“已修复”时停下；要让它拿证据回来。

::left::

<div class="col-good">

### ✅ 推荐执行循环

```text
1. 读项目规则：AGENTS.md / CLAUDE.md / Rules
2. 搜索相关实现：rg "refreshToken|SESSION_EXPIRED"
3. 阅读最小相关文件
4. 修改代码 + 补回归测试
5. 运行定向测试
6. 如失败，基于错误继续修
7. 输出最终证据和风险
```

</div>

::right::

<div class="col-good">

### ✅ 验证命令示例

```bash
npm test -- auth/session
npm run lint -- src/auth src/api
npm run build
```

```text
完成标准：
- 测试真实运行通过
- diff 不越界
- 没有敏感信息进入上下文或输出
- 高风险行为交给人类确认
```

</div>

# Step 5：把一次成功变成团队资产

<v-clicks>

**不要只留下代码 diff，还要留下 Agent 下次能读到的规则。**

```markdown
# AGENTS.md / .cursor/rules/session-refresh.mdc

## Auth session 修改规则

- 修改登录态、token refresh、http interceptor 时，必须补 session 回归测试。
- 不允许吞掉 401 / refreshToken 错误；必须保留可观测日志。
- 验证至少运行：
  - npm test -- auth/session
  - npm run lint -- src/auth src/api
```

**沉淀顺序**：失败样例 → 规则 / 测试 → 下次自动加载 → 团队行为一致。

</v-clicks>

<!--
演讲者备注：这页是 Harness 的落地关键。真正的提效不是这次快，而是下次同类问题不会从零开始。
-->

# 可复制工作流模板

```markdown
## 1. 目标
要修复/实现什么？用户可感知结果是什么？

## 2. 边界
优先改哪些模块？哪些行为不能破坏？哪些操作需要人工确认？

## 3. Context
现象、日志、堆栈、复现步骤、相关文件、已排除项。

## 4. 执行要求
先读规则和相关文件；最小修改；补测试；不要顺手重构。

## 5. 验收
必须运行的测试/构建/检查命令，以及输出格式。

## 6. 沉淀
本次失败样例是否要进入测试、规则、Command 或 Skill？
```

# 本章小结：实战演练

<v-clicks>

1. **研发主线**：Issue → Prompt 契约 → Context 证据包 → Harness 验证 → 规则沉淀

2. **提效关键**：不是让 AI 多写代码，而是减少猜测、缩短反馈、把成功路径复用

3. **迁移方法**：非研发可以把同一套结构用于会议纪要、周报、客户反馈等日常流程

</v-clicks>
