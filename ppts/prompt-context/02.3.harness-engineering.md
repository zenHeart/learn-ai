# 什么是 Harness Engineering？

* **Harness** = 模型外部的运行环境：Tool + Memory + Loop + 权限 / 日志 / 评测。
* **Harness Engineering** = 设计这套环境，让 Agent 能安全执行、观察结果、修正错误，并在边界外升级给人类。

::left::

<div class="col-bad">

### ❌ 无 Harness：只能聊天

- 看不到项目结构和当前状态
- 不能执行命令、跑测试、改文件
- 规则靠对话记忆，容易漂移
- 错误需要人类反复接手

</div>

::right::

<div class="col-good">

### ✅ 有 Harness：进入工程环境

- Tool：搜索、测试、编辑、PR
- Memory：注入项目规则和团队规范
- Loop：执行 → 观察 → 修正
- Guardrail：测试、Lint、人工接管

</div>

---

# 为什么需要 Harness？

<v-clicks>

**核心命题**：AI 协作管不管得住，取决于你设计的工程环境够不够稳。

**管得住的三层含义**：

| 维度 | 含义 | 没有 Harness 的表现 |
|------|------|-------------------|
| **稳定性** | 同一问题，今天问和明天问结果一样 | 每天问每天答案不同 |
| **一致性** | 团队每个人问，结果一样 | A 和 B 问出完全不同的代码风格 |
| **可持续性** | 20 轮对话后，代码不劣化 | 轮次多了代码腐化|

</v-clicks>

<v-click>

> **OpenAI 案例**：[Harness Engineering](https://openai.com/index/harness-engineering/) 中，小团队用 Codex 交付约百万行代码。关键不是“更会写 Prompt”，而是把工具、文档、CI 和反馈闭环做成 Agent 可用的环境。

<br/>

> 范式转变：从 **自己写代码** 到 **设计 AI 工作的环境** ——  <strong v-mark.underline.red="5">你的角色从执行者变为护栏的搭建者。</strong>

</v-click>

<v-click>


</v-click>

# Harness 三件套：最小完备结构

> Harness = **Tool + Memory + Loop**。三者缺一，AI 就无法持续稳定运行。

<div class="grid grid-cols-3 gap-6 mt-8">

<div class="p-4 rounded-lg" style="background: #eff6ff80; border: 1px solid #bfdbfe;">

### Tool

让 AI 能"动手做事"

- Bash
- Custom Scripts (Hooks、...)
- MCP

</div>

<div class="p-4 rounded-lg" style="background: #f0fdf480; border: 1px solid #bbf7d0;">

### Memory

让 AI 能"跨会话记忆"

- Session：单次对话
- Project：仓库规范
- User：个人偏好
- System：系统层面

</div>

<div class="p-4 rounded-lg" style="background: #fffbeb80; border: 1px solid #fde68a;">

### Loop

让 AI 能"自我纠错"

- 执行 → 观测 → 修正
- 不依赖人类确认每一步

</div>

</div>

<v-clicks>

- **没有 Tool**：AI 只能输出文字，无法修改代码
- **没有 Memory**：每次对话都从零开始
- **没有 Loop**：一次答错就放弃，不会自我修复

</v-clicks>

# Memory：跨会话持久化的三层结构

> AI 无持久记忆——Memory 是它的存储系统，按作用域分三层。

<div class="grid grid-cols-3 gap-4 mt-6">

<div class="p-4 rounded-lg" style="background: #f0f5ff; border: 1px solid #c7d2fe;">

### Session Memory

**单次对话内**

- 运行时注入，例如 `--system-prompt`
- Context Window

</div>

<div class="p-4 rounded-lg" style="background: #f0fdf4; border: 1px solid #bbf7d0;">

### Project Memory

**整个仓库共享**

- `CLAUDE.md` / `.claude/rules/`（项目级规范，进 Git）
- 已有 `AGENTS.md` 时，在 `CLAUDE.md` 里 `@AGENTS.md`
- 团队规范、架构决策

</div>

<div class="p-4 rounded-lg" style="background: #fff7ed; border: 1px solid #fed7aa;">

### User Memory

**跨项目跟随用户**

- `*.local.xx` 用户偏好（语言、风格）
- 个人 Skill / Command
- Global 规则跨项目复用
- [custom memory](https://code.claude.com/docs/en/memory#auto-memory)

</div>

# 资产选择 (以 Claude Code 选择)

**核心要点**：不要把所有规则都塞进 `CLAUDE.md`。按触发方式选择资产，Context 才不会膨胀。

::left::

| 资产 | 适合放什么 |
|------|------------|
| `CLAUDE.md、AGENTS.md` | 每次都会用的项目规则、命令、风格 |
| `.claude/rules/` | 只在特定路径/文件类型生效的规则 |
| Command | 快速触发的轻量任务入口 |
| Skill | 高频复杂流程、领域知识、SOP |


::right::

| 资产 | 适合放什么 |
|------|------------|
| Hook | 必须每次执行的动作，如 edit 后 lint, git pre/post hooks |
| MCP | 内外部系统接入 |
| Subagent | 任务拆解，复杂团队编排 |
| Plugin | 跨仓复用的一组 Skills/Hooks/MCP |

# ReAct：让模型边想边取证

::left::

### 论文核心逻辑

<v-clicks>

- **问题**：CoT 只基于已有上下文推理，缺少外部取证；一旦前置事实错误，后续推理会持续放大错误。
- **关键设计**：把动作空间从 `A` 扩展成 `A ∪ L`
- `Action ∈ A`：搜索、读文件、跑测试、编辑代码，会产生外部 `Observation`
- `Thought ∈ L`：语言推理，不改变环境，但写回上下文，服务下一步行动

</v-clicks>

<v-click>

> 引用：[Yao et al. 2022, *ReAct: Synergizing Reasoning and Acting*](https://arxiv.org/abs/2210.03629)

</v-click>

::right::

<v-clicks>

### 标准轨迹

```
Task
  ↓
Thought：拆目标 / 判断缺什么证据
  ↓
Action：调用工具获取证据或改变环境
  ↓
Observation：工具返回的事实
  ↓
Thought：更新计划 / 处理异常
  ↓
... until Finish
```

> 核心不是“多写推理过程”，而是让每一步推理都能被下一次工具调用验证。

</v-clicks>

# Claude Code 四步闭环

::left::

```text
① Explore
只读代码、日志和测试，不改文件

② Plan
输出改动文件、数据流、风险和验证命令

③ Implement
按计划小步修改，优先补失败测试

④ Verify / PR
跑测试、说明结果，交给人类 review / merge
```

> [Explore first, then plan, then code](https://code.claude.com/docs/en/best-practices#explore-first-then-plan-then-code)

::right::

### 什么时候需要 Plan Mode

<v-clicks>

- 多文件、多模块、需求还不清楚
- 不熟悉代码区域，需要先探索
- 改动会影响数据、安全、权限或兼容性
- 你需要 Claude 先提出方案供你确认

</v-clicks>

<v-click>

> 小改动可以直接做；说得清一行 diff 的任务，不必上完整计划。

</v-click>

# [Ralph Loop](https://claude.com/plugins/ralph-loop)：把 ReAct 落到 PR / CI

::left::

```
输入需求 ──▶      ① 新会话（清空历史噪音）
                       │
                       ▼
                 ② 固定加载上下文栈
                    Rules / specs / fix_plan.md
                       │
                       ▼
                 ③ 只选一个最重要任务
                       │
                       ▼
                 ④ 先搜索，再实现
                       │
                       ▼
                 ⑤ 单测 
                       │
                       ▼
人类 Review ◀── ⑥ 绿了开 PR，更新计划 → 下一轮
（仅边界）
```

::right::

### 三个关键约束

<v-clicks>

- **一轮一事**：每次只推进一个最重要任务，防止目标和上下文发散
- **固定上下文栈**：每轮重新加载项目地图、规格和 `fix_plan.md`，把状态留在仓库里
- **闭环验证**：单测 / 构建 / 静态检查 / CI 拒绝坏代码；验证越快，循环越稳

</v-clicks>

# Harness 安全红线

<v-click>

| 风险 | 攻击形态 | 防御 |
|------|---------|------|
| **Tool 越权** | AI 调用 `rm -rf /` / 读生产数据库 / 发邮件给客户 | 工具白名单 + 危险操作人工确认（YOLO 模式仅限沙箱） |
| **工具链注入** | 恶意 MCP Server / 不可信第三方 Tool | 工具来源审计 + 沙箱执行 + 最小权限原则 |
| **Loop 失控** | 无限重试 / 反复编辑同一文件 / Token 灾难 | 步数上限 + 终止条件 + 异常捕获 + 成本告警 |

</v-click>

<v-click>

```
✅ 三道防线：
   ① Tool 沙箱：危险动作（删文件 / 推远端 / 调外部 API）默认拦截
   ② 工具链审查，预测试，安全扫描
   ③ Loop 熔断：步数 / 时间 / 成本三重上限，超限即停
```

</v-click>

# Harness 反模式：好 vs 坏

::left::

<div class="col-bad">

### ❌ 三大反模式

- **CLAUDE.md 当百科全书**：1000 行 → 应保留“每次都需要”的规则
- **规范只靠文档**：README 写一遍 → 应 lint 强制
- **缺少工具**：Lint 代码约束、日志分析工具...

</div>

::right::

<div class="col-good">

### ✅ 三大原则

- **仓库即记录**：Agent 看不到的等于不存在
- **工具强制**：lint 规则 > 文档约定
- **熵管理**：定期清理 Agent 债务

</div>

# 主流 Harness 的实战经验

<v-click>

| 来源 | 可落地实现 |
|------|------------|
| **[Cursor](https://cursor.com/blog/continually-improving-agent-harness)** | **观念：Context 不是越多越好，而是让 Agent 在需要时取证。**<br> **实操：** `CLAUDE.md` 只放高频规则和命令；把 `当前文件、git status、lint / type error` 做成每轮可见的动态上下文；工具失败不要只重试，对错误分类，补脚本、补错误提示、补告警。 |
| **[OpenAI](https://openai.com/index/harness-engineering/)** | **观念：不要把规范写给人记忆，要写进仓库让 Agent 执行。**<br> **实操：** 挑 3 条最高频 review 意见先代码化：目录边界、类型命名、日志 / 错误处理；用 ESLint / 自定义 lint / 结构测试拦住；错误消息直接写 `为什么错 + 怎么改`；PR 模板要求 `复现证据、验证命令、失败时人工升级点`。 |
| **[Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)** | **观念：长任务不能靠对话记忆，必须靠交接资产推进。**<br> **实操：** 超过半天的任务先建 `feature_list.json`、`progress.md`、`init.sh`；每轮开始读 `pwd` / git log / progress / feature list，先跑 smoke 或 E2E；一次只改一个 feature，验证通过才标记 passing，结束时提交小 commit 并写下一轮入口。 |

</v-click>

# 本章小结：Harness 工程

<v-clicks>

1. **运行环境**：Harness 负责“管得住”，把模型接入工具、记忆和反馈回路

2. **反馈闭环**：质量来自执行、观察、测试、评审和指标回归，而不是一次性回答

3. **控制权设计**：工具执行权在宿主，关键动作必须最小权限、可审计、可回滚、可人工接管

</v-clicks>
