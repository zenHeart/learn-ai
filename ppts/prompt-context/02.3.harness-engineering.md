# 什么是 Harness Engineering？

* **Harness** = 模型外部的运行环境：Tool + Memory + Loop + 权限 / 日志 / 评测。
* **Harness Engineering** = 设计这套环境，让 Agent 能安全执行、观察结果、修正错误，并在边界外升级给人类。

::left::

<div class="col-bad">

### ❌ 无 Harness：只能聊天

- 看不到项目结构和当前状态
- 不能执行命令、跑测试、改文件
- 规则靠对话记忆，容易漂移
- 错误需要人类反复接手

</div>

::right::

<div class="col-good">

### ✅ 有 Harness：进入工程环境

- Tool：搜索、测试、编辑、PR
- Memory：注入项目规则和团队规范
- Loop：执行 → 观察 → 修正
- Guardrail：权限、审计、人工接管

</div>

---

# 为什么需要 Harness？

<v-clicks>

**核心命题**：AI 协作管不管得住，取决于你设计的工程环境够不够稳。

**管得住的三层含义**：

| 维度 | 含义 | 没有 Harness 的表现 |
|------|------|-------------------|
| **稳定性** | 同一问题，今天问和明天问结果一样 | 每天问每天答案不同 |
| **一致性** | 团队每个人问，结果一样 | A 和 B 问出完全不同的代码风格 |
| **可持续性** | 20 轮对话后，代码不劣化 | 轮次多了代码腐化|

</v-clicks>

<v-click>

> 三堵墙的解药：**问得不对** → Prompt；**给得不准** → Context；**管不住** → Harness。

</v-click>

<v-click>

> **OpenAI 案例**：[Harness Engineering](https://openai.com/index/harness-engineering/) 中，小团队用 Codex 交付约百万行代码。关键不是“更会写 Prompt”，而是把工具、文档、CI 和反馈闭环做成 Agent 可用的环境。

</v-click>

<v-click>

> 范式转变：从 **自己写代码** 到 **设计 AI 工作的环境** ——你的角色从执行者变为护栏的搭建者。

</v-click>

# Harness 三件套：最小完备结构

> Harness = **Tool + Memory + Loop**。三者缺一，AI 就无法持续稳定运行。

<div class="grid grid-cols-3 gap-6 mt-8">

<div class="p-4 rounded-lg" style="background: #eff6ff80; border: 1px solid #bfdbfe;">

### Tool

让 AI 能"动手做事"

- 读 / 写文件
- 执行命令
- 调用 API

</div>

<div class="p-4 rounded-lg" style="background: #f0fdf480; border: 1px solid #bbf7d0;">

### Memory

让 AI 能"跨会话记忆"

- Session：单次对话
- Project：仓库规范
- User：个人偏好

</div>

<div class="p-4 rounded-lg" style="background: #fffbeb80; border: 1px solid #fde68a;">

### Loop

让 AI 能"自我纠错"

- 执行 → 观测 → 修正
- 不依赖人类确认每一步

</div>

</div>

<v-clicks>

- **没有 Tool**：AI 只能输出文字，无法修改代码
- **没有 Memory**：每次对话都从零开始
- **没有 Loop**：一次答错就放弃，不会自我修复

</v-clicks>

# Memory：跨会话持久化的三层结构

> AI 无持久记忆——Memory 是它的外部存储，按生命周期分三层。

<div class="grid grid-cols-3 gap-4 mt-6">

<div class="p-4 rounded-lg" style="background: #f0f5ff; border: 1px solid #c7d2fe;">

### Session Memory

**单次对话内**

- 上下文窗口
- 多轮对话历史
- Token 耗尽即丢失

</div>

<div class="p-4 rounded-lg" style="background: #f0fdf4; border: 1px solid #bbf7d0;">

### Project Memory

**整个仓库共享**

- `CLAUDE.md` / `.claude/rules/`（项目级规范，进 Git）
- 已有 `AGENTS.md` 时，在 `CLAUDE.md` 里 `@AGENTS.md`
- 团队规范、架构决策

</div>

<div class="p-4 rounded-lg" style="background: #fff7ed; border: 1px solid #fed7aa;">

### User Memory

**跨项目跟随用户**

- 用户偏好（语言、风格）
- 个人 Skill / Command
- 历史学习记录

</div>

</div>

# Claude Code 资产选择

**核心要点**：不要把所有规则都塞进 `CLAUDE.md`。按触发方式选择资产，Context 才不会膨胀。

::left::

| 资产 | 适合放什么 |
|------|------------|
| `CLAUDE.md` | 每次都会用的项目规则、命令、风格 |
| `.claude/rules/` | 只在特定路径/文件类型生效的规则 |
| Skill | 高频复杂流程、领域知识、SOP |
| Hook | 必须每次执行的动作，如 edit 后 lint |

::right::

| 资产 | 适合放什么 |
|------|------------|
| Subagent | 大量读文件的调查、专项审查 |
| MCP | GitHub、Figma、数据库、监控等外部系统 |
| Plugin | 跨仓复用的一组 Skills/Hooks/MCP |
| Command | 快速触发的轻量任务入口 |

<v-click>

> 判断标准：一直要看 → `CLAUDE.md`；偶尔要用 → Skill；必须执行 → Hook；会污染主上下文 → Subagent。

</v-click>

# ReAct：推理 + 行动交替框架

<v-clicks>

**问题**：纯推理（CoT）缺乏外部验证；纯行动（Tool Use）缺乏任务理解

**解法**：推理（Thought）与行动（Action）交替进行

引用：[Yao et al. 2022, *ReAct: Synergizing Reasoning and Acting*](https://arxiv.org/abs/2210.03629)

</v-clicks>

<v-click>

```
Thought: 需要知道测试失败原因
Action: run_tests()
Observation: auth.spec.ts 第 42 行断言失败
Thought: 需要查看相关实现
Action: read_file("src/auth.ts")
Observation: token 过期分支返回了 null
Action: edit_file(...) + run_tests()
```

</v-click>

<v-click>

| 框架 | 核心机制 | 适用场景 |
|------|----------|----------|
| CoT | 纯推理链 | 通用推理 |
| Tool Use | 纯工具调用 | 简单查询 |
| **ReAct** | 推理 + 行动交替 | 需要外部验证的复杂任务 |

</v-click>

# Claude Code 四步闭环

::left::

```text
① Explore
只读代码、日志和测试，不改文件

② Plan
输出改动文件、数据流、风险和验证命令

③ Implement
按计划小步修改，优先补失败测试

④ Verify / PR
跑测试、说明结果，交给人类 review / merge
```

::right::

### 什么时候需要 Plan Mode

<v-clicks>

- 多文件、多模块、需求还不清楚
- 不熟悉代码区域，需要先探索
- 改动会影响数据、安全、权限或兼容性
- 你需要 Claude 先提出方案供你确认

</v-clicks>

<v-click>

> 小改动可以直接做；说得清一行 diff 的任务，不必上完整计划。

</v-click>

# Ralph Loop：把 ReAct 落到 PR / CI

::left::

```
人类输入需求 ──▶ ① 新会话（新鲜上下文）
                       │
                       ▼
                 ② 读 CLAUDE.md（地图）
                       │
                       ▼
                 ③ 执行任务
                    （写 / 调试 / 文档）
                       │
                       ▼
                 ④ 自审 + Agent 评审
                       │
                       ▼
                 ⑤ 开 PR → CI 通过 + 人类 Review
                       │
                       ▼
人类介入  ◀────  ⑥ 清理 → 下一轮
（仅边界）
```

::right::

### 三个关键约束

<v-clicks>

- **新鲜上下文**：每任务新开会话，避免历史污染
- **反压控制**：CI 失败 → Agent 自动修复，不阻塞其他任务
- **临时计划**：执行计划提交仓库，归档可追溯

</v-clicks>

<v-click>

### nn-client-all 查 Bug

1. 用户报告 "登录失败"
2. Agent 读 `CLAUDE.md` → 定位 `src/auth/`
3. 跑测试 → 拿到 stack trace
4. 修代码 + 加用例 → 开 PR
5. CI 通过 → 人类 Review / Merge

</v-click>

<v-click>

> Ralph Loop 是工程化的 Agent Review Loop：把执行、验证、评审、修复接到同一个闭环里。

</v-click>

# Harness 安全红线

<v-click>

| 风险 | 攻击形态 | 防御 |
|------|---------|------|
| **Tool 越权** | AI 调用 `rm -rf /` / 读生产数据库 / 发邮件给客户 | 工具白名单 + 危险操作人工确认（YOLO 模式仅限沙箱） |
| **Loop 失控** | 无限重试 / 反复编辑同一文件 / Token 灾难 | 步数上限 + 终止条件 + 异常捕获 + 成本告警 |
| **工具链注入** | 恶意 MCP Server / 不可信第三方 Tool | 工具来源审计 + 沙箱执行 + 最小权限原则 |

</v-click>

<v-click>

```
✅ 三道防线：
   ① Tool 沙箱：危险动作（删文件 / 推远端 / 调外部 API）默认拦截
   ② Loop 熔断：步数 / 时间 / 成本三重上限，超限即停
   ③ 工具链审查，预测试，安全扫描
```

</v-click>

# Harness 反模式：好 vs 坏

::left::

<div class="col-bad">

### ❌ 三大反模式

- **CLAUDE.md 当百科全书**：1000 行 → 应保留“每次都需要”的规则
- **规范只靠文档**：README 写一遍 → 应 lint 强制
- **缺少工具**：Lint 代码约束、日志分析工具...

</div>

::right::

<div class="col-good">

### ✅ 三大原则

- **仓库即记录**：Agent 看不到的等于不存在
- **工具强制**：lint 规则 > 文档约定
- **熵管理**：定期清理 Agent 债务

</div>

# 主流 Harness 的实战经验

<v-click>

| 来源 | 可吸收做法 | 落到团队实践 |
|------|------------|--------------|
| **[Cursor](https://cursor.com/blog/continually-improving-agent-harness)** | Harness 当产品迭代：offline eval + online A/B + Keep Rate | 不只看 benchmark，也看代码是否被用户保留 |
| **[OpenAI](https://openai.com/index/harness-engineering/)** | Agent Loop：instructions + tools + input + compaction | 每轮都能解释“模型看见什么、能做什么” |
| **[Anthropic](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents)** | Subagent 独立窗口 + 工具权限 + Hooks | 探索、评审、调试拆给专用 Agent |

</v-click>

<v-click>

```
落地检查：
① 工具错误要分类、告警、复盘，不能只让模型重试
② 不同模型可以用不同编辑工具和提示，不强求一套 Harness
③ 长任务用 subagent / 新会话隔离噪声，用总结回传主线
```

</v-click>

# 本章小结：Harness 工程

<v-clicks>

1. **运行环境**：Harness 负责“管得住”，把模型接入工具、记忆和反馈回路

2. **反馈闭环**：质量来自执行、观察、测试、评审和指标回归，而不是一次性回答

3. **控制权设计**：工具执行权在宿主，关键动作必须最小权限、可审计、可回滚、可人工接管

</v-clicks>
