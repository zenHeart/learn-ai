# 实战 A · 从 0 建一个 `reviewing-prs` Skill

<div class="grid grid-cols-2 gap-5 mt-3 text-sm">

<div class="theme-skill">

### ① 起骨架（30 秒）

```bash
mkdir -p ~/.claude/skills/reviewing-prs
$EDITOR ~/.claude/skills/reviewing-prs/SKILL.md
```

```yaml
---
name: reviewing-prs        # 动名词 = 目录名
description: 审查 PR diff，查 SQL 注入、N+1、
  敏感日志、异常吞掉。当用户说"审一下 PR /
  review / 检查这次改动"时使用。
---
## 正文：检查清单 + 容错（略）
```

只要 `name + description` 就能跑。

</div>

<div class="theme-mcp">

### ② dry-run 验证触发（最关键）

写完别急着用 —— 用两句话验证 description 灵不灵：

<div class="col-good text-xs mt-2">✅ 该命中："帮我审一下这个 PR" → 激活 `reviewing-prs`</div>

<div class="col-bad text-xs mt-2">❌ 不该命中："帮我写一个登录函数" → <strong>不</strong>激活（写代码不是审查）</div>

<div class="mt-3 text-xs text-slate-500">99% 的"不触发"都是 description 没写清 what + when。</div>

</div>

</div>

<div class="mt-3 p-2 theme-combo text-sm">
③ 正文长了 → 拆到 <code>references/</code>，SKILL.md 留目录页 · ④ 满意了挪进 <code>.claude/skills/</code> 进 Git，全员开箱即用。
</div>

# 实战 B · 把内部系统包成一个 MCP

<div class="grid grid-cols-2 gap-5 mt-3 text-sm">

<div class="theme-mcp">

### 用 FastMCP，会写 FastAPI 就会写

```python
# server.py
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("zentao")

@mcp.tool()
def get_issue(id: str) -> dict:
    """按工单 ID 查禅道详情，返回
    status / assignee / description。"""
    return fetch_zentao(id)   # 密钥只在这里

if __name__ == "__main__":
    mcp.run()      # 默认 stdio
```

docstring **自动变成** tool 的 description —— 写清 what + 返回什么。

</div>

<div class="theme-skill">

### 接进任何 AI 客户端，引一行

```json
{ "mcpServers": {
  "zentao": {
    "command": "python",
    "args": ["server.py"]
  }
}}
```

* 模型只发"调用意图"，**生产密钥封在 Server 端**
* 写一次，Claude / Cursor / Codex 全能用
* 不会写？让 `mcp-builder` 帮你把现成 API 包成 MCP

</div>

</div>

<div class="mt-3 p-2 theme-combo text-sm">
🎯 nn-ai 真实案例：禅道 / GitLab / Kibana 就是这么包成 <code>@nn/mcp-*</code>，发内部 npm，所有人引一行就能用。
</div>

# 私货 · 踩坑换来的 5 条经验

<div class="grid grid-cols-2 gap-x-6 gap-y-4 mt-5 text-sm">

<div v-click="1">
<strong class="accent-skill">① 先当三天同事，再造资产</strong><br>
<span class="text-slate-600">别开会拍脑袋列资产清单。先把 AI 当同事用几天，记下它<strong>反复</strong>掉链子的地方——90% 的痛点，造一个资产就够了。</span>
</div>

<div v-click="2">
<strong class="accent-skill">② 不触发，99% 是 description 的锅</strong><br>
<span class="text-slate-600">Skill 不灵几乎都不是逻辑问题，是 description 没写清 what+when。写完<strong>必做 dry-run</strong>：一句该命中、一句不该命中。</span>
</div>

<div v-click="3">
<strong class="accent-skill">③ 给 AI 装刹车，比装油门重要</strong><br>
<span class="text-slate-600">最危险的不是不会做，是<strong>错了还硬着头皮做</strong>。"什么情况停下问人"这段容错，是最该写、最常被漏写的一段。</span>
</div>

<div v-click="4">
<strong class="accent-skill">④ 资产有半衰期，要写"复审人"</strong><br>
<span class="text-slate-600">流程一变资产就过期。把<strong>谁维护、何时复审</strong>记下来，否则三个月后全是没人敢删的僵尸资产。</span>
</div>

<div v-click="5">
<strong class="accent-skill">⑤ 从 Rules 起步，别一上来就 Subagent</strong><br>
<span class="text-slate-600">80% 的需求 Rules + Skill 就够。只有主对话被严重污染、或确实要并行，<strong>再</strong>升级到 Subagent——别为架构而架构。</span>
</div>

<div v-click="6" class="theme-combo">
<strong>🧭 一句总纲</strong><br>
<span class="text-slate-600">资产不是越多越好——<strong>少而准</strong>胜过多而杂。每个资产都该能说清：它解决哪个反复出现的痛点。</span>
</div>

</div>
