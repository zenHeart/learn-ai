# MCP 原理 · 一句话三件事

<div class="grid grid-cols-3 gap-4 mt-4 text-sm">

<div v-click="1" class="theme-mcp">

### ① 它是标准，不是工具

`N × M` 集成噩梦 → `N + M`<br>
**一次开发一个 Server，所有 AI 客户端即插即用**。
就像 USB-C。

</div>

<div v-click="2" class="theme-mcp">

### ② 调用是 LLM 主动发起的

不是被关键词触发。
对话中**模型自己决定**调哪个工具、传什么参数（官方原文：*the language model decides to use a tool*）。

</div>

<div v-click="3" class="theme-mcp">

### ③ 密钥隔离

Token / 账号封在 **Server 端**，模型只发"调用意图"，永远拿不到你的生产密钥。
"AI 申请，宿主执行"。

</div>

# 等等 · 我都有 Function Calling 了，为什么还要 MCP？

<div class="text-sm text-slate-600 -mt-1">这是工程师最大的认知障碍。一句话：<strong>MCP 不替代 Function Calling，它是架在 FC 之上的"打包与分发标准"</strong>。</div>

<div class="table-scroll mt-3 text-xs">

| 维度 | 裸脚本 / 直接调 API | 原生 Function Calling | MCP |
|---|---|---|---|
| **是什么** | 代码里写死调用 | 在单个 App 里定义 tool schema 喂给模型 | 把 tools 封进独立 Server，用标准协议暴露 |
| **复用范围** | 一次性，绑死脚本 | 绑死这个 App + 这次集成 | **写一次，所有 MCP 客户端通用** |
| **谁发起调用** | 你的代码 | 模型（FC 机制） | 模型（**底层仍是 FC 机制**） |
| **密钥** | 明文在脚本 / 喂进 prompt | 在 App 后端 | **封在 Server 端，模型看不到** |
| **治理** | 无 | App 各自为政 | 统一鉴权 / 限流 / audit / 版本 |
| **何时用** | 真·一次性、只你自己 | 单一应用内的少量工具 | **跨工具 / 跨团队复用 + 要治理** |

</div>

<div class="mt-3 p-2 theme-combo text-sm">
🔑 关键澄清：<strong>调用工具的机制没变（都是模型生成 tool call）</strong>。MCP 解决的是另一个问题 —— "同一个 tool 怎么被 N 个 AI 应用复用、怎么统一治理"。所以不是二选一，<strong>MCP = Function Calling + 标准化封装 + 跨端复用</strong>。
</div>

<!-- 演讲者备注：

# 加载生命周期 · 谁、在何时、基于什么做决策

<div class="text-sm text-slate-600 -mt-1">把 Skill 和 MCP 摆在同一条时间线上——你会发现<strong>决策主体的切换规律完全一致</strong>。</div>

<div class="table-scroll mt-3 text-xs">

| 阶段 | Skill 发生什么 | MCP 发生什么 | 决策主体 | Context 占用 |
|---|---|---|---|---|
| **① 会话启动** | 所有 `name+description` 注入系统提示 | Host 连所有 Server，`initialize` 握手 + `tools/list` 拉清单进**工具池** | **框架**（无脑全装上桌） | Skill 常驻 ~100 tokens；工具进工具池 |
| **② 运行中·要不要用** | 模型读着 description 判断该不该激活 | 模型判断需要外部能力 → 生成 tool call | **模型**（读清单自决） | — |
| **③ 取用** | 激活 → bash 读 SKILL.md 正文；正文引用 → 按需读 references | Host 拦截 tool call → Client → Server 执行 | Skill：模型 / MCP：**宿主执行** | 正文 <5000 · 按需 |
| **④ 回灌循环** | 正文指引指导后续动作 | 结果回灌对话，模型继续推理 | **模型** | 结果进 context |

</div>

<div class="mt-3 grid grid-cols-2 gap-4 text-sm">

<div class="theme-combo">

### 🧠 一句话记住

框架只在 ① 把"目录/能力清单"摆上桌（Tier 1）；<br>
之后<strong>用不用、怎么用，全是模型读着清单自己决策</strong>。<br>
没有匹配引擎，没有规则路由。

</div>

<div class="col-bad">

### ⚠️ 由此推出的实战铁律

清单是<strong>常驻 context</strong> 的——装一堆用不到的 Skill/MCP，<br>
等于每轮都把无关说明书摊在模型眼前，<strong>稀释判断、挤占预算</strong>。<br>
👉 <strong>按需启用，别全家桶。</strong>

</div>

</div>

# 资产辨析 · Skill 和它的近邻，一张表分清

<div class="table-scroll mt-3 text-sm">

| 概念 | 谁触发 | 加载粒度 | 上下文 | 典型场景 |
|---|---|---|---|---|
| **Skill** | description 命中 / 显式 `/` | 三层渐进（100→5k→按需） | **共享主对话** | 团队 SOP、可复用工序 |
| **MCP Tool** | 模型自主决定调用 | JSON-RPC 单次调用 | **不进 Context** | 真正"做事"（写文件、查 DB） |
| **Rules / Memory** | 启动自动加载 | 全文常驻 Context | 共享主对话 | 硬约束、项目背景、用户偏好 |
| **Slash Command** | 用户输入 `/cmd` | 一次性指令 | 共享主对话 | 触发即时操作（如 `/clear`） |
| **Sub-agent** | 主 agent 主动派活 | 独立工具集 + 独立提示词 | **独立 Context** | 复杂分工、并行、隔离上下文 |

</div>

<div class="mt-4 p-3 theme-combo text-sm">
🧠 <strong>判别核心</strong>：Skill = <strong>知识 + 流程</strong>（教 AI 怎么做）· MCP Tool = <strong>真正去执行</strong>（伸手做事）· Rules = <strong>每次都生效的约束</strong> · Sub-agent = <strong>另开一个独立上下文的分身</strong>。
</div>
