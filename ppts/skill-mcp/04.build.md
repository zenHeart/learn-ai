# 第一原则 · 先评估，再造（eval-driven）

<div class="grid grid-cols-2 gap-5 mt-4">

<div class="col-bad">

### ❌ 常见错法

* 一上来铺一堆 Skill / MCP
* 照着别人的模板抄一套
* 先写一大篇文档，再想它解决什么

→ 没人用、还稀释了模型的判断

</div>

<div class="col-good">

### ✅ 官方做法：评估驱动

1. **先不带 Skill 跑几个真实任务**，记下 AI 反复掉链子处
2. 用这些失败建 **2-3 个评估场景**（你的"真相来源"）
3. 写**刚好够用**的最小指令去通过评估
4. 真实使用中观察，再迭代

</div>

</div>

<div class="mt-4 p-3 theme-combo text-sm">
🎯 官方原话精神：<strong>"Create evaluations BEFORE writing extensive documentation"</strong> —— 先证明它解决真问题，再补内容。判断标准：<strong>这个痛点反复出现、值得沉淀吗？</strong>
</div>

<div class="mt-3 col-bad text-xs">
🚫 <strong>什么时候别造</strong>：一次性脚本、纯个人偏好（放 Memory 即可）、没有跨人/跨工具复用诉求 —— 直接写函数更快，造资产反而是负 ROI。
</div>

# 写 Skill 的两条核心原则（官方）

<div class="grid grid-cols-2 gap-5 mt-4 text-sm">

<div class="theme-skill">

### 1. 简洁是王道（Concise is key）

Context 是**公共品** —— 你的 Skill 和系统提示、对话历史、别的 Skill 抢同一块预算。

* **默认假设：Claude 已经很聪明**
* 每句话自问："这是 Claude 不知道的吗？"
* SKILL.md 正文 **< 500 行**，超了就拆文件

<div class="col-bad text-xs mt-2">❌ "PDF 是一种常见文件格式……有很多库……" — Claude 全知道</div>
<div class="col-good text-xs mt-1">✅ 直接给"用 pdfplumber 提取文本 + 3 行代码"</div>

</div>

<div class="theme-mcp">

### 2. 给恰当的"自由度"

按任务的**脆弱程度**调指令的具体度：

* **高自由**（纯文字步骤）：多种解法都行 → CR、分析
* **中自由**（带参脚本）：有偏好模式 → 生成报告
* **低自由**（精确脚本，禁改）：脆弱易错 → 数据库迁移

<div class="mt-2 text-xs text-slate-500">
🌉 比喻：<strong>悬崖窄桥</strong>给精确护栏（低自由）；<strong>开阔旷野</strong>给大方向、信任 Claude 找路（高自由）。
</div>

</div>

</div>

# `name` 与 `description` · 决定它灵不灵的两个字段

<div class="grid grid-cols-2 gap-6 mt-3 text-sm">

<div class="col-bad">

### ❌ 模糊 / 错误写法

```yaml
name: helper            # 太泛
description: 帮助代码审查   # 没说何时用
```
```yaml
description: I can help you review code  # 第一人称
```

* 名字泛化、description 缺触发场景
* **第一人称**（进系统提示后视角错乱）

</div>

<div class="col-good">

### ✅ 官方写法

```yaml
name: reviewing-prs       # 动名词，见名知意
description: 审查 PR diff，查 SQL 注入、N+1、
  敏感日志、异常吞掉。当用户说"审一下 PR /
  review / 检查这次改动"时使用。
```

* **name 用动名词**：`reviewing-prs` / `analyzing-spreadsheets`（禁 `anthropic`/`claude`、≤64 小写连字符）
* **description 第三人称 + what + when + 关键词**（≤1024）

</div>

</div>

<div class="mt-3 p-3 theme-combo text-sm">
🔑 description 是从 100+ 个 Skill 里被选中的<strong>唯一依据</strong>，且<strong>注入系统提示</strong>——它是写给"模型读"的一句话，不是关键词堆砌。写完<strong>必做 dry-run</strong>（第 05 章）。
</div>

<!-- 演讲者备注：
官方最强调：name/description 是 Skill 被发现/选中的关键。
三条硬规则：动名词命名、第三人称、what+when+关键词。第一人称是高频错误（官方专门警告）。
-->

# 渐进披露实操 + 用 Claude 造 Skill

<div class="grid grid-cols-2 gap-5 mt-4 text-sm">

<div class="theme-skill">

### 📂 组织好文件（渐进披露）

* SKILL.md = **目录页**，指向细节文件
* **引用只放一层深**（别 A→B→C 套娃，Claude 可能只读一半）
* 长参考文件（>100 行）开头加**目录**
* 按域拆：`reference/finance.md`、`reference/sales.md` —— 问销售就只读销售

</div>

<div class="theme-mcp">

### 🌀 让 Claude 帮你写（A/B 迭代）

官方推荐：**Claude A 写、Claude B 用**

1. 先和 Claude 正常做完一个任务
2. "把刚才这套做法做成一个 Skill"——它原生懂格式
3. 换个新会话（Claude B）用这个 Skill 做类似任务
4. 看它哪卡住 → 回到 Claude A 改 → 再测

现成元资产：`skill-creator` · `mcp-builder`

</div>

</div>

<div class="mt-4 p-3 theme-combo text-sm">
💡 不用"写 Skill 的特殊 prompt"——<strong>直接让 Claude 造</strong>。你提供领域知识，Claude 负责结构；用真实任务暴露 gap，迭代收敛。
</div>

<!-- 演讲者备注：
渐进披露的实操三条：目录页、引用一层深、长文件加目录——都是官方 best-practices 明确点名的。
A/B 迭代是官方最推崇的开发法：Claude A 作者、Claude B 测试、观察真实行为再改。比"凭空设想"靠谱。

# 反模式 · 一眼识别 6 个坑

<div class="grid grid-cols-3 gap-3 mt-4 text-xs">

<div class="col-bad">

### ❌ 大而全 Skill
1200 行塞一个文件 → 超 5k token、description 稀释、难复用。**拆成多个小的**。

</div>

<div class="col-bad">

### ❌ 自夸式 description
"我是一个超级强大的助手……" → 模型无法判断何时用，频繁误触发。

</div>

<div class="col-bad">

### ❌ 在 Skill 里硬编码实现
Skill 是**剧本不是代码库** —— 一出现大段实现就该拆，交给 MCP / Bash。

</div>

<div class="col-bad">

### ❌ 没有容错段
失败路径没写清 → AI 自由发挥翻车。写明"什么情况停下问人"。

</div>

<div class="col-bad">

### ❌ 给太多选项
"可以用 A 或 B 或 C 或 D……" → 给**一个默认** + 必要时的逃生口。

</div>

<div class="col-bad">

### ❌ Windows 反斜杠路径
`scripts\helper.py` 在 Unix 报错 → 一律正斜杠 `scripts/helper.py`。

</div>

</div>

<div class="mt-4 p-2 theme-combo text-sm text-center">
🧠 这 6 个坑，前 4 个是"结构"问题、后 2 个是"细节"问题 —— 都来自官方 anti-patterns + 真实踩坑。
</div>

# 不是一家之言 · 四大厂商收敛到同一套

<div class="table-scroll mt-3 text-xs">

| 厂商 / 工具 | 资产载体 | 触发 / 加载 | 强调的最佳实践 |
|---|---|---|---|
| **Anthropic** · Claude Code | `SKILL.md` + `CLAUDE.md` | 模型读 description 自激活 · 渐进三层 | description 写 what+when；正文 < 500 行；细节拆 `references/` |
| **OpenAI** · Codex | `AGENTS.md` | 启动注入上下文 | 一个仓一份；写清构建/测试/约定；可分目录覆盖 |
| **Google** · Gemini CLI | `GEMINI.md` | 分层加载（全局/项目/目录） | 项目级 + 个人级分开；保持精简、避免冗长 |
| **Cursor** | `.cursor/rules/*.mdc` | 按 glob 自动挂 / 手动 @ | 一条规则一个关注点；用 `globs` 精准作用域 |

</div>

<div class="mt-4 grid grid-cols-2 gap-4 text-sm">

<div class="col-good">

### ✅ 四家共识

* **Markdown 写"给 agent 读的说明书"**，进 Git 版本化
* **渐进式披露**：按需加载，绝不一次塞满 Context
* **一份标准多工具复用**：`AGENTS.md` 已成跨工具事实标准（[agents.md](https://agents.md)）
* **高危操作留人工闸门** + 工具权限白名单

</div>

<div class="col-bad">

### ❌ 四家都反对

* 把所有规则堆进一个万行大文件
* 自夸式描述、关键词堆砌（没有匹配引擎）
* 让 AI 无确认地执行删库 / 发版 / 打款

</div>

</div>

<div class="mt-2 text-xs text-slate-500 text-center">
载体名字不同（SKILL.md / AGENTS.md / GEMINI.md / .mdc），<strong>底层心智完全一致</strong>。
</div>
