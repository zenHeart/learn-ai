# 文档架构：Diataxis 四象限

> 这是写文档时如何**规划整页结构和跨页关系**的方法论，不是写单个段落的方法。回答的核心问题：这份文档该属于哪一类？和旁边那份是什么关系？什么时候该拆、什么时候该合？
>
> 通用维护流程见 [`maintenance-workflow.md`](./maintenance-workflow.md)。下面用 Claude 家族当**已验证示例**，不是要求每个消费仓库都有这些文件。

## 为什么用 Diataxis

不分类地写"一份大而全的文档"是常见反模式：读者越多、目的越不同，文档越要塞进越多内容，直到最后没人能看完——教程章节里突然冒出一段配置参数对照表、参考手册里塞进了一段操作步骤、解释型文档里混了 Quickstart。读者不知道该相信哪一段、作者不知道该往哪里加新内容。

[Diataxis 框架](https://diataxis.fr/)把文档按读者的**阅读目的**切成四个象限，每份文档有且只有一个目的：

```
                  学习导向                                                   工作导向
            ┌─────────────────────────┬─────────────────────────┐
            │                         │                         │
            │   Tutorial 教程         │   How-to 指南          │
            │   "带读者完成一个       │   "给读者一系列步      │
            │    可学习的体验"         │    骤解决具体问题"      │
            │                         │                         │
            │  - 入门/导览/学习路径    │  - 场景化操作指南      │
            │  - 循序渐进、有连贯性    │  - Recipe/cookbook 形态 │
            │  - 强调"为什么这样"      │  - 跳着读没关系         │
            │                         │                         │
 ───────────┼─────────────────────────┼─────────────────────────┼─────────
            │                         │                         │
            │   Explanation 解释      │   Reference 参考       │
            │   "讨论一个主题、       │   "列出所有选项、      │
            │    给读者背景知识"       │    供查找而非学习"      │
            │                         │                         │
            │  - 概念/术语表/原理      │  - API/配置/参数表      │
            │  - 为什么这样设计       │  - 决策表/命令清单      │
            │  - 跨页面统一口径       │  - 不解释"为什么"      │
            │                         │                         │
            └─────────────────────────┴─────────────────────────┘
```

## 四个象限的边界与典型错误

### Tutorial 教程 — "跟着一遍学"

- **特征**：从起点到终点有明确叙事弧线、读者跟着做就能完成一个完整的小项目、强调"为什么这样做"，不强调"还有哪些选项"
- **典型错误**：把 reference 内容（参数表、API 清单）塞进教程里——读者本来跟着做，结果突然跳到一张 30 行的配置对照表
- **典型实例**：`claude-code.md` 的"CLI 快速入门"、"交互基础"、"最佳实践"章节

### How-to 指南 — "我要解决 X 问题"

- **特征**：以"问题"或"场景"为组织单位，每节是独立的 recipe、可以跳着读、不需要连贯故事
- **典型错误**：和 Tutorial 混淆——把"如何从零开始"也写成 How-to 章节，结果读者卡在"上下文跟不上"上
- **典型实例**：`claude-code-cookbook.md`（9 大日常开发场景的提示模式）、`claude-code.md` 的"修复 Bug / 实现功能 / 写测试"场景

### Explanation 解释 — "这玩意儿是啥 / 为什么这样"

- **特征**：以"概念"或"主题"为组织单位，回答"是什么 / 为什么 / 它怎么运作 / 它和其他概念的关系"，不教具体操作、不给参数清单
- **典型错误**：抄一份 reference 表格当概念解释；或者反过来——把"如何使用"写进 Explanation 里
- **典型实例**：`claude-code-glossary.md`（14 个核心概念：是什么、为什么、怎么实现的）

### Reference 参考 — "我要查 X 的参数 / 命令 / 配置"

- **特征**：以"查询路径"为组织单位，章节对应当类型的查询（如"权限模式"对应五种模式对照表），信息密集、可预测、不解释动机
- **典型错误**：往 Reference 里加"为什么推荐这样"——读者查参数时不想读散文；或者不及时更新导致信息过时
- **典型实例**：`claude-code-cheatsheet.md`（决策表、配置参数、数据源链接）

## 产品家族完备（排轴之前）

回答「官方有哪些产品」，不是「教程有哪些章节」。硬规则、密度表、易撞名和踩坑见 [`family-completeness.md`](./family-completeness.md)。

**轴 A/B 只决定顺序，不决定删不删。** 官方一级入口可以排后、或只在 `index.md` 占一行，不能从家族图消失。排轴前先把官方一级 nav 对完账。

## 决策框架：什么时候拆、什么时候合

### 应该拆成两份文档

| 场景 | 拆法 |
|------|------|
| 一个文档同时承担"教"和"查"两种目的 | 拆成 Tutorial + Reference |
| 同一份配置表出现在多份文档里（口径漂移风险） | 收敛到唯一 Reference 文档，其他文档引用 |
| "概念定义"和"配置参数"混在同一节（如"权限模式"既讲什么是权限模式又列配置语法） | 拆成 Explanation（概念） + Reference（配置） |
| 一份文档的主要读者已经分成明显两类（"想学" vs "要查"） | 拆 |

### 应该合并成一份文档

| 场景 | 合并法 |
|------|------|
| 两份文档的章节高度重叠、读者通常连着读 | 合并 |
| 一份文档只有一两节、还没有到独立成章的密度 | 合并到相邻文档 |
| 拆分后读者需要持续在两份文档间跳转才能完成一次查询 | 合并 |

### 跨页排列顺序

按读者使用频率和"学完一个产品接下来最可能翻哪页"排，而不是内容生产顺序或字母序。这不是一根轴，是两根独立的轴叠加，排序时要分别测试、不要用一根轴的结论去覆盖另一根：

**轴 A——概念依赖（决定"最早能放在哪"）**：一份文档如果读起来需要前面某个概念（如 MCP、Skills、Hooks）作为前提，就不能排在那个概念之前，哪怕它本身很常用。

**轴 B——受众复杂度（决定"该往后拖多远"）**：文档的目标读者是"所有用户"还是"开发者/发布者/团队管理员"，决定了它该多靠后。轴 A 只规定下限，轴 B 才决定在下限之上具体排多后。

排列步骤：

1. **学习地图**（index）永远最前——先建立全景图，再进任何一个产品
2. **核心产品的 Tutorial** 按使用频率排（同一家族里两个高频核心产品的相对顺序由实际使用习惯决定，不是绝对规则）
3. 每个核心产品的 Tutorial 之后紧跟它自己的 **How-to → Reference → Explanation** 三件套（Cookbook → Cheatsheet → Glossary）——读者学完主教程，最先想动手（How-to），动手时随时跳查参数（Reference），概念记混了才翻定义（Explanation）；这个内部顺序不要因为字母序或创建顺序而打乱
4. **依赖前面概念、且仍是消费级/面向所有用户的文档**（如 Connectors——依赖 MCP，但用户侧只是点一下 OAuth）紧跟在核心产品三件套之后
5. **不依赖前面概念、但对目标读者本身相关度较低的独立周边产品**（如 Cowork——概念上离 Claude.ai 更近，但自身定位"面向非工程师"，对当前教程的目标读者优先级低）按预期使用频率排在中段——**不要因为它概念上更亲近某个早出现的产品，就把它排到那个产品旁边**；读者相关度优先于概念亲缘
6. **开发者/发布者/团队管理员向的进阶扩展文档**（如 Plugin——即使它和 Connectors 同属"扩展机制"，只要读者对象换成了"开发者、发布者"、内容涉及"企业级分发""marketplace 配置"，就要独立于 Connectors 挪到全篇收尾）永远放最后，不因为轴 A 判定它和 Connectors 同属一类就并排

**踩过的具体错误（Claude 家族示例）**：曾经把 Connectors 和 Plugin 当"同一对扩展机制"相邻排列——只测了轴 A（两者都依赖 Claude Code 讲过的概念），没测轴 B（Connectors 面向所有用户、Plugin 面向开发者/发布者，中间有个复杂度断崖）。正确做法是两根轴分开测：轴 A 只回答"能不能放在 Claude Code 家族之前"（不能），轴 B 才回答"具体排第几"（Connectors 靠前、Plugin 收尾）。

判断一份文档是否需要"往后拖到底"（轴 B 强信号），检查它的开篇定位句是否出现"开发者""发布者""团队""企业级"这类字眼——出现即说明受众已经从"终端用户"切换到"构建/分发方"，无论轴 A 结果如何都应该整体上排到更靠后的位置。

Claude 家族示例顺序：

```
index.md                   ← 学习地图 + 功能速查
claude-ai.md               ← 核心产品 1：Claude.ai（Tutorial）
claude-code.md              ← 核心产品 2：Claude Code（Tutorial）
claude-code-cookbook.md    ←   └ How-to（实战工作流）
claude-code-cheatsheet.md  ←   └ Reference（决策表/配置/数据源）
claude-code-glossary.md    ←   └ Explanation（术语表）
connectors.md              ← 轴 A：依赖 MCP；轴 B：消费级，紧跟核心产品
claude-design.md           ← 轴 A：无依赖；轴 B：终端用户向，对前端工程师相关度中高
cowork.md                  ← 轴 A：无依赖（概念上更亲近 Claude.ai）；轴 B：定位"面向非工程师"，相关度低，排后
plugin.md                  ← 轴 A：依赖 Skills/Hooks；轴 B：开发者/发布者/企业级，全篇收尾
```

> **踩过的坑**：这个顺序曾经被写反过——Cheatsheet 排在 Cookbook 前面（读者还没学完 How-to 就先看参考手册）、Connectors/Plugin 排在 Design/Cowork 后面（扩展机制被当成了和独立产品同等地位，混在字母序/创建顺序里）。写完顺序后用上面的测试逐个过一遍，比凭直觉排更可靠。

## 何时需要多一层导航分组（侧边栏嵌套）

一个产品家族的文档页数变多之后（Claude 示例到了 9 个二级页面），单层平铺的侧边栏会让读者一屏看不全、也看不出"哪些是天天要用的、哪些是偶尔才碰的"。这时该不该拆成物理子目录、还是只加导航分组，判断依据：

**只加导航分组，不建物理子目录**——除非有强理由，否则默认选这个：

- VitePress（以及大多数静态站点生成器）的侧边栏支持嵌套 `items`（`{ text: '分组名', collapsed: true/false, items: [...] }`），纯展示层特性，文件路径、URL、文件间的相对链接完全不受影响
- 建物理子目录（如把 `connectors.md` 挪到 `claude/advanced/connectors.md`）的代价是：所有外部书签/引用的 URL 失效、目录内所有 `./xxx` 相对链接要重写成 `../xxx`，为了一个纯展示需求承担这些不可逆成本不划算
- 只有当"文件系统组织"本身也是目标（比如团队按目录分工维护、CI 按目录路径跑不同校验）时，才值得建物理子目录——没有按目录分工或按路径跑不同 CI 时，不要建物理子目录

**分组依据来自权威先例，不是凭空发明**：Claude Code 官方文档（[code.claude.com/docs](https://code.claude.com/docs/llms.txt)）本身就是分层导航——顶层categories 里单独有一类 **"Extensibility"**（MCP、Skills、Plugins、Hooks、Channels），和 **"Using Claude Code"**（含 Common workflows）分开；**"Reference"** 类目下 CLI reference、Hooks reference、Plugins reference 和 **Glossary** 汇总在一起。这印证了两点：核心用法和扩展能力分层是官方验证过的模式；Glossary 属于 Reference 的一部分，不需要单独成一个导航层级，放进同一个"参考"分组即可。

**分组数量和折叠状态按频率定，不是按分类学定**（[Fern 信息架构指南](https://buildwithfern.com/post/information-architecture-best-practices-documentation)：*"嵌套文档系统的顶层可见分类建议控制在 3-5 个""永远不要把庞大层级塞进单个展开侧边栏，开发者需要的是搜索和分层收纳，不是滚动几千行树状列表"*）：

| 分组 | 折叠状态 | 判断依据 |
|------|---------|---------|
| 核心产品（Tutorial + 紧邻的 How-to） | 默认展开 | 每天都会点，藏起来增加点击成本 |
| 更多产品与扩展 | 默认折叠 | 学习曲线里的"20%"，进阶后才需要，折叠 = 渐进式呈现（progressive disclosure），不代表不重要 |
| 速查与参考（Cheatsheet + Glossary） | 默认展开 | 虽然是"查阅型"而非"学习型"，但使用频率和核心产品一样高——UX 研究对渐进式呈现的告诫是"不要把高频功能藏进 advanced 分组"，速查表就是这种反例的典型，必须展开 |

判断某类内容该不该折叠，用这一句测试：**读者还在学的时候会不会天天点开它？** 会 → 展开；只有学到一定阶段或做特定任务才会点 → 折叠。折叠不是"不重要"的标记，是"现在还用不上"的标记，别混为一谈。

示例三层分组：

```
Claude（侧边栏一级）
├── 🗺️ 学习地图                          ← 独立于分组之外，永远最先看到
├── 核心产品（默认展开）
│   ├── Claude.ai 平台
│   ├── Claude Code CLI
│   └── Claude Code 实战 Cookbook
├── 更多产品与扩展（默认折叠）
│   ├── Connectors 连接器
│   ├── Claude Design
│   ├── Cowork 桌面代理
│   └── Plugin 开发
└── 速查与参考（默认展开）
    ├── Cheatsheet 速查表
    └── 术语表 Glossary
```

## Cheatsheet 应该包含哪些模块

速查表是产品文档的"瑞士军刀"——读者查参数、查决策、查资源都靠它。完整的速查表应该包含：

| 模块 | 作用 | 典型内容 |
|------|------|---------|
| **决策表** | "我该选哪个？" | 用场景列对照行、用方案列对照列的二维表 |
| **术语表索引** | "这个术语是什么意思？" | 链到 Glossary 详页 |
| **配置参数速查** | "这个 key 怎么写？" | 字段、类型、默认值、示例 |
| **命令清单** | "这个命令的参数是什么？" | 命令 + 用途 + 关键 flag |
| **常见错误** | "我遇到 X 错误怎么办？" | 症状 → 原因 → 解决 |
| **模板** | "给我一个能跑的样例" | 复制即用的 JSON/YAML/CLI |
| **数据源** | "我该去哪继续学习？" | 官方文档/Cookbook、核心账号、博客、仓库 |

可以不全要，但**只有决策表没有配置速查**或**只有参数没有数据源**的速查表都不完整——读者查到一个 key 怎么写，立刻想知道"这个为什么这么选"和"还有哪些选项"，决策表能补上后者。

**"术语表索引"是索引，不是第二份术语表**：这一模块最容易写成"把 Glossary 每个词条抄一遍、稍微精简"——真实发生过：Cheatsheet 曾完整复制 Glossary 里每个概念的"是什么/机制/官方链接"（127 行），两边各自维护后一周内措辞就开始漂移（同一个 Connectors 的定义两边字眼不一样）。正确形态是**一行一个概念**：术语 + 一句话钩子 + 链到 Glossary 对应锚点，绝不重复"是什么"以外的解释性内容。写完 Cheatsheet 的术语索引后，检查每一行是否只有一句话——超过一句话就是在抄 Glossary，应该删到只剩链接。

## Glossary 应该包含哪些模块

术语表是产品文档的"语义层"——保证跨页面口径一致。建议模块：

| 模块 | 作用 | 典型内容 |
|------|------|---------|
| **概念关系图** | 一图看全局 | 节点 + 关系图（ASCII/Mermaid） |
| **每个概念的"是什么"** | 一句话定义（区别于其他概念） | 1-2 句 |
| **每个概念的"为什么需要"** | 没有它会怎样 | 1-2 段 |
| **每个概念的"在生态中的角色"** | 它和谁相关、谁依赖它 | 1 张表 |
| **每个概念的"工作机制"** | 它怎么实现的（高层、不钻细节） | 1-2 段 |
| **每个概念的"与 X 的区别"** | 易混淆的概念用对比表澄清 | 表格 |
| **每个概念的"使用场景"** | 什么时候该用它 | 列表 |
| **每个概念的"官方文档"** | 链回官方深读 | 链接 |

不必每个概念都全写——但 **"是什么"** 是必填项，**"与 X 的区别"** 是高频出错概念的必填项。

## 何时更新本文档

- 官方一级导航出现新产品时，先更新家族图（见 [`family-completeness.md`](./family-completeness.md)），再决定轴 A/B 位置
- 新增一个产品文档目录时，先确认它的结构和 Diataxis 四象限的对应关系，记到消费仓库对应工具的维护参考
- 跨文档出现章节重复或口径漂移时，回看决策框架判断该拆还是该合
- 切分原则需要变更时（如发现新的典型错误模式），更新本文档
