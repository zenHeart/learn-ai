# AGENTS.md

本文件是本书章节骨架的**单一真相来源**。`book/validate.js` 校验其中的机械规则（标题编号、源码链接格式、章节清单）。写作方法论见 `deep-tech-author` skill 的 `SKILL.md`，两者冲突以本文件为准。

> `<src>` 等占位代表 `book/metadata.yaml` 里 `source_dirs` 配置的目标仓真实源码目录。正文请写真实目录名（如 `src/`）。

## 文档源码链接规范

- 所有源码层面的引用必须用可点击 Markdown link，**不允许把 link 包在反引号中**。
- 源码引用必须细化到当前仓库内真实路径和具体行号，优先写成 [main.ts#L424](<src>/main.ts#L424)（正文里把 `<src>` 换成真实目录，如 `src`）。
- 正文需要展示函数名时，函数名可用反引号；对应源码位置必须另给可点击链接，例如：`runMigrations()` 见 [migrations.ts#L305](<src>/migrations.ts#L305)。
- 正文保持仓库相对路径形式，**不手写 GitHub URL**，也不使用其他书籍的虚拟源码前缀。EPUB 构建会把 `<src>/...#Lx` 自动转换为 `{repo_url}/blob/{source_ref}/...#Lx`（取自 `metadata.yaml`）。
- 若配置了 `upstream_repo`，正文源码链接不得指向上游仓库，必须指向你自己的 fork。
- 修改章节后运行 `node book/validate.js`，确认章节清单、标题编号、docs 引用和源码链接有效。

## 文档标题编号规范

- `book/chapters/chapter-*.md` 必须使用显式编号标题，避免 EPUB 目录中同级标题不一致。
- H1 使用章节号，例如 `# 13. 上下文压缩与长期任务`。
- H2 使用章节号和小节号，例如 `## 13.1 它解决什么问题`。
- H3 必须在父 H2 编号后追加第三级序号，形如 `N.m.p`，例如父小节 `## 13.3 核心机制` 下写 `### 13.3.1 边界条件`。H3 是最深的编号层级；更深的嵌套应重构回 H3，不要下沉到 H4。
- 同一文档内不得混用编号标题和裸标题。“总结”小节也必须是顺延编号的最后一个 H2，例如 `## 13.8 总结`，不允许写成裸标题。
- 新增或移动小节时必须同步调整后续编号。修改后运行 `node book/validate.js`，它会校验 H1 章号、H2 顺延小节号、H3 的 `N.m.p` 前缀。

## 分析章节写作范式

- 本书面向完全不了解目标项目、但具备相应方向工程经验的读者。章节目标不是罗列代码，而是还原设计决策、让读者能独立复刻。
- 全书开篇应有一章「架构与权衡总览」：给出分层心智模型、关键术语定义、核心权衡清单。
- 每章统一采用以下标准小节骨架，名称保持一致，便于 EPUB 目录与跨章引用：
  - 章首引用块声明：前置知识、本章覆盖/不覆盖、**关键术语**（首次出现、需先建立的 2–5 个术语，一句话定义）。
  - `## N.1 它解决什么系统问题` — 用具体场景说明缺了它会有什么不可接受的成本、风险或能力缺口；有层次的机制先给一张结构总览图。
  - `## N.2 用户视角完整流程` — 一个可独立运行的最小示例，串起从用户操作到系统响应的完整路径。
  - `## N.3 机制拆解` — 每个核心子机制用一个 `### N.3.p` H3，走「朴素实现 → 边界缺陷 → 改进实现」的迭代叙事；这是承载「源码级复刻」的核心小节，不可退化为路径罗列。为未来预留的字段/分支须显式标注（“X 节会用到”）。
  - `## N.4 源码映射` — 表格列出文件、责任、输入、输出、裁决边界。
  - `## N.5 设计不变量与权衡` — 解释 WHY，**每个关键决策必须溯源到外部权威**（规范/协议、真实 bug、语言或工具约束、不变原理），并给出至少两个被拒绝的替代方案（why-not）。
  - `## N.6 常见误解与失败模式` — 读者最易踩的误解与生产环境失败场景及根因。
  - `## N.7 本章训练` — 三级练习：`### N.7.1 使用级`、`### N.7.2 原理级（最小复刻）`、`### N.7.3 扩展级`。
  - `## N.8 总结` — 按小节回顾要点，最后一句连接下一章。
- 简单章节可在 N.3/N.4 内合并部分内容，但小节编号与命名不得改写。
- “如何解决”应写成机制组合，而不是只写函数调用链；优先说明协议、运行时、产品策略、安全边界如何协作。
- “源码映射”要说明源码承担的系统责任、输入、输出，以及在链路中的裁决边界。
- 设计经验应从本项目的具体实现抽象到通用原则，明确哪些经验可迁移到读者自己的系统，哪些只是本项目的产品选择。
- 复杂章节应包含常见误解、失败模式或边界条件，避免读者学到过度简化的模型。
- 复刻类章节应区分最小可用实现、生产级实现和可暂缓的高级能力，帮助读者按风险和收益分阶段落地。

## 图示规范（图示是一等公民）

- 结构、数据流、状态迁移、多角色交互等内容应配图；业界最好的源码书都因配图被反复称赞，**该上图就上图**。
- 图类型匹配内容：结构→树/分层框图；流向→有向图（标注链路）；状态→`stateDiagram`；交互→`sequenceDiagram`；决策分支→`flowchart`。
- 复杂能力的图应显式标出阶段边界，例如“启动/发现”“用户触发/模型决策”“执行/结果回灌”。
- 克制点：单变量变化、简单条件分支、直接顺序步骤不必上图。每张图前后必须有文字说明和标题，图不替代讲解。

## 生命周期问题（带运行时/事件循环的系统适用）

若目标项目是带运行时、事件循环或 Agent loop 的系统，复杂能力章节优先回答：它解决什么系统问题；用户视角完整流程是什么；启动时加载什么、运行时再加载什么；外部调用方能看到什么、运行时私下保留什么；触发条件是什么；执行权在哪里；结果如何回灌；失败和安全边界是什么。
