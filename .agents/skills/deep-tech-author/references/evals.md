# Skill 评估用例

检查 `deep-tech-author` 是否正确触发并产出预期工作流时，使用这些用例。

## 应触发

- “帮我给这个开源仓库写一章架构总览。”
- “改写第 3 章，让 N.3 更像源码级复刻。”
- “对这个项目做源码级深度分析，写成技术书章节。”
- “把这个模块从朴素实现到生产级设计逐步拆给读者。”
- “写一章，解释 agent loop 的状态机和为什么这样设计。”
- “生成本章 N.3 的朴素实现、边界失败和改进实现计划。”
- “给这个仓库做一本源码级书的章节规划。”
- “技术书籍写作：把这段源码讲到读者能复刻。”

## 不应触发

- “帮我 review 这个 PR 的安全问题。”
- “写一个普通 README。”
- “把这篇论文总结成三段。”
- “生成一个前端 landing page。”
- “检查这章质量是否达标。” 应改用 `agents/deep-tech-reviewer`。

## 功能验收

- 给定目标仓库和章节范围后，Skill 应先分析源码文件并产出章节计划，再撰写长正文。
- Skill 应先读取 `~/config/resource.yaml` 或 `RESOURCE_CONFIG_PATH` 指定的资源注册表；缺少仓库、机器、Agent 或分支权限时应停止并报告，而不是猜测路径或权限。
- 对 Fork 项目，Skill 应区分 upstream 默认分支同步与个人内容分支写入，不得向 upstream push 或创建 PR。
- 章节计划应包含 H2 目标、N.3 子机制、代码示例迭代计划、图示计划、关键术语和 WHY 溯源候选依据。
- 章节草稿应遵循 N.1-N.8，包含可运行示例，使用仓库相对源码链接，并通过 `node book/validate.js`。
- 未经用户明确确认，Skill 不安装依赖、不提交、不推送、不发布、不启用 GitHub Pages。
