# 写给读者的产品文案

`product-schema.md` 规定 `solves` / `best_for` / `desc` **写什么**。本文件规定**怎么写**，
以及为什么第一版 251 条读起来像机器写的。

---

## 1. AI 味主要不是词汇问题

`check_ai_flavor.py` 跑遍全库只命中 3 处，其中 2 处是误报（*address bar* 的 bar、
*Ascendant* 里的 bar）。**查不出问题，不代表没有问题**——规则匹配的是空洞大词
（赋能、抓手、闭环、矩阵），而这里的毛病不在词。

真正的破绽是**结构齐一**：251 条全都是同一个两拍模板——

> 「痛点铺垫句。你<产品名>来<解决动作>。」

豆包、Cursor、Dots、Fathom 全是这个形状。读者连看五行就会意识到这不是人写的。
**整齐本身就是破绽。** 省略号式的整齐、每段都同长度、每条都先抑后扬——这些是模型
出厂设置带来的，不是内容需要。

排检器查不出的，就是这一类。

## 2. 五条改法

### 2.1 先读产品自己的话，再动笔

不要凭 `tags` 和 `category` 推理文案——那正是「AI 味」的来源，因为推理出来的东西
必然是分类的复述。

去 `homepage` 抓产品自己的描述、帮助文档首段、功能列表标题。**产品方用的词就是
准确的词**：他们叫 *workspace* 不叫 *协作空间*，叫 *transcript* 不叫 *转录文本*。
把产品的原话压缩到一句话，比自己造一句更像人话。

抓不到就如实写你确实知道的那部分，**不要用形容词补足长度**。

### 2.2 一条一个形状，不要每条同一拍

不是每条都该「先痛后解」。按产品实际特点选形状，用得上的都用：

| 形状 | 什么时候用 | 例 |
|---|---|---|
| 直陈 | 产品做的事本身就说明白，无需铺垫 | `本地跑模型，一条命令拉下来。` |
| 场景切入 | 痛点很具体、有画面 | `半夜排查线上问题，AI 给不出上下文。` |
| 限制先行 | 产品有明确边界，说清比吹好 | `不写代码，只查代码。` |
| 对照 | 前后差异大、反差明显 | `原来要开五个网页，现在一个对话框。` |
| 代价点破 | 用户踩过坑，知道贵在哪 | `效果好的模型都贵。这家按 token 计价。` |

**注意**：形状不同不等于长短不一。句子该短还是短，只是骨架别重复。

### 2.3 不要每条都造一个「你」

模型很爱写「你一关标签页，活就停了」这种——先替读者造一个困境，再由产品拯救。
偶尔一次是好文案，251 次就成了套路，还会显得油腻。

写「关掉标签页后任务中断」比「你一关标签页，活就停了」更省字也更准。**能用陈述句
就不用第二人称。**

### 2.4 删掉为了完整而加的尾巴

模型倾向把一句话补成一个完整的小结，因为怕显得短：

- 「……长任务不会因为你走开而中断。」→ 断在半句也有力。
- 「……直接问就行。」→ 删掉「就行」更像人。
- 「……你不用自己动手点。」→ 前面已经说过了。

**每条结尾问一句：最后那半句是信息，还是补齐手感？**

### 2.5 专有名词按产品方的写法

- 大小写照抄：`GitHub Copilot` 不是 `Github Copilot`；产品自称 `dots` 就别写成 `Dot`。
- 保留产品自己的技术词：`supertag`、`RAG`、`MCP` 不要翻成模糊说法。
- 官方没有中文名的，别硬翻；官方有中文名的，用官方的。

## 3. 不要用这些自查

- **不要**追求「口语化」而堆俚语。给工程师看的产品说明不需要「超香」「绝了」。
- **不要**每条都加感叹号或破折号强调。
- **不要**因为排检器零命中就认为过关——第 1 节说过，它查不出这一类。
- **不要**为了长短一致去改写得别扭的句子。**长短不齐是对的**，刻意对齐才是。

## 4. 写完之后

1. 把这一批的 `solves` 首句连着读一遍，只看首句。**如果开头十个都是同一个句式，
   就是没改干净。** 这是最快的自检。
2. 挑三条跟同类产品并排读。同一场景下的两条，长得不一样才对。
3. 有没有句子是为了「像个产品介绍」才写的？删掉它通常不损失信息。

## 5. 事实纪律（不可让位给文风）

上面全是文风。**下面这些一条都不许为了顺口而改**：

- 数字、日期、版本、参数
- 能力边界与限制（「只支持英文」「不写代码」）
- 否定、适用条件、确定程度（「仅精确到月」「未确认」）
- 产品名与专有名词的原样写法

文风是**减法**：删冗余、删套话、删补齐手感的尾巴。**不是加法**——不要为了具体感
编造场景、数据或经历。要写一个具体场景，就用产品文档里真实存在的那个。
