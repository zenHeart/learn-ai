Cindy source code walkthrough: how the three harnesses are wired into one workspace ​

The short version: the core of Cindy is not yet another agent, but a layer of "session plus adapters". packages/maker-core translates three mutually different process protocols, those of Claude Code, Codex and Pi, into the same event stream, and the interface, the local database and the phone's remote control above it all recognize only this event stream. Codex has no separate maker-codex-manager package; it is implemented directly in packages/maker-core/src/agents/codex/ and driven by a codex app-server subprocess.

Every conclusion on this page is checked against makecindy/cindy commit 6fdec7fb (full hash 6fdec7fb89b955be548c3f5cc9a42d83bf174aa3); later changes are outside the scope of this page. For the Verified / inferred / unknown layering, see the end of the page.

Who it is for / who it is not for ​

  • Who it is for: people who want to audit Cindy and need to know whose hands tasks and files pass through and what the phone can do to the computer; people who want to submit a PR and first need to know where the code lives; people who have used it and have questions, such as why switching harness loses context.
  • Who it is not for: if you only want to install it and use it, read the tutorial; if you want to read the server side, the README states that the backend is "Not in this repo"; if you want an introduction to Electron, this page assumes you already know that the main process and the renderer process are two different things.

Three counterintuitive facts ​

First, the largest single file is the Codex adapter. Non-test line counts of the three adapters: agents/codex/index.ts 16,738 lines, agents/pi/index.ts 10,437 lines, agents/claude-code/index.ts 8,740 lines. Second, maker-cc-manager is not the driver of the local Claude Code. Its package description states that it is an NDJSON RPC daemon "spawned on remote SSH machine". The driver of the local Claude Code is in maker-core and calls the official SDK directly. Third, maker-ipc/register.ts in the desktop main process is 23,761 lines in one file, with 174 calls to ipcMain.handle or ipcMain.on. Phone remote control can reuse these handlers, and not because they were refactored one by one; see Mechanism 2 below.

Architecture and data flow: the complete round trip of one task request ​

Read on with this question: the interface sends only one IPC call, so how does the message reach an external process that knows nothing about Cindy?

Outbound: from the interface to the subprocess ​

The renderer process does not touch tasks directly. It calls an IPC channel through preload: ipcRenderer.invoke('maker:send', sessionId, message, createOpts, sendOpts) (apps/desktop/src/preload/preload.ts, line 7859). The entry on the main-process side is sendToSessionInternal (register.ts, line 12284); queueing and saving to the database are handled by AgentInputCoordinator in the same directory. Its file-header comment explains why this layer exists:

One user input crosses four state owners: the queue projection, the visible bubble, the SQLite message row, and the maker-core dispatch boundary. This coordinator makes the state transitions explicit and routes every pre-dispatch failure through a rollback path.

Source: agent-input-coordinator.ts, lines 19 to 42.

The center of maker-core is Maker and Session. Maker holds all active tasks in one map (maker.ts, lines 534 to 539). Session.send hands the actual send to dispatchSend. The latter runs a long list of guards: wait for the previous turn to end completely, wait for a permission switch to land, confirm that no other send has already reserved the slot, and only then push the message to the harness:

ts
          await this.handle.send(msg, bindSessionSendOwner({
            ...handleOpts,
            [AUTO_REVIEW_SOURCE_CONTENT]: autoReviewSourceContent,
            signal: reservation.abortController.signal,
          }, reservedTurnGeneration, () => {
            if (reservedTurnGeneration !== this.turnGeneration) return undefined;
            return this.terminalEventObservedGeneration === reservedTurnGeneration
              && this.unsolicitedTurnGeneration !== reservedTurnGeneration ? 'settled' : 'unsettled';
          }));

Source: packages/maker-core/src/session.ts, lines 1145 to 1153. Here handle is a very thin interface, AgentSessionHandle; Session knows only its send(message, opts) and no concrete harness (base-agent.ts, lines 2641 to 2642).

Taking Codex as the example, handle.send ends at one JSON-RPC request:

ts
      await host.request(Method.TurnStart, {
        threadId,
        input: [{ type: 'text', text: prompt }],
      } as TurnStartParams);

Source: packages/maker-core/src/agents/codex/index.ts, lines 3624 to 3627. It is written to the standard input of the codex app-server subprocess. The subprocess is started like this:

ts
  const args = ['app-server', ...(opts.extraArgs ?? [])];
  const child: ChildProcessWithoutNullStreams = spawn(opts.binaryPath, args, {
    cwd: opts.cwd,
    env: opts.env,
    // All three streams are piped: we write to stdin, read stdout, and stderr goes to onStderr (for diagnostics).
    stdio: ['pipe', 'pipe', 'pipe'],
    // Windows: no shell, go straight to the binary; going through a shell brings env injection risk
    // and makes the stdio piping behavior uncontrollable.
    shell: false,
    // On Windows the app-server and its console handle should not interrupt the desktop UI.
    windowsHide: true,
    // Do not create a separate process group; close() must still explicitly wait for and confirm the child's exit.
    detached: false,
  });

Source: packages/maker-core/src/agents/codex/app-server/stdioTransport.ts, lines 77 to 90. Note three conservative choices: no shell, no separate process group for the subprocess, and closing must wait until it has really exited.

What the diagram is based on: the entry point maker:send is checked against preload.ts L7859 and register.ts L12284; dispatchSend and "no running turn" against session.ts L925–L930 and L1145–L1153; the adapter's send against base-agent.ts L2641–L2642; Codex's turn/start against codex/index.ts L3624–L3627 and host.ts L796–L811; the unified event types against events.ts L30–L47, all at commit 6fdec7fb. Two points stated as they are: for the return path of steps 10 and 11 only the two ends were verified, and the middle is drawn hop by hop along the path already given by steps 1 and 9, so it is inferred; the arrows between the UI and the main process cross the preload-bridge lane directly, because only step 1 states that it passes through it. Return: unified events and confirmation requests in the reverse direction ​

Each of the three adapters has its own translator.ts that turns the harness's raw output into unified events. There are 17 event types in all (packages/maker-core/src/types/events.ts, lines 30 to 47); the ones the interface cares about are these:

Event typeMeaning
text, thinkingStreaming body text and reasoning text
tool_use, tool_resultA tool call starting, and its condensed result
turn_diffThe harness's cumulative unified diff of this turn's workspace changes
interaction_requestNeeds a user decision: permission, a question, plan review
statusA state change, with a usage snapshot
done, errorA turn ended, or an error

The confirmation card travels as a reverse request. When Codex wants to run a command, it is the app-server that sends a request to Cindy. Cindy's handling has a fallback: when no matching subscriber is found, it always declines.

ts
      if (!handlers?.commandExecutionApproval) {
        this.logger.warn('commandExecution approval without subscriber → decline', {
          threadId: params.threadId,
          itemId: params.itemId,
        });
        return { decision: 'decline' };
      }

Source: packages/maker-core/src/agents/codex/app-server/host.ts, lines 796 to 811. The catch block right after it also returns a decline when the handler throws. In this direction the rule is "block on error", not "allow on error".

Key mechanism 1: how Cindy drives the three harnesses ​

The problem to solve: the three harnesses speak three languages, and Cindy wants the layers above to need no knowledge of which one is underneath.

HarnessAdapterHow the process is started and how it talksEvidence
Claude Codeagents/claude-code/index.tsThrough query and forkSession of @anthropic-ai/claude-agent-sdk 0.3.321Lines 35 to 38, line 1124
Codexagents/codex/index.ts and app-server/Starts a codex app-server subprocess and runs NDJSON JSON-RPC over stdioThe two excerpts in the previous section

Where Codex plugs in: the most frequently asked point about this page. The answer:

  1. There is no maker-codex-manager under packages/; it is not in the output of ls packages.
  2. The Codex adapter is in packages/maker-core/src/agents/codex/: one CodexAgent class plus an app-server/ subdirectory.
  3. The helper code for accounts and sign-in is on the Node background service side: eight files under apps/host/src/agent/, including codex-runtime.ts, codex-credentials.ts, codex-system-login.ts, codex-thread-storage.ts and codex-token-reader.ts.
  4. The three instances are created in two places: on the desktop side at maker-host/index.ts, line 1453 and line 1768 and maker-host/pi-host.ts, line 268; on the Node background service side at runtime.ts, lines 702, 774 and 860.

One place is easy to get wrong: the "mcp-integrations codex MCP" mentioned in the repository map and the Orca document is where the collaboration feature attaches an MCP bridge to Codex; it is not the entry that drives Codex.

The Codex side has one more design that differs from the others. The file header of AppServerHost states (lines 1 to 14): one CodexAgent starts only one app-server, each task maps to one thread on the server side, and inbound notifications are routed back to the matching task by threadId. The same file also leaves a note for Windows: "Windows child processes do not die with the parent", so it must be closed explicitly before the app exits.

What happens when you switch harness. The desktop main process has a dedicated handler, and its file header states the flow plainly:

ts
 * The send transaction (applyPendingAgentSwitchIfIdle → applyNow=true) runs once:
 *   validate → look up the target engine's docked binding (Phase 2) → build the handoff text (pure code,
 *   agentHandoff.buildHandoffText: with a docked binding = incremental mode, otherwise full)
 *   → close the old live session → DB commit (agent_kind + model + provider_id + effort/fast;
 *   sdk_session_id lands on the migration / docking id or null) → insert the agent_switch boundary row (the full handoff text is persisted
 *   here, and the UI can expand it) → register the pending injection → (on resume) immediately rebuild the new engine's session.

Source: apps/desktop/src/main/maker-ipc/sessionAgentSwitchHandler.ts, lines 6 to 11.

What it means for users:

  • Losing context when you switch harness is by design. The new engine gets a piece of handoff text plus a rebuilt session, not the old engine's internal state. This is the code behind the README sentence "rather than making their internal states identical".
  • Switching back to the original harness loses a little less. A comment in the same file states that each engine's native session is "docked" when it leaves, and when you switch back it is restored with only the increment filled in.
  • Codex's confirmation card would rather block wrongly. A missing subscriber or a handler that throws both end in a decline.

Key mechanism 2: device connection, how devices find each other and where the traffic goes ​

The problem to solve: the phone has no agent, yet it must be able to operate tasks on the computer; at the same time the phone must not get all of the computer's capabilities.

How they discover each other. After a device connects to the service it sends one hello frame, carrying the device name, platform, app version, whether it allows being controlled, and whether it is busy; the server broadcasts state changes of devices on the same account as presence-changed. The device list has a separate REST endpoint, GET /api/device-link/devices. These are written in the "Connection lifecycle" section of packages/device-link/README.md.

Whether the traffic passes through a relay. Device Link has two routes: a direct connection over WebRTC, and a relayed connection over WebSocket. There are four kinds of line, which the product rules list as: the official relay, deployed on my server, this computer as the relay, and joining someone else's relay. The core of a self-hosted relay is in this repository: the package description of packages/device-link-relay says it "can run both inside Cindy and standalone with Node on a server".

Can the relay see the content. In two layers. The protocol envelope is Envelope in packages/device-link-protocol/src/protocol.ts (lines 51 to 65); the payload field has the type unknown, and the whole interface has no encryption or signature field at all. In other words, on the V1 wire protocol the relay can get the business content. The self-hosted relay core in the repository declares that it does not look:

ts
 * Only understands connection-layer frames and routing headers; tunnel-layer payloads (the channel/args of invoke, push content) are forwarded as is, not parsed.

Source: packages/device-link-relay/src/hub.ts, line 3. That is the behavior of the open-source core. The official relay is closed source; whether it reads or retains content cannot be verified on this page.

Who can see what. The controlled computer does not hand over the whole main process; it opens only one allowlist:

ts
 * Two-layer validation: before the controller sends (fail fast) + before the controlled end executes (authoritative).
 * A new channel that is not added to the table is naturally not remotely callable (the code guarantees determinism).

Source: packages/device-link/src/allowlist.ts, lines 19 to 20. The full set is REMOTE_INVOKE_ALLOWLIST in the same file (line 832), deny by default. The file header also lists the categories that are "never allowed": application windows and UI, local dialogs, shell side effects, accounts and keys, writes to the controlled end's global settings, raw writes to the local database, and the updater. The implementation has a clever shortcut: apps/desktop/src/main/device-link/invoke-registry.ts replaces ipcMain.handle before any handler is registered and records the whole mapping from channel name to handler, so a remote call can use a synthetic event to call the handlers that already exist on the computer, with zero changes to the registration points in more than forty files.

Agent-Net (Beta) adds encryption. The product rules position it as "the next generation of device-link: replacing the transport layer and the identity layer"; the first hard rule is "end-to-end encryption", and it also requires that "users can use their own relay" and that "the LAN does not depend on a server". Its transport core, packages/agent-net-core, is a general reliable UDP protocol. The rules also state that it is "off by default", and that when off its behavior must be exactly the same as the existing Device Link.

Remote desktop uses a separate media channel. The developer document states: Device Link's WebSocket remains the signaling and control channel, the picture and input go over WebRTC's ICE, and when the video cannot connect it falls back to the original JPEG picture channel; the ICE configuration (including TURN credentials) is requested by the controlled end and the viewer separately from GET /api/device-link/ice-servers.

What it means for users:

  • Under V1, your task content is visible to the relay at the protocol level. If you mind, turn on Agent-Net (Beta), self-host a relay, or use local mode only.
  • The phone cannot get your keys, and it cannot change the computer's global settings. This is not done by hiding them in the interface; the allowlist simply has no such channels.
  • A task that can run remotely does not have small permissions. The allowlist's own comment puts it clearly: with the same account and being controlled explicitly turned on, the controller can already run an agent in the working directory, and so can run arbitrary commands. So the "Allow same-account devices to control this machine" switch amounts to handing the shell of the working directory to the other devices signed in to your account.

Key mechanism 3: Orca, one Lead directing several Workers over MCP ​

The problem to solve: one agent has limited context and can use only its own kind of model. A large task needs several agents with different strengths working in parallel.

How the code does it. Orca is "one Lead task plus several Worker tasks". The collaboration architecture document in the repository defines it precisely: the Lead is responsible for splitting the task, assigning work, acceptance and summary; the Workers are responsible for execution; "a Worker is a complete session, not a one-off subagent". The Lead directs Workers through a set of MCP tools, on a server named cindy_orca. The Lead's system prompt lists them directly:

ts
    'Tools: get_workspace_info, create_worker, create_workers, send_to_worker, interrupt_worker, get_worker_queue_status, update_queued_message, cancel_queued_message, merge_queued_messages, steer_queued_message, move_queued_message, update_worker.',
    '(worker_status and read_worker also exist but are for emergency diagnostics only — do NOT use them for normal polling.)',

Source: packages/orca-workflow/src/orca-bridge-prompt.ts, lines 32 to 33.

  • Assigning work is asynchronous. The same prompt states that a Worker calls send_to_lead to report when it is done, the Lead "is woken up automatically", and no polling is needed.
  • Each Worker has its own queue. The queue is first in, first out; the Lead can jump the queue, merge, and cancel instructions that have not run yet.
  • Workers and native subagents are deliberately kept apart. The prompt requires the Lead to use the native mechanism only when the user explicitly says "subagent", and not to use the native subagent lifecycle tools to wait for a Worker. The Worker side has its own bridge, on a server named orca_worker_bridge.

What it means for users: each Worker is a real task, with its own harness, model, permissions and history; you can see it in the interface and take it over on its own. The Lead's harness can differ from the Workers'; this is what the official site's example of "one kind each for planning, execution and review" is built on. The document's "current boundaries" state that a team is bound strictly to one Lead, sharing Workers across Leads is not supported, and switching focus only changes what is displayed rather than showing them side by side.

Appendix: what problem model protocol bridging solves ​

Each harness speaks only one model protocol: Claude Code speaks Anthropic Messages, Codex speaks OpenAI Responses, Pi goes through its own SDK. To let any harness use any provider, someone has to translate. Cindy's approach is to start a proxy on the local machine that listens only on the loopback address, and translate inside the proxy. The third column below is the beginning of the description in each package's package.json; where there is an ellipsis only the first half of the sentence is kept, and the source is authoritative for the full description:

PackageWhat it doesPackage description, verbatim
anthropic-compat-proxyStrips the Anthropic-only fields when Claude Code uses a non-Anthropic modelLoopback HTTP proxy that strips Anthropic-only request fields when the target model is non-Anthropic…
anthropic-responses-bridgeTranslates between Anthropic Messages and OpenAI Responses, so that Claude Code can drive a ChatGPT subscription or xAI modelsLoopback HTTP bridge that translates Anthropic Messages API <-> OpenAI Responses API…
responses-anthropic-bridgeTranslates Responses requests for Anthropic-compatible providersIn-process bridge that translates OpenAI Responses requests and events to and from Anthropic Messages compatible providers
responses-chat-bridgeTranslates Responses for Chat Completions-compatible providersIn-process bridge that translates OpenAI Responses requests and streaming events to and from OpenAI Chat Completions compatible providers

packages/model-compat/README.md has a table showing who consumes these fixes; the last row of the table is "Mobile / remote UI": the interface side uses the selected desktop execution path and does not bring a second model transport into the interface client.

There are two points for users. First, "running domestic Chinese models with the Claude Code harness" works through translation; wherever the translation does not reach shows up as a compatibility problem, which is why the official site says the available combinations "depend on the connected service, authorization and model capability". Second, model requests are sent from the computer that runs the task, not from the phone.

The commands are authoritative in the repository's CONTRIBUTING.md and the docs/dev-rules/environment-setup.md it points to. What follows is a paraphrase, checked item by item against the root package.json.

Minimal entry point and launch ​

bash
git clone https://github.com/makecindy/cindy.git
cd cindy
git lfs pull
pnpm install

Know what pnpm install does before you run it. The environment document states that postinstall does its best to download the Desktop runtime binaries for the current platform automatically: claude, codex, ripgrep and pi, none of which go into git; a failure only warns and does not block. It also re-checks that the Electron binary is installed.

bash
pnpm restart:desktop:remote --region=cn      # Mainland China Cindy account
pnpm restart:desktop:remote --region=global  # Global Cindy account

Two things are easy to trip over. Do not rely on the default region: the README says "do not rely on the internal default". The default is an isolated dev sandbox: the desktop development document explains that the restart command is equivalent to automatically appending --isolated=dev by default, and does not share the account sign-in state or business data of your stable build; add --shared only when you explicitly want to reuse them. The experimental web version is previewed with pnpm preview:host: it always listens on http://127.0.0.1:3466, is for local access only, and uses a separate data directory. The document is restrained: until permission confirmation, stopping, reconnection recovery and desktop regression are done, it is "to be called a local experimental preview only, not a release-ready product".
