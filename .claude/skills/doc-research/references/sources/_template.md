> 这是**建立数据源清单的方法论 + 模板**，本身不产出数据。实际的数据源清单要发布成读者可见的文档页面：复制下面「条目格式」往下的内容，写进 `docs/zh/products/ai-coding/<tool-slug>/<tool-slug>-cheatsheet.md` 的「高质量信息源」章节（不要新建独立的 `sources.md`——数据源清单是 Reference 象限的一部分，和配置速查、决策表同属 Cheatsheet，拆成单独文件只会制造第五个要维护的文件，读者也要多点一次导航才能查到）并加入侧边栏和该工具 `index.md` 的资源链接区块——这样它既是 doc-research / deep-search-optimizer / doc-quality-auditor 三个 Agent 共用的事实清单，也是读者可以直接看到的资料索引，不用维护两份。该工具的目录结构/commit scope 等维护信息见 [`../<tool-slug>.md`](../claude-code.md)（同名参考文件），通用维护流程见 [`../maintenance-workflow.md`](../maintenance-workflow.md)。
>
> **写入门槛**：只收录亲自核实过（打开链接确认存在、账号确实活跃、仓库确实是该工具生态）的信息源。不确定的候选放进文末「待核实」区，不要直接列进正式分类——教程里曾经出现过凭印象写出一个不存在的命令（`/run-skill-generator`），数据源清单一旦掺入臆造条目，后续所有基于它的研究都会被污染，成本比多花五分钟核实高得多。

## 如何系统性发现数据源（先读这个，再动手搜）

真正遗漏高质量数据源，往往不是"搜不到"，而是**搜索方式本身有系统性盲区**。研究 Claude Code 的数据源时踩过三个坑，是通用规律，适用于任何工具：

### 1. 先画"官方属性地图"，再开放搜索

一个产品几乎从不只有一个官方域名/账号：主文档站之外，通常还有营销站/Blog、API 或平台文档站、Cookbook、Courses、GitHub org、社交账号——这些"姊妹站点"经常互相链接，但搜索引擎对**站内导航链接**（页脚、Resources 区块）的收录和排序，远不如对博客文章、热门仓库这类"外链多的内容"，所以纯搜索会系统性漏掉官方自己的导航图。

正确顺序：
1. 从已知的主文档域名出发，专门去读它的**首页/页脚/Resources 区块**（不是正文内容，是导航结构）
2. 每发现一个新的官方域名，重复步骤 1，直到不再冒出新域名（收敛）
3. 走完官方属性地图之后，才去开放网络搜第三方信源——顺序反过来会漏官方自己的东西

以后每次已经在读某个官方域名的任意页面时，顺手扫一眼页脚/导航，很可能免费换来 2-3 个新数据源。

### 2. 社交账号发现和排名：优先用 Grok CLI 深度搜索，而不是关键词搜索引擎

X/Twitter 之类的平台无法直接 WebFetch（未登录会被 402 拦截），普通搜索引擎摘要也给不出准确的简介原文、认证状态、近期互动数据——这些恰好是判断"一个账号值不值得关注"最关键的信息。**Grok 有 X 的原生搜索和实时数据访问权限，是我们工具链里唯一能真正做到"深度搜 X + 按互动数据排名"的工具**，应该作为发现和排名社交账号的首选，而不是关键词搜索的退而求其次选项。

标准做法：

```bash
script -q /dev/null grok -p "深度搜索 X 给我值得关注的 <tool> 工具使用的 X 账号，并做排名说明理由" 2>&1
```

好的排名结果通常会自带：
- **分层**（如 官方一手信息源 / 高价值补充 / 内容要过滤广告推销的 / 明确不建议跟的高粉营销号）
- **排名依据**（是否一手信息、是否讲真实用法而非泛泛技巧、更新是否跟得上版本、推销比例）
- **具体证据**（近期具体帖子的互动数据，而不是泛泛的"粉丝多"）

拿到结果后仍然要核实：
1. 结果里明确给出的账号 URL，逐条确认账号确实存在（Grok 也是 LLM，账号名有虚构可能，但因为它有实时 X 检索能力，出错率远低于普通网页搜索）
2. 公司账号/产品账号的官方身份，优先找**官方渠道自己链接过**或**员工亲自发文宣布**这类交叉证据（比如某条推文里团队成员亲自说"我们推出 XXX 作为官方渠道"）
3. 排名和评价本身是 Grok 的综合判断，不是我们逐条验证过的事实——收录时要在数据源清单里注明"整理自 Grok 深度搜索"，让后来者知道这是二手判断而不是一手核实，需要时可以自己复核
4. 粉丝数、浏览量这类数字会很快过时，收录时尽量只记录能长期成立的**定性判断**（这个人是不是在写代码/定产品），不要把某条推文的精确浏览量写进长期文档

如果 Grok CLI 不可用（没有 TTY 环境），退回关键词搜索时：
- 官方渠道（文档页脚、官方博客文章）**自己链接过**这个账号，比搜索结果标题可信
- 从已确认的负责人/公司账号出发，看他们经常互动、转发、置顶的对象（图扩展，比泛关键词搜索更容易找到不自称"core developer"的人）
- 看官方 GitHub org 的 public member 列表、官方博客/发布说明的署名或致谢名单
- 都找不到就诚实放进「待核实」，不要凭搜索结果标题猜

## 条目格式

每条数据源按这个格式记录，字段不要省略：

```
- **[名称](URL)** — 一句话说明它是什么/为什么权威
  - 建议访问方式：<用哪个工具读，如 web-reader 全文读取 / web-search-prime 搜索 / zread 读源码 / Grok CLI 搜索 / 需要人工浏览（没有对应 MCP 时如实写）>
  - 最后核实：YYYY-MM-DD
```

「最后核实」字段是这份清单能长期可信的关键——每次用到某条数据源时顺手看一眼日期，超过 3-6 个月没核实过的，用之前先花一分钟确认链接还活着、账号还在更新。

## 官方 / 核心团队社交账号

<按四个层级系统性搜索，不要只搜到一个就停：
1. **公司账号**（如 @AnthropicAI）— 覆盖全部产品线的公司级账号
2. **产品账号**（如 @ClaudeDevs）— 专门给这个工具/产品的更新账号
3. **负责人个人账号**（如 @bcherny）— 创始人/负责人，偏战略和产品方向
4. **核心开发者个人账号**（如 @trq212）— 具体参与开发的工程师，偏实战技巧和实现细节
每条都要写清楚属于哪个层级、身份是怎么核实的>
