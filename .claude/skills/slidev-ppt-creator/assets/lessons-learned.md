# 实战踩坑记录 (Lessons Learned)

来自一次真实技术分享修订中反复出现的问题。这里只记录**具体案例**，抽象规则见 `patterns.md` 的检查清单——这份文件是给"为什么会有那条规则"提供证据，读不懂规则动机时回来翻这里。

## 1. 生造词 / 语域打架的标题

**案例**：`# 贴 AI vs 零基再造`

- "贴 AI" 是活的口语比喻（还行），"零基再造" 是从"零基预算"嫁接来的商业黑话（也还行），但两个词**从没被同一个人在同一句话里说过**，拼在一起读起来就是卡。
- 第一次"修复"变成 `# AI 是贴上去，还是重新设计流程？`——语法上更糟：前半句 AI 是被动的（被贴上去），后半句 AI 又隐身成了主动的设计者，主宾关系不一致。
- 第二次"修复"变成 `# 旧流程贴一层 AI，还是干脆重新设计？`——"贴一层 AI"是我编出来的，中文里没人这么说。
- **最终修复**：`# 旧流程套个 AI 壳，还是干脆重新设计？`——"套壳"是中文技术圈本来就通用的词（"AI 套壳应用"），不是编的，两半句共享同一个主语"旧流程"，语法也顺。

**教训**：写比喻/俚语类短语时，只能用**真实存在**的说法，拿不准就搜一下这个词在中文语境里是否真被人这么用过；不要因为"听起来像那么回事"就自己拼一个。改完之后自己读一遍出声，卡顿的地方大概率有问题。

## 2. 讲者调度信息泄漏到观众可见区域

**案例**：`::: tip 台上主线` 块和一行裸文本 `讲者 **45 分钟轨整段可跳**；会后自学 / 投影闪过`，都不在 `<!-- -->` 注释里，导致投影时观众直接看到"这页可以跳过""引子已经立好样板"这类给讲者自己看的调度笔记。

**根因**：Slidev 里只有 `<!-- -->` HTML 注释是隐藏的演讲者备注；`::: tip`、普通段落、任何 markdown 文本都会原样渲染给观众。写"这段口播多长""这页台上跳过""深挖哪两个样板"这类元信息时，必须确认它被完整包在注释块里。

**教训**：生成完一页后，检查里面每一处"关于这场演讲本身"的调度性文字（时长、跳过、深挖、口播时长标注）是不是全部在 `<!-- -->` 内，一个字都不能漏到外面。

## 3. 同一概念全篇用了三个不同的词

**案例**：飞轮第④步"迭代→复用下次直接用"这个概念，组件 `EfficiencyFlywheel.vue` 里叫"迭代复用"，`03.playbook.md` 一张表里单列一行叫"复用"，`04.practice.md` 的路径 A 表叫"复利"，路径 B 表叫"复制"——四个地方三个词，还有的有编号有的没编号。

**根因**：改名一个核心术语时只改了"正在看的那一页"，没有跨文件 grep 这个概念的所有旧称呼。这类不一致比错别字更隐蔽——每处单独看都通顺，观众对照着看才会发现"这到底是几个东西"。

**教训**：重新定义/改名任何一个反复出现的术语或组件默认值后，**立刻全仓库搜索旧词**（包括各页面正文、小结、speaker notes、组件默认参数），一次性同步完再继续。

## 4. 断章引用：页面删了，别处还在指它

**案例**：`目标与非目标`、`核心论断`（公式页）、`与前两期如何衔接` 几页被整页删除后：
- 另一页的演讲者备注里还写着"点 4 后进入核心论断"——那页已经不存在了。
- `05.QA.md` 结尾的"常见引导"备注失去了"有人追问协议源码/框架对比怎么答"的台词——这个预案原本长在被删掉的那页里，没人把它搬到还活着的安全网页面。

**教训**：删除或重命名任何一页前，先搜索这个标题/内容在全项目范围内还被谁引用（其他文件正文、speaker notes、README 时间盒说明）。如果某页承担了"给讲者一个应对预案"这类功能性角色，删页时要把这个功能迁移到别处，不能连功能一起删掉。

## 5. 动态拼接 Tailwind 类名不生效

**案例**：

```vue
<!-- ❌ 不会生成对应样式 -->
:class="`border-blue-${100 + stage.id * 50} bg-blue-50/${40 + stage.id * 15}`"
```

Tailwind 用静态扫描找源码里出现过的完整类名字符串来决定生成哪些 CSS；插值拼出来的类名在源码里从未以完整字符串形式出现过，扫描器看不到，样式不会生成，渲染出来是空的。

**修复**：给每条数据预置一个完整的字面量类名字段：

```js
const stages = [
  { id: 1, cls: 'border-blue-100 bg-blue-50/40' },
  { id: 2, cls: 'border-blue-200 bg-blue-50/60' },
  // ...
]
```

```vue
<!-- ✅ -->
:class="stage.cls"
```

**教训**：任何"用循环变量算出一个颜色深浅"的写法都要停下来检查——Tailwind 类名必须以完整字符串形式存在于源码里，不能靠运行时拼接。

## 6. 密度调整靠来回试错，反复过冲

**案例**：一个信息密集的自定义组件（协作矩阵）经历了"太挤 → 加大间距/字号 → 溢出黑边 → 再改回去"三轮返工，每次只凭上一张截图的观感调整数值，没有对"这页大概能放多少内容"有一个数量级的预判。

**教训**：
- 先判断内容量级别——超过 3~4 个独立信息块/表格，默认假设**放不进默认字号+间距**，直接规划"拆页"或"做紧凑组件"，不要等溢出了再补救。
- 做紧凑组件时，先估算一个大致的高度预算（标题区 + N 个区块 + 收尾条，每块留多少 px），而不是从大字号开始试。
- 内容优先级要分清楚"核心信息"和"锦上添花"——遇到空间不够，先砍最边缘的（如本例里的"落地示例"命令清单，本来就在演讲者备注里完整讲过，视觉上删掉不损失信息），而不是把所有区块的字号一起往小调。

## 7. 事实核查：训练数据 / 二手摘要不可靠

**案例**：
- 起初判断 nn-ai 的 `/bugfix` 技能"只存在于聊天记录草稿里、没有实现"——因为只查了 nn-ai 主仓库；后来用户指出它其实是另一个项目仓库（`nn-client-all`）里当天刚提交的真实功能，做得非常扎实。
- 差点把 Claude Code 专属的 `/goal` 命令写成 Codex CLI 也有的功能——某次搜索引擎摘要把两个产品的功能混在一起总结，不查官方 changelog 原文根本发现不了。

**教训**：
- 涉及具体产品功能/命令的表述，**必须核对官方文档或源码，不能只信搜索引擎的摘要**（摘要经常混淆不同产品）。
- 用户给的背景资料（如 `purpose.md` 里"先做了 A 再接入 B"这类历史描述）本身可能不准确或不完整，能查 git log / 代码库的都应该查一遍再写进 PPT——查完可能发现比描述里写的更真实、更有说服力，也可能发现某些是尚未实现的规划，两种情况都要如实反映在最终表述里，不能照抄了事。
