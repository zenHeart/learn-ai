# 章节模板

每章都必须遵守目标仓库的 `book/AGENTS.md`。本文档记录 `deep-tech-author` 默认使用的 N.1-N.8 骨架；如果目标仓有更严格的规则，以目标仓为准。

## 标准骨架

````markdown
# N. 章节标题

> 前置知识：第 X 章、第 Y 章
> 本章覆盖：[1-2 句核心主题]。不覆盖：[明确说清楚不写什么]
> 关键术语：[本章首次出现、读者必须先建立的 2-5 个术语，一句话定义]

[2-3 句过渡：第 N-1 章我们构建了 X，现在我们需要 Y，因为...]

## N.1 它解决什么系统问题

- 用具体场景说明没有这个模块会有什么成本、风险或能力缺口。
- 给出 1-2 个修辞性问题，答案就是本章要揭示的核心。
- 若机制有清晰层次或边界，先给结构总览图建立心智模型。

## N.2 用户视角完整流程

- 给出一个 10-50 行、完整可运行的最小示例。
- 串起从用户操作到系统响应的完整路径。
- 路径较长时配数据流图，并标注链路阶段。

## N.3 机制拆解

每个核心子机制对应一个 `### N.3.p` H3，按以下模板写：

**设计目标**：[一句话说清楚这个子机制要达成什么]

**朴素实现**：
```typescript
// 01-xx  [只处理成功路径的简化版本]
```
[前面加一句：这里先做最简实现，保证能跑]

**逐行剖析**：
[逐行解释关键逻辑，精确到行号，例如“第 03 行中，我们...”]

**边界与缺陷**：
[朴素版本在什么具体输入/条件下失败，给出真实错误输出]

**改进实现**：
```typescript
// 01-xx  [新增/修改的行标注 // 新增]
```
[前面加一句：为了让 X 成立，我们需要...]

**改进剖析**：
[解释新增部分解决了什么问题，改变了什么假设。若新增了暂时用不到、后面才用的字段或分支，明确写出“这里多留一个 X，N.3.q 节会用到”。]

[如有多轮迭代，重复朴素 -> 边界 -> 改进；每 2-3 轮给一个“当前完整状态快照”，即完整可运行代码块。]

### N.3.1 [子机制 A]
### N.3.2 [子机制 B]

## N.4 源码映射

| 文件 | 责任 | 输入 | 输出 | 裁决边界 |
|------|------|------|------|----------|
| [agent.ts#Lx](<src>/agent.ts#Lx) | ... | ... | ... | ... |

“裁决边界”列说明该文件在链路中决定什么、不决定什么。
源码路径使用仓库相对路径，如 `<src>/...#Lx`；正文不要手写 GitHub URL。

## N.5 设计不变量与权衡

- 无论实现如何变化，哪些约束永远成立。
- 每个关键设计决策都要追到外部权威：规范/协议条款、浏览器或硬件 bug、语言或工具约束、不变的工程原理。
- 至少列出 2 个被拒绝的替代方案及其代价。
- 区分可迁移的通用原则和本项目的产品选择。

## N.6 常见误解与失败模式

- 读者最可能产生的 3-5 个误解及纠正。
- 生产环境常见失败场景及根因，不只写“不要这样做”。

## N.7 本章训练

### N.7.1 使用级
[操作练习：熟悉 API 和配置]

### N.7.2 原理级（最小复刻）
[实现 200 行以内的最小可运行版本，覆盖核心机制，并给出从零搭起的脚手架指引]

### N.7.3 扩展级
[添加生产级能力：错误处理、性能优化、安全边界；有明确验收标准]

## N.8 总结

[按小节顺序，每节 2-4 句核心要点]
[最后一句连接到下一章]
````

## 格式规则

- H1: `# N. 标题`
- H2: `## N.m 标题`
- H3: `### N.m.p 标题`
- 源码链接：`[file.ts#Lx](<src>/.../file.ts#Lx)`，不要把链接包在反引号中。
- 正文不要手写 GitHub URL；EPUB 构建会根据 `metadata.yaml` 转换仓库相对源码链接。
- 同一章内不要混用编号标题和裸标题。
