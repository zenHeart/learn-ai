# Agent 交付闭环：把补丁与迁移类任务做成可编排、可验证的流程

## 0. 三十秒判断：值不值得抄

原文把难点说得很准："难点不在于“能不能生成一段修改”，而在于：**能否让一次补丁交付具备可追踪的过程、可验证的结果和可持续优化的机制。**"

这篇真正可以照做的只有一件事：**别让 Agent 直接吐补丁，先给它一个「状态 → 判断 → 执行 → 门禁 → 回检」的流水线。** 下面 5 张卡就是这条流水线拆开的，每张都能单独上。

两个必须先说清楚的前提：

1. **原文正文的「阶段性实践效果」一节里没有任何数字**，只有一张配图。所以这篇不能当作「AI 能提效多少」的通用依据，只能当工程结构参考。
2. **场景高度特化**：内核补丁交付（上游 patch 回合到下游分支）。原文自己给了外推边界——"这套方法同样适用于 SDK 大版本升级、跨分支移植、fork 同步等代码迁移场景。"也就是说你手上得有一类「重复、证据充分、结果可验证」的迁移任务，纯新功能开发不在适用范围内。

## 卡 1｜失败任务自动分流：快筛 + 精判

**要解决的问题**
"一次合入失败可能是依赖缺失、上下文变化或真实代码冲突。人工先判断“值不值得修、能不能修”，本身就消耗大量时间。"——大量同构失败任务下，「判断本身」比「修复本身」更费人。

**具体做法**

| 步骤 | 动作 | 关键设计 |
| --- | --- | --- |
| 1. 规则层打分 | 用启发式规则评估四个维度：冲突规模、缺失符号、危险变更、补丁复杂度 | 规则先筛，成本≈0 |
| 2. 分三档 | 明确可修 / 模糊区间 / 高风险 | 阈值来自回放历史失败样本，不是拍脑袋 |
| 3. 模糊区间才进 LLM | "仅将处于模糊区间的任务交由 LLM 进一步判断" | 原文："先以启发式规则快速评估，再仅对模糊任务调用 LLM 精判" |
| 4. 强制升级出口 | 高风险改动直接转人工，Agent 不再往下走 | 原文："自动化不是无边界自治。" |
| 5. 落库分流理由 | 记录判定依据，供后续调阈值 | 分流本身也是可优化对象 |

"这样形成“快筛 + 精判”的双层漏斗：明确任务快速推进，复杂任务再投入深度分析。"

**前置条件**
- 有机器可读的合入日志（`git apply` / `rebase` / `merge` 的原始输出），不能只有一句「合并失败」。
- 有历史失败样本能用来回放定阈值。
- 有一条明确的人工升级通道（有归属人、有 SLA），否则「升级」= 丢任务。

**适用边界**
- 任务量大、同构、输入明确（原文方法论第一条："优先选择日志、代码、任务状态等输入明确的场景，而不是一开始追求全自动决策。"）。
- 不适合：一次性新功能、探索性重构、低频长尾任务——这些直接人工做更快。

**反例 / 失败模式**
- 阈值靠感觉定 → 危险改动被塞进自动通道，出事才知道。
- 只做规则不留升级出口 → 规则失效时任务静默卡住。
- LLM 判定结果不落库 → 无法复盘，阈值永远调不准。

**可验证效果指标**
- 自动处理占比、人工升级率、**误升级率**（升级后人工发现本可自动的比例）。
- 单任务的前置判断耗时（规则层应≈0）。

**原文**
"PatchPilot 先以启发式规则快速评估冲突规模、缺失符号、危险变更和补丁复杂度；仅将处于模糊区间的任务交由 LLM 进一步判断。"
"证据充分且风险可控的任务自动处理；不确定或高风险任务升级工程师"

## 卡 2｜State-First 依赖分析：别只找缺失符号

**要解决的问题**
上游补丁回合失败，表面是冲突，真实原因常常是「这段代码已经不是你记忆里的样子」："失败原因往往不是单一的 Git 冲突：同一函数可能已被重构，结构体字段或函数签名可能已演化，修复所依赖的前置提交也可能尚未进入目标分支。"

**具体做法**

1. **意图分析先收窄范围**：补丁想干什么，决定看哪几个文件/函数，而不是全仓扫。
2. **以「状态偏离」为线索**，而不是以「缺失符号」为线索：函数实现、结构体字段、函数签名三类演化都要进判断。原文："仅找缺失符号会遗漏代码演化造成的真实冲突"、"以“代码状态偏离”而非单纯缺失符号为线索追踪依赖：函数实现、结构体字段和函数签名的演化都会纳入判断。"
3. **依赖只从 Git 事实里选**：先用 Git 命令枚举候选 commit（`git log -S` / `git log --oneline <tag>..<branch>` / `git show`），模型只做选择，不做编造。原文："要求通过 Git 命令枚举 commit SHA，以工具输出作为事实依据"。
4. **递归但有上限**：定位必要前置提交要递归，递归深度/时间窗要设上限，否则会一路拉到不相关提交。原文给的反面是"避免只按缺失符号补丁、导致依赖链膨胀"。

**前置条件**
- 仓库有完整历史（没被 squash / 单次导入过）。
- 符号级搜索与 `git log -S` 可用。
- 能定义「什么算同一个符号的重构」——这是脏活，先人工标一批样本。

**适用边界**
- 适用：patch 回合、fork 同步、跨分支移植、大版本升级。
- 不适用：无历史的仓库、只有二进制产物的仓库、单文件微调。
- 大仓先做范围收窄，否则状态偏离本身就会超时。

**反例 / 失败模式**
- 直接问模型「需要哪个前置提交」→ 它会编一个看起来很像的 SHA。原文点名了这个坑："依赖提交必须由 Git 工具精确枚举，避免模型凭直觉补全不存在的前置变更。"
- 只做符号级搜索、不看签名/字段演化 → 补丁能编译但行为变了。
- 递归无上限 → 依赖链膨胀，合出来的 diff 大到没人敢 review。

**可验证效果指标**
- 引入的无关提交数 / 有效依赖提交数（比值越低越好）。
- 首轮解冲突成功率、平均重试轮次。
- 单个补丁最终 diff 行数中「非必要变更」占比。

**原文**
"结合补丁意图、代码状态和前置提交，递归识别必要依赖"
"比较函数、结构体和签名的状态偏离，再定位必要前置提交"

## 卡 3｜结构化失败记忆：让 Agent 不要重复走死路

**要解决的问题**
多 Agent / 多轮重试最容易浪费的地方：第二轮干了和第一轮一样的事。原文给的原因——多轮尝试容易重复走进同一条死路。

**具体做法**

1. **每轮落一条结构化记录**（不是自由文本日志），固定三字段：`处理方案` / `失败原因` / `改动范围`。
2. **重试前强制读这份记忆**，并且要求本轮方案与记忆中的方案有差异，否则不允许提交。
3. **先对齐补丁意图再动手**：原文"解决 Git 冲突不等于保留了原补丁意图。AI 可能产生残留冲突标记、遗漏关键改动，甚至生成上游不存在的代码。"——解冲突前先复述「原补丁想做什么」。
4. **改动范围只记摘要 + 文件列表**，不要贴全量 diff，否则记忆本身会撑爆上下文。

**前置条件**
- 任务状态可持久化（不能只活在一次会话里）。
- 有一个固定的记忆文件/表，按 task_id 归档。
- 迭代过程本身能被脚本包裹（否则「每轮都记」靠自觉必然漏）。

**适用边界**
- 适用：需要 ≥2 轮重试的任务（真·复杂回合）。
- 不适合：一次就过的任务，写记忆是纯开销。
- 记忆需要定期清理/归档，否则检索不到有效历史。

**反例 / 失败模式**
- 记忆写成自然语言流水账 → 检索不到「已经试过什么」。
- 重试不读记忆 → 原地打转，且看起来在「努力」。
- `改动范围` 记全量 diff → token 成本失控。
- 只记失败不记成功方案 → 丢掉可复用路径。

**可验证效果指标**
- 平均重试轮次、**重复失败率**（相同失败原因重复出现的比例）。
- 单轮 token / 调用成本。
- 记忆命中后本轮方案变化率（应≈100%）。

**原文**
"Agent 的每一轮尝试都会记录处理方案、失败原因和改动范围；后续重试带着这些结构化记忆继续，而不是重复同一条无效路径。"
"保存方案、失败原因和改动范围，驱动下一轮差异化尝试"

## 卡 4｜质量门禁三件套：能合入 ≠ 可交付

**要解决的问题**
回合成功、PR 成功之后仍然可能交付失败。"一次回合成功后，仍可能在 PR、检测轮次或后续链路中失败。只统计“命令执行成功”会高估自动化价值。"

**具体做法**

按顺序跑三层检查，每层都有可机器判定的输出：

| 层 | 检查什么 | 最小实现 |
| --- | --- | --- |
| L1 冲突残留 | 残留冲突标记、空白/行尾破损 | `grep -n '<<<<<<<\|=======\|>>>>>>>'` + `git diff --check` |
| L2 代码漂移 | 生成物偏离基线或上游意图 | 与基线 branch 的 diff 审查 / 结构化 diff 统计 |
| L3 语义偏差 | 行为不等价（最贵，放在最后） | 编译 + 现有测试；没有测试就人工抽检 |

- 原文："执行后依次检查冲突残留、代码漂移与语义偏差。"
- 每层都要定义**不通过时的去向**（重试 / 转人工），这就是原文说的门禁："对每个自动化动作定义可验证的结果与人工升级条件。"
- 门禁不过不许静默通过。原文："不把“能合入”误判为“可交付”"

**前置条件**
- CI 能编译、能跑测试（哪怕只有 smoke test）。
- 有一条基线可比对（目标分支 / 上游 tag）。
- 门禁规则与升级条件写进仓库，而不是记在某个人的脑子里。

**适用边界**
- 三层里 L1、L2 可以完全自动化；L3 在没有测试的仓库里只能降级为人工抽检——这时候不要假装自动。
- 门禁不是越多越好，超过 ~5 条以后没人愿意看。

**反例 / 失败模式**
- 只检查命令返回码 → 这正是原文反对的。
- 门禁不过但不升级 → 静默通过，问题一路漏到线上。
- 阈值调到「刚好能过」→ 门禁形式化，指标好看但缺陷没少。
- 把语义偏差交给模型自查 → 自己批自己的卷子。

**可验证效果指标**
- 门禁拦截率（拦下 / 提交总次数）。
- 拦截后的人工返工率（拦截是否真拦住了问题，还是噪音）。
- 逃逸到 PR / 上线后的缺陷率。

**原文**
"检查残留冲突标记、代码漂移和语义偏差"
"每一个自动化结论都能对应到任务状态、Git 事实或质量检查结果。"

## 卡 5｜以端到端交付定义成功 + 持久化任务状态

**要解决的问题**
两个坑：一是只统计「命令执行成功」，二是任务在异常中断后无声消失。第二种更贵，因为它不可见。

**具体做法**

1. **建一条任务状态链**：入队 → 分析 → 执行 → 检测轮次 → PR → 合入。原文："任务从入队到 PR 合入的状态被连续记录"。
2. **回合成功后不结束，进入回检**：自动创建检测轮次、回检 PR 与交付状态。原文："回合成功后自动创建检测轮次、回检 PR 与交付状态，并将任务、日志、审查结论和最终产物统一关联。"
3. **持久化状态负责恢复与重排**：中断、超时、异常时基于持久化状态恢复或重新调度，"而不是把任务留在不可见的中间状态"。
4. **运行保障三件套**：去重、调度恢复、超时处置。原文："PatchPilot 将任务状态、执行产物和审查结果持续沉淀；通过去重、调度恢复和超时处置，避免重复执行、异常中断或任务遗漏影响整体交付节奏。"
5. **换掉 KPI**：原文："PatchPilot 以“是否完成交付”而非“是否完成一次执行”衡量效果。"

**前置条件**
- 有可查询的任务存储（Issue / PR / 一张表都行）。
- 有明确的超时阈值和恢复入口（谁来捞、什么时候捞）。
- 任务有唯一 ID，产物、日志、审查结论都挂在 ID 上。

**适用边界**
- 适用：每周几十个以上重复任务、多人/多 worker 并行。
- 不适合：一天跑不到 10 个任务时，一张表就够了，别上调度器。
- 多 worker 并行时，去重不是优化项而是必需项。

**反例 / 失败模式**
- 用「一次执行成功率」当团队 KPI → 报表漂亮，交付周期没变。
- 中断后不恢复也不告警 → 任务烂在队列里，没人知道。
- 同一补丁被两个 worker 同时处理 → 冲突加倍。
- 状态写在会话上下文里 → 进程一重启全丢。

**可验证效果指标**
- 端到端交付率（入队 → 合入）。
- 任务吞吐（每周完成数）、失败可见性（卡住任务的平均滞留时长）。
- 超时 / 丢失任务数、返工率。
- 原文给的完整观察清单："同时观察效率、成本、交付率、人工升级率和返工率，避免只看单点成功率。"

**原文**
"调度侧以持久化任务状态管理执行与恢复，使异常中断不会让任务悄然丢失。"
"系统的优化对象不仅是“单次解冲突是否成功”，还包括任务吞吐、失败可见性和交付链路的稳定性。"

## 3. 哪些是阿里云的主张，哪些是你能自己复现的

| 条目 | 性质 | 说明 |
| --- | --- | --- |
| 多阶段工作流 + 每阶段明确输入/产出/状态 | **主张**（设计取向） | 无平台依赖，任何仓库都能搭 |
| 快筛 + 精判双层漏斗 | **主张 + 可复现** | 规则层几十行代码即可 |
| State-First 依赖分析 | **可复现** | 全靠 Git 原生命令 |
| 工具约束推理（枚举 commit SHA） | **可复现** | Agent 强制走工具调用即可 |
| 结构化失败记忆 | **可复现** | 一个文件或一张表 |
| 质量门禁三件套 | **可复现** | grep + diff + CI |
| 持久化任务状态 / 恢复 / 去重 / 超时 | **可复现，但需要最小任务系统** | 一个人做要先砍到只剩状态表 |
| 价值来自「轻量规则 + 昂贵推理 + 质量校验 + 调度回检」四层组合 | **主张（无对照实验）** | 原文没给分层消融数据，不能当成因果结论 |
| 第 4 节的效果数字 | **内部数据** | 见下节，只有配图、无口径定义 |

原文自己的排序也值得抄："先建立工作流，再引入 Agent。"——理由是"没有状态、上下文和回检的 Agent，难以在生产工程中稳定运行。"

## 4. 内部数据（配图口径，务必带 caveat 使用）

## 5. 一人公司 / 小团队降级版

原文整套东西假设了「多内核版本 + 大批量补丁」。一个人手上通常只有几十个任务，照抄会过度工程。降级原则：**保留状态与门禁，砍掉调度与自动分流。**

| 卡 | 小团队做法 | 最小工具 | 明确放弃 |
| --- | --- | --- | --- |
| 卡 1 分流 | 5 条 checklist 人工打分（冲突行数 / 触及公共 API / 改签名或结构体 / 跨版本 / 补丁规模），只有灰区才问一次 LLM；结果写进 issue 标签 | Issue 标签 + 一个固定 prompt | 自动分流、阈值自学习 |
| 卡 2 依赖分析 | 手工导一份「状态偏离清单」（`git log -S'<符号>'` + `git diff <tag>..<branch>` 关键文件），让 Agent 只从清单里选前置提交 | 一个 JSON 清单文件 | 递归自动定位 |
| 卡 3 失败记忆 | 仓库内 `.agents/failure-log.md`，每轮追加 `方案 / 失败原因 / 改动范围` 三行；重试前先读 | 一个 Markdown 文件 | 自动检索、记忆清理 |
| 卡 4 质量门禁 | 冲突标记 grep + `git diff --check` + 跑一次测试；语义偏差 100% 人工过 | 三条命令 + 现有 CI | 自动语义审查 |
| 卡 5 端到端度量 | 一张状态表（queued / in-progress / blocked / merged），卡住 >24h 手动提醒；只留 4 个指标：交付率、人工升级率、返工率、单任务耗时 | 一张表格 + 定时提醒 | 自动恢复、自动重排、去重服务 |

**一人公司推荐顺序**（先做能被验证的，最后做最贵的）：

1. 第 1 周：状态表 + 回检（卡 5 的最小版）——先让你能看见任务。
2. 第 2 周：质量门禁（卡 4 的 L1/L2）——最便宜、收益最直接。
3. 第 3 周：失败记忆（卡 3）——重试次数一多就回本。
4. 之后：依赖分析（卡 2）、分流（卡 1）——只有任务量真的上来了才值得。

配套一句原文，正好是上面顺序的理由："从高频、证据充分的问题开始。"（原文方法论第一条；同条正文为"优先选择日志、代码、任务状态等输入明确的场景，而不是一开始追求全自动决策。"）
