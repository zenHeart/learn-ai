## 0. 阅读约定

- **【可复现】**：不依赖阿里云产品，你今天在自己的仓库里就能做，并且能量出效果。
- **【阿里云主张】**：阿里云团队在书中的判断、内部数据或参考实现，采纳前要按自己的负载复测。
- **【外部案例】**：书中引用的公开论文/厂商实践（Anthropic、Qoder Cloud Agent、百炼、RocketMQ LiteTopic 等），属于可借鉴的第三方材料，不是阿里云结论。
- **【需按版本核验】**：书中以特定协议版本或产品提交为基线的结论，随版本会变。

术语约定（全书统一）：**Task** = 异步执行的最小业务单元，有独立标识与业务状态；**Session** = 一段交互/执行上下文；**Task Run** = Task 的一次实际执行；**Artifact** = 可寻址、可交付的成果；**Sandbox** = 按任务分配、有隔离边界的执行环境；**Harness** = 编排层（持有目标、上下文与下一步决策）；**Runtime** = 执行生命周期与资源；**Gateway** = 入口治理点。**Task 与 Session 是业务关联关系，不等于同一进程**（ch10）。

## 1. A 组：任务语义与异步（ch10）

### 卡1 把"执行结束"和"业务完成"分成两层

- **要解决的问题**：模型说"完成了"、HTTP 200、流程跑完，被当成业务成功。
- **做法**：把一次任务的结论拆成五类信息并分别落库——① 执行状态（running/succeeded/failed/killed）；② 节点运维状态（Worker 是否在线、租约是否有效）；③ 候选证据（日志、Trace、快照、Artifact、LLM 原始响应）；④ Evidence（被成功标准明确引用、可核验来源的证据）；⑤ Outcome（业务应用或获授权 Verifier 依成功标准做出的判定）。运维动作（如"强制标记成功"）只改执行状态并留审计（谁、何时、原因、原状态、新状态）。
- **前置条件**：任务有稳定 ID；有可写的状态存储；能区分"人读的材料"和"可判定的证据"。
- **适用边界**：任何有验收标准的任务；纯一次性问答可以不建完整五层，但至少要把"执行成功"和"结果被采纳"分开记。
- **反例 / 失败模式**：用 LLM 评分直接当业务结论；把 `succeeded` 直接映射为"客户已收到通知"；审计只留"放行"不留最终执行结果。
- **可验证指标**：Outcome 可追溯率（能回溯到 Evidence 的任务 / 全部判定任务）；误判率（人工复核推翻的 Outcome 占比）；审计字段完整率（who/when/reason/from/to 齐全的强制操作占比）。
- **一人 / 小团队降级**：一张 `runs` 表（`task_id, status, evidence_url, verified_by, verified_at`），人工"验收"只改 `verified_*` 字段，不改 `status`。
- **原文引用**（ch10）：「LLM-as-a-Judge 是 Evaluation 的一种实现方式，不是 Outcome 的天然权威」「运维侧的"强制标记成功"操作只能在获授权范围内改变执行状态，并留下完整审计记录」「它不能跨越层级直接判定 Outcome」。

### 卡2 异步任务：解耦执行生命周期与请求生命周期

- **要解决的问题**：同步请求—响应在长任务上必然超时；进程在等待外部事件期间空占资源。
- **做法**：
  1. 客户端提交任务 → 拿到可靠接收确认与 **Task ID**，请求即返回；
  2. 后台队列按优先级 + FIFO 排序，调度器取任务、租给 Worker、维护租约；
  3. 状态机维护合法转换：`waiting → queued → running → succeeded/failed/killed`，`hold` 表示等待审批或外部条件；
  4. 状态持久化到数据库（内存缓存只加速高频查询），数据库是 Task State 的权威源；
  5. 状态通知用"回调为主 + 租约/轮询兜底 + 共享存储做权威持久化"组合。
- **前置条件**：任务属性显式化（成功标准、重试策略、超时时间、优先级、关联 Session）；有可查询的任务入口。
- **适用边界**：超过网关超时、含外部等待或人工介入的任务；几十秒内可完成的调用不要上队列。
- **反例 / 失败模式**：把"超时"当作"执行已停止"；把队列深度监控丢掉直到积压才发现；用内存存状态导致进程重启即丢。
- **可验证指标**：队列深度与**最老任务等待时长**；端到端完成率；`unknown` 状态占比（进入对账的比率）。
- **一人 / 小团队降级**：`cron` + SQLite/JSON 状态文件即可实现同样的语义分层；Task ID 用日期 + 序号；"权威源"就是那个文件。
- **原文引用**（ch10）：「请求超时只能表示调用方未在期限内取得结果，不能证明执行已经停止」「生产环境通常以数据库为主存储、内存缓存加速高频查询，并把数据库视为 Task State 的权威源」「队列深度本身是核心可观测指标」「背压的本质是让消费速率自适应执行速率，避免过载崩溃」。

### 卡3 Checkpoint 不等于幂等：把恢复责任写清楚

- **要解决的问题**：实例恢复后重复扣款、重复发消息、重复提交。
- **做法**：
  1. 在契约里写清 Checkpoint **保存什么、谁写、与业务状态/外部提交如何排序**；
  2. 区分两件事：**计算结果复用**（Checkpoint 已存在且版本匹配就跳过）与**外部副作用幂等**（另选幂等键、去重账本、事务性 outbox/inbox、租约与 fencing、对账补偿）；
  3. 外部调用可先写"调用意图"，执行后再写"调用结果"，让恢复时能判断是否已提交；
  4. 轮询/回调/Watch 只当**信号**，信号丢失后以权威 Task State 重新对账；
  5. 明确"不能保证恰好一次"时的边界（哪些操作可重放、哪些只能确认或补偿）。
- **前置条件**：业务操作有稳定唯一键或幂等键；外部系统至少可查询执行结果。
- **适用边界**：任何跨进程、跨天的任务；只读分析可以放宽。
- **反例 / 失败模式**：把 Checkpoint 当作"事务提交"的替身；靠调度器不重复投递来保证业务不重复；邮件、扣款这类操作试图用恢复检查点"撤销"。
- **可验证指标**：恢复后重复副作用条数（应为 0）；对账发现率与对账耗时；恢复后任务续行成功率。
- **一人 / 小团队降级**：外部写操作一律带 `idempotency_key = hash(task_id + step)`；恢复脚本先查"这个 key 写过没有"。
- **原文引用**（ch10）：「Checkpoint 必须明确"保存什么、由谁写入、与业务 State 和外部系统提交之间如何排序"，才能参与恢复语义」「轮询、回调、Watch 是状态变化信号，不是权威事实源」「外置调度系统不接管业务 State 权威」「根据交付语义选择幂等机制，不把任何一种写成通用必选项」。

### 卡4 定时任务：预授权触发 + 错过策略 + 并发上限

- **要解决的问题**：定时任务重复跑、漏跑、被工具调用轰炸后无人察觉。
- **做法**：
  1. 触发类型统一成"往队列投递一个 Task"（时间：Cron / ScheduledAt / FixedRate；事件：Webhook / MQ / 内部事件共用同一条执行链路）；
  2. 显式配置：并发上限（1 = 串行）、阻塞处理策略（排队 / 跳过 / 合并为最新一次）、**错过策略**（`run_latest` 只补最新一次 / `run_all` 全补跑 / `skip` 跳过 / `prompt` 挂起通知人工）、失败重试、超时；
  3. 明确时区与夏令时处理，用**调度 ID + 计划发生时间**标识同一次触发，去重靠这个组合而不是靠时间戳近似；
  4. 无人在场也要算账：预算维度扩到调用次数、执行时长、并发数、外部副作用次数、总费用。
- **前置条件**：任务有幂等能力（见卡3）；触发与执行路径分离，状态外置。
- **适用边界**：日报、周检、周期巡检；秒级高频轮询不要用定时任务，直接用流式/事件。
- **反例 / 失败模式**：多实例各自跑定时器导致重复执行（需分布式锁或 Leader 选举）；只写"失败重试 3 次"而不设并发上限；无人值守下死循环 Agent 在数小时内累积出非预期账单。
- **可验证指标**：同一次触发的重复执行率；错过触发的补跑决策正确率；单任务日成本与预算告警命中率。
- **一人 / 小团队降级**：系统 `crontab` + 一个 `runs` 表做触发去重（`(trigger_id, planned_at)` 唯一索引）；`prompt` 策略 = 发一条 Telegram/Slack 提醒给自己。
- **原文引用**（ch10）：「以调度ID与计划发生时间识别同一次触发」「死循环 Agent 在数小时内累积出非预期账单是真实风险」。

### 卡5 人在回路：挂起、重新准入、释放资源

- **要解决的问题**：审批等待期占着 Worker；审批通过后 Agent 用过期状态继续跑；审批回调被当成"必然放行"。
- **做法**：
  1. 任务进入 `hold` 状态时保存继续点与等待条件，然后**释放执行资源**（前提是恢复所需的最小集合已持久化）；
  2. 审批事件载荷必须带：Task ID、审批版本号、授权主体、决策结论；
  3. 接收方（Runtime 或调度器）据此重新投递前，逐项校验：事件未过期、未重复、与 Task 当前状态兼容；
  4. 等待期仍承担调度、状态存储、通知与可能保留环境的成本，要单独计入成本表；
  5. 审批授权链路由业务应用与 Verifier 定义，流程引擎只负责暂停/恢复协调。
- **前置条件**：审批请求有唯一 ID 与版本；等待条件可用结构化字段表达。
- **适用边界**：高风险写操作、资金动作、外发通知；只读查询不需要。
- **反例 / 失败模式**：把"审批通过 → 唤醒 Agent"画成一根没有标注接收方的箭头；超时自动降级为只读执行；恢复时沿用旧心跳/旧凭证直接写入。
- **可验证指标**：`hold` 平均时长与资源占用；审批后重新准入失败的拦截次数；审批事件重复投递被丢弃的比例。
- **一人 / 小团队降级**：不用队列，直接"写一个 `approvals` 表 + 一个后台轮询进程"；Agent 恢复后第一步总是重新读一次 Task 状态再动手。
- **原文引用**（ch10）：「把"审批通过 → 回调唤醒 Agent"画成一根没有标注接收方的箭头会掩盖这些必要校验」「Task 与 Session 按业务关联，资源和权限隔离由相应机制保证」。

## 2. B 组：执行环境与沙箱（ch7）

### 卡6 会话亲和 + 工作区挂载：两件独立的事

- **要解决的问题**：Agent "记不住上次做到哪"，或者工作区被别的实例覆盖。
- **做法**：
  1. **第一类映射**：逻辑会话 → 执行环境（稳定会话标识到达后查已有环境，或启动恢复流程）；
  2. **第二类映射**：任务身份 → 工作区（按已验证的租户/用户/项目关系挂载数据目录）；两者不必一一对应；
  3. 职责切分：源码、下载文件、中间制品在工作区；**任务目标、已完成步骤、待确认事项、外部操作结果属于任务事实，存状态库**；
  4. 恢复后由编排层重新确认进度，不能靠"文件还在"推断任务进度；
  5. 恢复检查未通过时保持"恢复失败/等待"状态，**不把空工作区当恢复成功**；任务状态与工作区的保留期独立于计算实例。
- **前置条件**：稳定会话标识；工作区归属在服务端校验；任务状态可持久化。
- **适用边界**：跨多轮的项目型任务（写代码、数据分析、长文档）；一次性查询不需要。
- **反例 / 失败模式**：目录名拼用户 ID 就当访问控制；只因 CPU 低就回收实例而成果只在实例内；把容器临时地址当长期入口。
- **可验证指标**：续行成功率（切换实例后从已有成果继续并完成的比例）；工作区挂载失败被正确阻断的比例；状态完整率（恢复后可核对出"已完成步骤"的任务比例）。
- **一人 / 小团队降级**：一个持久化项目目录 + `SESSION.md`（当前目标/进度/待办）随仓库提交；Agent 每次启动先读它。
- **原文引用**（ch7）：「仅把用户编号拼接到目录名中，并不能代替服务端对工作区归属及访问权限的检查」「任务目标、已完成步骤、待确认事项和外部操作结果构成任务事实，应由状态存储保存。」「恢复内存和磁盘之后，编排层仍需确认任务进度，避免重复提交操作或遗漏后续步骤」「检查未通过，实例应保持恢复失败或等待状态，不能将空工作区作为恢复结果交付」。

### 卡7 等待期成本用"状态分层"，而不是"保住进程"

- **要解决的问题**：长会话里 Agent 大部分时间在等，按秒计费的实例却一直在跑。
- **做法**：按等待时长选状态策略——持续运行 / 浅层暂停（保内存）/ 深度休眠（持久化状态、释放算力，恢复时重建外部连接）/ 只留文件重建进程；并结合**活跃时间占比**、等待时长、恢复频率、状态大小设休眠阈值与保留期限。
- **前置条件**：工作区与任务状态已外置（否则无法休眠，见卡6）。
- **适用边界**：等待可预测且长的任务（等审批、等外部数据）；高频短等待的反复保存/恢复反而更贵。
- **反例 / 失败模式**：以"接口返回成功"判定恢复完成；把某个 pause 接口等同于所有平台的同一种休眠；回收只看 CPU 使用率。
- **可验证指标**：**活跃时间占比** = 实际计算时间 ÷（等待 + 计算）；单位完成任务成本；恢复失败率；环境到期回收及时率。
- **一人 / 小团队降级**：没有平台就自己在流程里分叉——等待审批时把 Agent 进程 `kill` 掉，只留状态文件；事件到达后再起新进程读状态。
- **原文引用**（ch7）：「仅维持进程存活，无法完整承担这些责任」「接口返回成功只是其中一个环节」「CPU 使用率较低不能单独作为回收依据」。

### 卡8 围栏（Fencing）：让旧执行者真正失效

- **要解决的问题**：实例 A 失联被判死，新实例 B 接管，A 却复活继续写同一份状态或工作区。
- **做法**：
  1. 区分执行环境故障与依赖服务故障——存储不可用时反复重建实例无用；
  2. 用**执行代次**标识接管前后，写入路径校验代次，旧代次的提交被拒（文件句柄场景用独占挂载或私有分支 + 只允许当前持有者发布新版本）；
  3. 对已提交给外部系统的操作，恢复时按原操作标识查询结果再决定等待/读结果/重试；
  4. 只有任务能从已有成果继续推进，才算恢复完成。
- **前置条件**：写入入口可控（可校验代次或可做成"发布者"）；外部操作可查询。
- **适用边界**：同一任务/工作区存在并发写入者时；纯只读分析可放宽。
- **反例 / 失败模式**：只更新任务表里的租约编号；靠心跳判断旧实例已停；快照回滚被误当成撤销外部副作用。
- **可验证指标**：旧代次写入被拒次数（应 > 0，说明围栏真的在生效）；并发恢复冲突率；恢复后状态不一致条数。
- **一人 / 小团队降级**：本地 Agent 场景用"工作目录互斥锁 + 单写者"；批量导出/发布用"写临时文件 + 原子 rename"。
- **原文引用**（ch7）：「失去心跳只表示平台暂时观察不到实例，旧进程仍可能继续运行」「仅更新控制面的编号，不能阻止旧进程继续产生影响」「只有任务能够从已有成果继续推进，才能确认恢复完成」。

### 卡9 三类负载分开验收，并用"单位成功任务成本"算账

- **要解决的问题**："我们上了沙箱/沙箱化，所以有效"。
- **做法**：按三类负载分别建基线——① 工具执行（用沙箱：编排在外，按步调用代码/浏览器）；② 长时任务（Agent 在沙箱内：延续项目状态）；③ 训练与评测（批量独立交互、收集轨迹）。每类记录分阶段耗时（排队、分配、镜像准备、挂载、初始化、模型等待、工具运行、验收、释放），P95/P99 必须写明"从哪个事件到哪个事件"；成本用：
  **单位成功任务成本 =（窗口内归属该负载的计算 + 状态存储 + 网络 + 预热费用）÷ 成功完成的任务数**，失败与重试消耗同样计入。
- **前置条件**：有"成功"的客观判据（产物可读、测试通过、指标达标）。
- **适用边界**：所有引入执行环境的场景；对比时保持口径一致（含模型调用费）。
- **反例 / 失败模式**：用空环境启动耗时代表完整业务响应；把环境故障算进模型能力；评测环境被 Agent 改动后仍用同一份评分材料（需独立保护评分规则与关键验证材料）。
- **可验证指标**：完成率、有效反馈率、产物验收通过率、首次可用时延、重复准备耗时、**单位成功任务成本**、有效轨迹吞吐、重置耗时、分支污染率。
- **一人 / 小团队降级**：不建平台，只做一件事——为你的 Agent 工作流写一个"完整任务链基线脚本"，每次改动都跑一遍并对比 P50/P95 与"一次成功任务花了多少钱"。
- **原文引用**（ch7）：「沙箱快照不能自动回退外部数据库、已经发送的消息或已经完成的业务操作」「对于会修改代码和文件的 Agent，评分规则与关键验证材料应受到独立保护」「高频、稳定的计算可以进一步沉淀为固定工具」「单位成功任务成本」「不能仅依据是否采用沙箱判断收益」。

## 3. C 组：状态、记忆与检索（ch8）

### 卡10 运行时状态三件套：Event Log / Checkpoint / Artifact

- **要解决的问题**：任务跑了几小时，实例一重启就"失忆"；或者反过来，什么都记下来导致无法判断事实。
- **做法**：
  1. **Event Log（只追加）** 记录任务事实变化；强一致边界放在**任务/会话/业务对象**级，同一任务内有序、独立任务并行；
  2. 事件与当前状态同时维护时用事务或可靠 outbox 保证同步，并按事件 ID 去重；
  3. **Checkpoint** 记录"某个可信时刻的状态"，内容是当前阶段、已完成/未完成步骤、工具结果引用、工作区版本、等待条件、状态版本——不是上下文拷贝；在关键边界（外部调用前后、人工确认前后、工作区重要变更后、交接前）主动打点，并支持增量快照；
  4. **Artifact** 保存可复用成果并给稳定身份 + 元数据（来源任务、版本、生成者、输入依据、审批状态、权限、保留策略）；
  5. 先定义状态对象的正确性边界，再匹配存储能力；别让所有状态落进同一种引擎。
- **前置条件**：稳定 Task ID；事件/检查点/产物的写入是幂等或可去重的。
- **适用边界**：分钟以上的任务；短对话不需要完整三件套。
- **反例 / 失败模式**：把诊断日志或模型输出当成可重放事件记录；把所有 Agent 写进同一条全局日志形成串行瓶颈；无限累积事件而不做保留策略。
- **可验证指标**：恢复点损失（实例故障后重做的步骤数）；恢复耗时 P95；Evidence→Outcome 可回溯率；产物引用失效数（应为 0）。
- **一人 / 小团队降级**：`tasks.jsonl`（事件追加）+ 每 N 步一个 `checkpoints/<ts>.json` + `artifacts/` 目录用内容哈希命名。
- **原文引用**（ch8）：「同一任务内部的状态变化需要有明确先后关系，而相互独立的任务可以并发执行」「先定义不同状态对象的正确性边界，再为其匹配相应的存储能力」「实例本地文件可以提供快速读写，却不应成为唯一事实来源」「Agent 需要的不只是容量与吞吐」。

### 卡11 分层工作区与不可变产物：区分"试错"和"交付"

- **要解决的问题**：Agent 的临时文件、失败尝试和最终成果混在一起，没人说得清哪个是结论。
- **做法**：
  1. **分层工作区**：底部只读基础层（运行环境、依赖、公共数据）→ 中间共享数据层 → 顶部任务私有可写层；共享不变部分、隔离变化部分；
  2. **Copy-on-Write 快照/分支**：快照给出可回滚的版本边界，并记录"哪个任务、哪个阶段、基于什么输入、由谁生成"；运行时 Checkpoint 记录对应快照引用；
  3. **不可变产物**：进入 Artifact Store 的成果不再原地修改，后续变更生成新版本，引用方永远知道自己读的是哪一份；
  4. 保留策略分层：一次性中间文件按策略清理，正式成果按业务/合规周期保存。
- **前置条件**：工作区可挂载、有私有可写层；产物有稳定引用方式。
- **适用边界**：会产生文件与数据集的任务（分析、代码、报告）；纯问答不需要。
- **反例 / 失败模式**：把实例本地目录当唯一事实来源；用"环境回滚"撤销已提交到外部系统的操作；多个 Agent 直接改同一目录，退化成不可审计的文件覆盖竞争。
- **可验证指标**：产物引用可解析率；回滚正确率；临时文件清理及时率；跨 Agent 合并冲突率。
- **一人 / 小团队降级**：Git 就是你的快照与分支；把"交付物"放到单独 `deliverables/` 目录，文件名带日期与内容哈希。
- **原文引用**（ch8）：「环境回滚不撤销已经提交到外部系统的操作」「一次性中间文件可以在任务结束后按策略清理」。

### 卡12 记忆写入管线：只记经过验证的，并允许遗忘

- **要解决的问题**：Agent 把猜测当事实，越用越自信；旧偏好一直污染新回答；用户要求删除却删不干净。
- **做法**：
  1. **抽取**：只抽取对后续交互有预测价值的信息；寒暄、临时调试指令、一次性查询不入长期记忆；
  2. **合并与冲突消解**：与已有记忆做语义匹配、去重、覆盖或标记"待确认"；保留来源与边界（谁产生、经过什么验证、适用哪个场景、何时写入、是否仍有效）；
  3. **检索**：语义 + 关键词 + 实体关系多路召回后统一排序；时间衰减只作加权，**不能用来淡出长期有效的约束**；
  4. **遗忘**：归档 / 降召回权重 / 删除是三种不同操作；删除要同步处理原始记录、摘要、索引与缓存，并防止后续重建把它重新引入；无法确定的概括保留"待确认"状态而不是硬写；
  5. 人设与身份配置（Persona）由构建方显式维护，不来自 Agent 经历。
- **前置条件**：记忆条目有来源字段与写入时间；能区分原始记录与摘要/索引副本。
- **适用边界**：有跨会话复用的产品；一次性任务不需要记忆系统。
- **反例 / 失败模式**：把对话历史整段存进向量库当记忆（"共用一个向量数据库"不等于团队记忆）；用引用频率当正确性证据；只删主记录、索引里还在。
- **可验证指标**：记忆陈旧引用率（后续任务引用了已被更正记忆的比例）；删除生效时延（请求删除 → 索引与缓存清理完成）；记忆命中率与误命中（命中但不该命中）比例。
- **一人 / 小团队降级**：一个 `MEMORY.md`（带"最后确认时间"和"来源"两列）+ 每月人工复核一次；删除就是直接删行 + 重建索引。
- **原文引用**（ch8 / ch11）：「记忆不是原始对话的简单归档，而是经过结构化加工后的认知沉淀」「未经验证的内容如果直接进入长期记忆，容易在后续任务中被当作事实反复引用」「归档、降低召回权重与删除是不同操作」「用户要求删除的信息需要同步处理原始记录、摘要、索引和缓存」「时间衰减可以提高近期记忆的排序权重，但不适用于所有信息」。

### 卡13 检索前过滤权限，并区分权威事实与派生视图

- **要解决的问题**：向量检索跨租户召回后再过滤，泄漏发生在"候选生成"阶段；索引与主数据不一致导致结论陈旧。
- **做法**：
  1. 权限过滤前置到**索引空间、检索条件与重排序策略**，让 Agent 只在被授权的语义空间里召回；覆盖检索到生成的全链路，避免推理成为旁路；
  2. 一致性分级：影响任务正确性的运行时状态（租约、工具调用结果、关键检查点）以强一致/可验证提交为目标；向量索引、全文检索、统计聚合接受短暂最终一致，但要能说出新鲜度与对应源数据版本；
  3. 写入顺序：先可靠提交权威事实，再异步或增量推动索引与副本；查询流量切换到新索引前必须达到可用水位；
  4. 回答要能标注引用的对象版本、索引时间与来源，让"过期"能被定位到数据还是模型；
  5. 交互只能提出候选事实或模型修订建议，**不得把模型推测直接写成组织规则**。
- **前置条件**：租户/权限标识能进入索引与查询参数；索引与主数据之间有水位或版本号。
- **适用边界**：多租户或含敏感语料的知识/记忆检索；单用户本地库可简化。
- **反例 / 失败模式**：先跨租户召回再在应用层过滤；把索引当权威事实；用回滚掩盖脏数据。
- **可验证指标**：越权召回条数（应为 0）；索引滞后 P95；结论可溯源率（回答能定位到文档段落与版本的比例）。
- **一人 / 小团队降级**：检索前先用目录/命名空间隔离（例如每个客户一个 collection 或一个 `docs/<client>/` 前缀过滤），不要靠回答后过滤。
- **原文引用**（ch8）：「语义检索若先跨租户召回、再过滤结果，可能已在候选生成阶段引入不必要的数据暴露风险」「不得将模型推测直接写成组织规则」「故障恢复同样遵循这一分工：控制平面定义恢复策略，执行平面的 Runtime 负责落实」。

## 4. D 组：通信语义与 Multi-Agent 协作（ch12 / ch11）

### 卡14 通信语义四档：选"最低充分"，并写出六要素契约

- **要解决的问题**：一律用长连接/同步调用，长任务撑不住；或者一律上消息队列，简单调用复杂化。
- **做法**：把通信面分为**人机面、能力面、协作面、内构面**，交互语义分四档：
  S1 请求—响应 / S2 请求域流式 / S3 任务句柄（提交后凭 ID 查询或订阅）/ S4 持久通道（订阅、确认、补读）。
  逐段检查"这段通信需要独立任务句柄吗？需要补读事件吗？"再选档；默认从最低充分档开始，只在实际需要的链路加机制。每段通信的契约写清六个要素：**标识、顺序、投递保证（至少一次/至多一次/恰好一次 + 去重键）、续传点、生命周期、背压**。
- **前置条件**：会话与任务有独立标识（连接只是当前传输路径）；结果查询与续传分别声明。
- **适用边界**：全部 AI 原生应用通信；短调用用 S1，人机交互用 S2，Agent 交接用 S3，削峰与补读才上 S4。
- **反例 / 失败模式**：把流式结束当作任务结束；有任务句柄就以为有事件重播；把推送通知当成结果送达（它是"去拉取"的触发器）；把协议无状态理解成业务无状态；把"会话 = 常驻进程"绑死导致扩容迁移困难。
- **可验证指标**：断连后可恢复率（重连后能补齐遗漏事件/查到任务状态的比例）；长任务查询成功率；投递重复率与幂等丢弃率；积压深度。
- **一人 / 小团队降级**：两档就够——短调用同步，长任务"提交 + 轮询一个 URL"。补上 `task_id`、状态查询接口、幂等键三样，其余不必上。
- **原文引用**（ch12）：「选型的起点是为每个通信面选择成本与风险可接受的最低充分语义，而不是统一采用最高档位」「会话与任务应有独立标识，连接只是当前的数据传输路径」「有任务句柄不一定有完整事件重播，有事件序号也不自动保证业务状态可恢复」「推送通知的角色是"去拉取"的触发器，结果的可寻址性仍由任务查询保证」「协议无状态不等于应用无状态」「不能将无状态核心解释为没有持续通知连接」「任务状态、检查点、消息日志和消费位置各有职责」「需要逐段检查调用时限、结果获取和恢复要求，再选择合适的通信方式」。

### 卡15 通道键决定治理粒度；决策与执行分离（手脑分离）

- **要解决的问题**：一个共享队列下，某客户/某会话的突发拖垮所有人；执行环境成了不能替换的"宠物"。
- **做法**：
  1. **通道键选在业务并发单元上**（会话标识、用户、用户×模型组合），让通道天然成为隔离、限流、观测与回收的粒度；
  2. **手脑分离**：Harness（决策）无状态，凭会话标识唤醒、拉取事件历史续跑；沙箱降级为"一只普通的工具"，失败表现为工具层错误而不是会话中断；会话是追加式事件日志，不等于模型上下文窗口；
  3. 反模式：会话与常驻工作进程一对一绑死（持续占用算力、断线丢上下文、扩容迁移困难）。
- **前置条件**：会话状态外置且可重放；执行侧可按需申请/释放（见卡6、卡7）。
- **适用边界**：多会话、多执行环境的中等以上规模系统；单机单会话不必。
- **反例 / 失败模式**：用共享队列做隔离却额外补一套路由表；把某个容器地址当长期入口；以为"进程还活着 = 任务还在跑"。
- **可验证指标**：单通道积压隔离成功率（一个通道堆积不影响其他）；会话恢复成功率；会话状态占用的单位成本；换机后任务续行成功率。
- **一人 / 小团队降级**：按"项目/客户"分目录 + 分队列（或至少分限流键），不要一个全局队列；执行侧保持"随时可重启"，状态在文件里。
- **原文引用**（ch12）：「通道以什么业务标识命名，就决定了隔离、限流、观测与回收以什么粒度进行」「把通道键选在业务并发单元上，让通道天然成为治理单元」「会话不等于模型的上下文窗口」「任务不属于某台机器，机器只负责当前这一棒」「将会话与常驻工作进程一对一绑死」。**【外部案例】**书中把该结构归到 Anthropic 的"meta-harness"与 Qoder Cloud Agent 的四层手脑分离（Agent Runtime / MQ / Sandbox Worker / Session State），并用 RocketMQ LiteTopic 承载海量的 Session-as-Topic；引用其结论时要注明是第三方材料。

### 卡16 Multi-Agent 上线判据：收益必须覆盖协调成本

- **要解决的问题**：为了"多 Agent"而多 Agent——所有信息汇到一个主管，反而回到单点瓶颈。
- **做法**：
  1. 先判断任务是否**真的**有专业分工、独立权限、可并行交付、故障隔离需求；否则用单 Agent；
  2. 组织拓扑三选一（主管—执行 / 对等协作 / 分层编排），并写明谁决定什么、何时寻求协调；
  3. 明确判断标准：只有当分工、并行、隔离与治理收益覆盖沟通与协调成本时才值得；
  4. 避免"主管替执行者解决专业问题 + 执行者等主管决定每一步"的双向低效；
  5. 验收口径是**成员分工与共同交付是否成立**，而不是"有几个 Agent"。
- **前置条件**：每个成员有清晰的能力边界与责任归属；共享事实落在 Task State / Artifact（见卡17）。
- **适用边界**：需求分析 + 实现 + 测试 + 安全 + 上线审批这类跨专业链路；单一目标的短任务不要上。
- **反例 / 失败模式**：主管 Agent 成为上下文与执行瓶颈；角色只停留在名称上；Agent 交接被当成权限扩大；子代理未显式授权就当作团队成员。
- **可验证指标**：协调开销比（协调消息数 ÷ 有效执行步骤数）；任务端到端时长 vs 单 Agent 基线；返工轮次；成员阻塞时长。
- **一人 / 小团队降级**："一人公司"其实是单成员团队——保持单 Agent，把子任务做成 Task Run 而不是新 Agent；只有在**并行**真的省时间时才开第二个进程。
- **原文引用**（ch11）：「如果所有信息都必须先汇总到一个主管 Agent，再由它决定每一个步骤，多智能体系统很容易重新回到单点决策的模式，主管 Agent 也会成为新的上下文和执行瓶颈」「只有当专业分工、并行执行、故障隔离和过程治理带来的收益，能够覆盖沟通与协调成本时，Agent 团队才真正具有价值」「团队编排需要验证的，是成员分工与共同交付是否成立」。

### 卡17 最小充分共享 + Task 级停止条件

- **要解决的问题**：共享不足导致重复探索与状态冲突；共享过量把噪声与错误扩散给所有人；任务无限重试烧钱。
- **做法**：
  1. **共享的是上下文来源，不是同一个 Context 窗口**：目标、约束、任务状态、已确认事实与产物构成来源，每个 Agent 按角色/任务/权限/阶段取自己需要的视图；
  2. **Handoff 四类信息**：目标（范围与交付要求）、已知事实（已确认信息与已完成工作）、待处理事项（未解决问题、依赖与关键约束）、可用引用（可继续使用的 Task / 数据 / Artifact 引用）；完整搜索过程与未验证的中间推理通常不传递；
  3. **事实载体分工**：消息说"发生了什么"，Task State 与 Artifact 记录"当前事实是什么"；接收方通过可访问的 Artifact 引用取成果，而不是消息摘要或本地绝对路径；
  4. **停止条件在根 Task 开始前约定**：总时间/成本预算、最大委派深度、派生任务数、单项重试次数、返工轮次，以及"连续多轮无新增有效产物"时的处理；触顶后暂停新委派、保留已完成结果与剩余预算，交人工判断；单个 Agent 的重试上限不能替代这一级约束；
  5. 已有材料足以证明结果时，不为形式完整重复制作报告。
- **前置条件**：Task / Task Run / Session 三者分别标识并按需关联；成员能读到产物引用。
- **适用边界**：多成员协作与长程任务；单人工作流适用其"停止条件"部分。
- **反例 / 失败模式**：把对话历史当 Team State；消息发送成功就认为任务被承接；一次性把全部上下文广播给所有成员；无人值守下自动返工无限循环。
- **可验证指标**：重复劳动率（同任务内重复执行已确认步骤的比例）；交接后可继续率；停止条件触发次数与触发后人工介入时长；派生任务数/根任务数。
- **一人 / 小团队降级**：给自己写一份"任务契约"：目标、交付物、预算上限（次数/时长/金额）、停止条件；写在任务文件头部，每次启动先读它。
- **原文引用**（ch11）：「团队共享的是 上下文来源，而不是完全相同的 Context」「成员可以通知一份报告已经生成，但接收方应通过可访问的 Artifact 引用取得报告本身」「本地 Agent 生成报告后，如果只回复一个绝对路径，其他机器上的成员通常无法读取」「团队级停止条件需要在根 Task 开始前约定」「消息可以触发任务或补充信息，但发送成功不代表任务已经被承接。」「一次消息可以触发协作，却不能单独代表工作已经被承接或完成」「已有材料能够证明结果时，也不必为了形式完整重复制作报告」。

## 5. E 组：网关与流量治理（ch9）

### 卡18 严格预算 ≠ 阈值检查

- **要解决的问题**：以为"请求前查余额、响应后扣减"就能卡住花费；并发下直接超支。
- **做法**：区分四种机制并各自承诺边界——请求速率限制（QPS/令牌桶）、token 时间窗限制（请求前检查、结束后累计）、余额型配额（准入查余额、结束扣减）、**严格预算**（可证明的最大消耗 + 准入时原子预留 + 幂等结算 + 退款）。严格预算的不变量：

  ```text
  可用额度 = 已授权额度 − 已结算消耗 − 在途预留
  准入条件 = 本次最大可计费消耗 ≤ 可用额度
  ```

  预留要覆盖输入、受约束的最大输出与其他计费项，**每次重试单独占用额度**；流式中断或结果未知的请求不能因租约到期就无条件退款；token 配额与金额预算分开建模。
- **前置条件**：调用能拿到可验证的最大消耗；预留与结算是同一原子操作或等效一致性事务。
- **适用边界**：多团队/多项目的无人值守 Agent；个人单用户可只做速率限制 + 日预算告警。
- **反例 / 失败模式**：把阈值插件当严格上限宣称；把缺失 usage 记为零消耗；用 credits 当统一货币；只在某一层预留导致悬挂记录。
- **可验证指标**：预算超限率（实际消耗/授权额度 > 1 的窗口占比）；未结算用量占比与对账差异；重试造成的额度占用占比。
- **一人 / 小团队降级**：模型调用加"每日 token 上限 + 超限自动降级到小模型/暂停"，用供应商账单或自建 usage 表对账；达不到原子预留就如实声明"软预算"。
- **原文引用**（ch9）：「两次最大消耗分别为 80 的请求同时通过余额检查，最终消耗就可能达到 160」「响应后的原子扣减可以避免丢账，但不能撤销已经发生的消耗」「可用额度 = 已授权额度 − 已结算消耗 − 在途预留」「区分时间窗限制、余额配额和严格预算」「若现有插件仅支持阈值控制，就如实声明边界」「缺少 usage 不能记录为零消耗，客户端取消也不能证明上游停止生成」「缓存键还必须区分租户、权限范围、模型版本、系统提示和知识版本」。

### 卡19 重试预算跨层传递：别让 3×3=9

- **要解决的问题**：客户端重试 3 次、网关重试 3 次，一次用户调用打到上游 9 次；故障被多层恢复机制放大且无法归因。
- **做法**：
  1. 先判断**能否重试**，再选重试目标：限流看重置时间与配额，服务端错误只在调用语义允许时重试，认证错误直接终止并修凭证，上下文超限交给应用/Harness 决定而不是截断历史；
  2. 尝试预算**跨层传递**：总截止时间是绝对时间，网关只保留必要的传输余量；剩余尝试额度由调用方给出，网关按 `call_id` 原子扣减，耗尽返回明确错误；
  3. 每次实际尝试用稳定的 `call_id` + `attempt_id` 关联，重试、摘除、模型切换分开记录；
  4. 切换 provider 前检查工具、结构化输出、数据地域与模型能力兼容性；没有验证过的兜底路径返回可解释失败。
- **前置条件**：调用有业务幂等键或能确认尚未提交执行；有跨层传递的截止时间与额度。
- **适用边界**：所有有重试的调用链（SDK → 网关 → 上游）；不重试的路径也建议记录 attempt。
- **反例 / 失败模式**：按 HTTP 状态或"是否收到首包"决定重试（请求可能已计费或已触发副作用）；流式响应向客户端提交后还想透明重放；真实探活产生费用并被多副本放大。
- **可验证指标**：**重试放大系数** = 上游实际尝试次数 ÷ 逻辑调用次数；未知结果率；每逻辑调用的成本分布 P95。
- **一人 / 小团队降级**：在 SDK 层做唯一重试点，网关/代理层重试关闭；用 `idempotency_key` + 总超时兜底。
- **原文引用**（ch9）：「如果 SDK 客户端对一次逻辑调用最多尝试 3 次，网关对每次转发又最多重试 3 次，那么一次用户可见的调用最多会到达上游 9 次」。

### 卡20 工具授权：默认拒绝、审批后重新准入

- **要解决的问题**：模型能"看见"就能"调"；审批过了就直接执行；超时把高风险操作悄悄降级成只读。
- **做法**：
  1. **协议说明不是身份证明**：认证（独立凭据的主体映射）→ 协议校验 → 授权（主体/工具/参数）→ 转发，四步分开；逐请求元数据只服务于协议校验与转发；
  2. **默认拒绝**：工具权限取调用者原有授权、工作负载授权、任务委托范围与资源侧限制的交集；过滤工具列表只是减少误选，**调用时必须再次鉴权**；输入 Schema 校验只保证结构合规，不证明业务授权；
  3. **审批未决的请求不得转为实际执行**；批准后要**重新准入**（身份、委托、参数摘要、预算预留），因为等待期间这些都可能过期；审批记录含调用者、工具及版本、参数摘要、风险与有效期，回调需认证与防重放；
  4. 超时不自动降级为只读执行；无幂等支持的外部操作在结果不明时交给业务查询或补偿；
  5. 入口要"不可绕过"才有资格当策略执行点：凭证不下发、出口网络受控、直连路径禁止且旁路受审计；否则它只是集中入口。
- **前置条件**：主体与凭证分离；工具调用有统一入口；策略有版本与命中记录。
- **适用边界**：多 Harness、多团队共享工具的平台；工具少时可在框架内做同等检查。
- **反例 / 失败模式**：用模型自述身份或 `clientInfo` 扩大权限；REST-to-MCP 模板放开可变主机/路径造成 SSRF；只靠"只读 SQL 前缀判断"判断写操作；日志记录带密钥的地址与请求头。
- **可验证指标**：策略拒绝率与拒绝原因可解释率；审批后重新准入被拦截次数；绕行直连次数（应为 0）；高风险工具未授权调用数（应为 0）。
- **一人 / 小团队降级**：不做网关，做"工具白名单 + 参数 Schema 校验 + 危险操作二次确认（人工粘贴确认码）"；密钥放环境变量、绝不进 prompt。
- **原文引用**（ch9）：「协议说明不是调用者身份证明」「过滤 `tools/list` 可以减少模型误选无权工具，但 `tools/call` 仍必须再次鉴权」「权限应取调用者原有授权、工作负载授权、任务委托范围和资源侧限制的交集」「审批未决的请求不得转为实际执行」「对于无幂等支持的外部操作，超时后的执行结果不确定必须交由业务查询或补偿流程处理，不能由网关盲目重试」「客户端看到同一个模型名，不应意味着平台可以不经验证地替换其实际能力」。

### 卡21 成本与结果归因：从 Session 扩展到 Task 分层账本

- **要解决的问题**：知道"这轮对话花了多少"，回答不了"这项长任务花了多少、恢复了几次、结果如何"；把网关 200 当业务成功。
- **做法**：建立归因链路 `task_id → session_id → turn_id → model/tool call → attempt_id`；`task_id` 来自业务应用，网关只生成请求/尝试标识；客户端带来的关联头要绑定已认证主体并校验租户范围，防伪造转移费用。分层记录：Attempt（端点、计费模型、用量来源、状态、错误、耗时）/ Call·Turn（多次尝试、上下文变化）/ Session（累计用量、等待与失败分布）/ Task（跨会话归集、恢复阶段、运行资源费用、Outcome 引用）。**网关请求成功率与业务任务完成率分别统计**；缺少 Outcome 或未结算成本的任务保留对应状态。
- **前置条件**：可信身份与稳定的任务标识；记录含身份引用、任务/会话/轮次关联、实际模型、用量来源、状态、时延与策略版本。
- **适用边界**：长程任务、需要 FinOps 的团队；短会话可只做 Call/Session 两层。
- **反例 / 失败模式**：把一条 Trace 或 Session 当完整 Task 账本；把网关记录冒充完整任务账本；用高基数字段（task_id、session_id）做指标标签拖垮监控；内容字段无差别全量落日志。
- **可验证指标**：**成本归因完整率** = 可归因到 `task_id` 的费用 ÷ 总费用；Outcome 回填率；未结算用量占比；单位任务成本（按任务类型分）。
- **一人 / 小团队降级**：每次 Agent 运行写一条 `usage.json`（时间、任务名、模型、输入/输出 token、耗时、结果状态），月底用一条 SQL 汇总到"每个任务多少钱"。
- **原文引用**（ch9）：「网关记录是调用账本的一部分，不应冒充完整任务账本」「网关的请求成功率与业务任务完成率分别统计」「网关只保证准入、转发与记录的一致性，既不能仅凭请求成功断言任务完成」「Evaluation 不天然拥有发布授权」「不能因为网关是多副本，就认为其依赖已经没有单点」。

## 7. 一人公司 / 小团队降级路线

原则：保留**语义分层与判定权**，砍掉平台与中间件。

| 卡 | 完整做法 | 降级做法（1 人 / 2—5 人） |

| 卡1 | 五层完成语义 + Verifier | `runs` 表两列：`status`（执行）与 `verified`（业务采纳），人工只改后者 |
